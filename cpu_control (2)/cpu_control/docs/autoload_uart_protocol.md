# 三线自动加载版 UART 外部存储协议

对应 RTL：`rtl/soc/autoload/image_bridge_autoload.sv`。这是独立新版本；旧 `image_bridge.sv` 仍保留原来的被动 IMIO 功能。两种桥选择其一，不在同一个 UART 上自动切换。

## 1. 谁主动，谁回复

FPGA 是读取发起方，外部设备是数据提供方。CPU 拉高 `load_req` 后，桥主动发送 IMIO 读请求，外部设备收到后返回 IMOR 数据。外部设备必须有执行该协议的控制器，不能把裸 Flash 的引脚直接接到 UART。

- UART：8N1，空闲高电平，字节内低位先发；无 RTS/CTS。
- 默认时钟 50 MHz、波特率 115200；分频为 `CLOCK_HZ/BAUD` 的整数商，必须至少为 4。
- 多字节整数、CRC 字段均为小端。
- 同一时间只允许一笔未完成请求。设备只针对收到的请求回复，不主动推送下一包。
- 设备应在请求完整结束后回复；推荐至少留 1 个 UART 位时间的转向间隔。当前测试模型留 3 位时间。
- 接收计时从请求发送完毕开始；每收到一个字节重新计时。无响应或字节间隔达到 `TIMEOUT_CYCLES` 时失败。
- 不自动重试，不协商波特率，不支持任意终端文本协议。

## 2. FPGA 发出的读请求：固定 16 字节

| 字节偏移 | 长度 | 内容 |
|---|---:|---|
| 0 | 4 | ASCII `IMIO`：49 4D 49 4F |
| 4 | 1 | 操作码 02：读外部存储 |
| 5 | 1 | tag：当前请求序号，8 位循环 |
| 6 | 2 | 本包数据长度，1～CHUNK_BYTES |
| 8 | 4 | 外部源字节地址：SOURCE_BASE + 已加载长度 |
| 12 | 4 | 前 12 字节的 CRC32 |

地址表示外部设备中的位置，不是 FPGA SRAM 地址。桥在 FPGA 内部另外计算目标地址 `LOAD_BASE + 已加载长度`。

## 3. 外部设备返回：16 + N 字节

| 字节偏移 | 长度 | 内容 |
|---|---:|---|
| 0 | 4 | ASCII `IMOR`：49 4D 4F 52 |
| 4 | 1 | status，正常为 00 |
| 5 | 1 | 原样返回请求 tag |
| 6 | 2 | N，必须等于请求长度 |
| 8 | 4 | 原样返回请求源地址 |
| 12 | N | 连续 N 字节数据 |
| 12+N | 4 | 前 12+N 字节的 CRC32 |

本版按请求长度接收固定总长度，再检查字段。非零 status、错误长度/地址/tag 都不能继续加载；若发送一个较短的错误应答，桥可能以接收超时结束，而非立刻识别 status。设备成功回复须严格遵守上表。

CRC32 为反射形式：多项式 `0xEDB88320`，初值 `0xFFFFFFFF`，结束取反。与 Python `zlib.crc32(bytes)` 一致。

## 4. 分包与整批校验

默认外部地址 `0x00000000` 起的 256 字节，加载到 SRAM `0x00000100..0x000001FF`；每包 64 字节，共 4 包。最后一包可以小于 CHUNK_BYTES。

桥先收完一包并验证包头/包 CRC，再逐字节写 SRAM，使用现有 `io_mem_req/we/addr/wdata/be` 和 `gnt/error`。每次写入成功确认后，才计入已加载数据。

所有载荷按加载顺序再次计算整批 CRC，与 `EXPECTED_CRC32` 比较。演示数据的期望值为 `0xFE679CC9`，不含包头和包 CRC。更换内容须同步更改期望值。

包 CRC 错误：该包一个字节也不写入。整批 CRC 错误：数据已写入 SRAM，但整批判无效，固件不启动 CNN。此前成功写入的包不会回滚，不能把失败后的 SRAM 当作有效输入。

目标范围必须在 SRAM 内且不能覆盖 CPU 本地寄存器 `LOAD_CTRL_ADDR..LOAD_CTRL_ADDR+7`，源/目标范围不能跨越 32 位地址空间末尾。应用还须避免覆盖结果邮箱和其他工作区；硬件没有自动分配内存。

## 5. CPU 与图像桥的三线握手

| 阶段 | load_req | load_complete | load_error |
|---|---:|---:|---:|
| 空闲 | 0 | 0 | 0 |
| CPU 发起、桥加载 | 1 | 0 | 0 |
| 成功结束，等待 CPU 确认 | 1 | 1 | 0 |
| 失败结束，等待 CPU 确认 | 1 | 1 | 1 |
| CPU 保存结果后确认 | 0 | 暂为 1 | 原结果 |
| 桥撤销完成 | 0 | 0 | 0 |

成功后桥返回空闲，可由固件发起下一批相同配置的加载。失败后桥进入 HALTED，`bridge_error` 保持 1，需系统复位才可重新加载，迟到的串口回复不再触发 SRAM 写入。

`load_complete` 表示本次已结束，包括成功或失败；不是单周期脉冲。CPU 必须在确认之前保存 `load_error`。

## 6. CPU 封装本地寄存器

这两个寄存器在 `cpu_core_autoload` 内部实现，占用 CPU 数据地址空间的两个保留字，不从顶层分流 CNN MMIO，也不改变原 Datapath 地址译码。

| CPU 地址 | 属性 | 内容 |
|---|---|---|
| 0x40 | 读/写 | bit0 为 load_req；整字 SW 写 1 发起，完成后 SW 写 0 确认 |
| 0x44 | 只读 | bit0 为 load_complete；bit1 为 load_error；其他为 0 |

默认地址可由 `LOAD_CTRL_ADDR` 参数一起移动，但须位于 SRAM 地址窗口、8 字节对齐，固件也必须同步更新。CPU 访问这两个字不会送到 datasram A 口；读返回仍为一拍。CNN/图像桥不能把它们当作 CPU 寄存器访问，软件须预留这段地址。

仅整字 SW 有控制效果；SB/SH 忽略。未完成时写 0 不能取消，已发起时重复写 1 不会排队；写状态寄存器忽略。等待请求撤销和完成撤销后才允许再次请求。

本地控制并不检测 CNN 的全部工作状态。当前固件按“加载成功→启动 CNN→等待结束”的顺序运行，不会在 CNN 工作时重新加载。以后增加多帧/双缓冲时须另行设计调度。

## 7. 调试与错误

内部 `u_image_bridge.error_code` 供仿真观察，不增加 CPU 外部端口：

| 值 | 含义 |
|---:|---|
| 1 | 固定加载范围配置错误 |
| 2 | UART 帧错误 |
| 3 | 外部回复/字节间超时 |
| 4 | 包头、status、tag、长度或地址不匹配 |
| 5 | 包 CRC 错误 |
| 6 | SRAM 写入返回 error |
| 7 | SRAM 写入等待 gnt 超时 |
| 8 | 整批 CRC 错误 |
| 9 | 非法状态 |

`led_busy` 仍表示图像桥忙，不表示 CNN 忙；`led_ready` 是桥可接受请求，不是整个人脸任务完成；`led_error` 汇总桥错误及 CNN 存储故障。应用计算失败还可由 CPU 结果邮箱报告。

外部设备的一个可执行参考模型见 `tb/integration/tb_soc_autoload.sv`。它在仿真中扮演真实设备，实际部署需在选定外部控制器上实现等价协议。
