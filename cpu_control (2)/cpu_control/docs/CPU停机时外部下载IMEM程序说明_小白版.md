# CPU 停机时，由外部电脑下载 IMEM 程序（小白版）

日期：2026-10-08。本文按你最新提出的范围设计：**只停 CPU，电脑写 IMEM；其他模块不跟着停；正式运行时，仍由 CPU 向 IMEM 取指。**

本文是方案说明，没有修改 RTL，也没有把这一功能说成已经实现。它细化并替代上一篇说明中“下载时同时复位 CPU 和 CNN”的建议；本方案不因下载而复位 CNN 或共享数据 SRAM。

## 1. 你的想法可行，最终应当这样使用

可以把 IMEM 看成一本能重写的“CPU 指令书”：

- **运行时：**CPU 读这本书，下载器不能改它。
- **下载时：**CPU 停下来，电脑通过下载器改写这本书。
- **下载完成：**确认写对、写全，再让 CPU 从程序入口重新读这本书。

这不是让 CPU 一边读、一边被电脑改指令，也不是让 CPU 改从数据 SRAM 取指。CPU 正式工作的路径保持原样。

推荐第一版把“CPU 不工作”定义为：**CPU 被独立保持在复位状态，确认它不再发出取指、数据访存或 CNN MMIO 请求。** 下载后从 `RESET_PC` 重新启动，默认地址为 0。

这会清除 CPU 的寄存器和流水线状态，不支持从旧程序暂停的位置继续执行。如果以后需要“暂停后原地续跑”，要另做完整的暂停和状态保持机制；本次需求不必增加这部分。

## 2. 整体接线长什么样

```text
电脑
  │ 程序数据、校验、启动命令
  ▼
UART RX/TX → 下载控制逻辑 ── 写入/读回校验 ──┐
                 │                         ▼
                 │                     可写 IMEM
                 │                         │
                 │                 原来的固定一拍取指接口
                 │                         ▼
                 └── CPU独立复位控制 ──── CPU

与此同时，下面的连接继续工作：
CNN ── 原生 mem_* ── datasram
图像桥 ── io_mem_* ── datasram
```

电脑不是直接把两根串口线接到存储单元上。下载控制逻辑负责接收字节、解析命令、拼成指令、提供写地址和写使能。

本项目已有 UART RX/TX，可以复用，不必默认新增外部信号引脚。内部则需要新增 IMEM 下载通路及 CPU 独立复位连线。实际串口仍需公共地、电平匹配和正确的板级引脚约束。

## 3. IMEM 应当怎样改

当前 [imem_rom.sv](../partners/datapath/delivery/rtl/soc_memory/imem_rom.sv) 只有取指读口，默认容量 64 KiB，未提供运行时写入口。建议保留这个原始文件，另建一个可写 IMEM 模块，在顶层替换实例。

新模块在逻辑上提供两组接口：

| 接口 | 谁使用 | 作用 |
|---|---|---|
| 原取指接口 | CPU | `imem_addr / imem_re / imem_rdata`，时序保持固定一拍 |
| 新下载接口 | 下载控制逻辑 | 指定地址、写入指令、读回校验、返回完成或错误 |

新下载接口至少需要表达以下信息，信号名称和具体协议待实现时确定：

| 信息 | 小白理解 |
|---|---|
| 请求及读写类型 | 这次是要写指令，还是读回检查 |
| 地址 | 写到 IMEM 的哪个位置 |
| 写数据 | 要放进去的 32 位内容 |
| 完成/错误 | 这次访问有没有成功结束 |
| 读回数据 | 实际存进去的内容是什么 |

第一版可只支持按 4 字节对齐的整字读写，电脑工具将程序整理成完整的 32 位指令字。程序装载地址固定从 0 开始，默认容量上限 64 KiB；大文件不能写出 IMEM 边界。若尾部需要补齐，应由工具按明确规则处理。

**两个逻辑接口不代表一定要使用双端口 RAM。** 因为 CPU 和下载器不会同时访问，可以用工作模式切换存储器的访问者；也可以使用双端口 RAM 实现。最终以综合结果和资源情况选择，但要满足：

1. CPU 运行时，下载写入必须被拒绝，不能悄悄覆盖指令。
2. 下载时，CPU 已停止取指，下载器独占 IMEM 的修改权限。
3. CPU 取指仍是一拍返回，不增加等待信号。
4. CPU 独立复位不能清空 IMEM，也不能让 IMEM 下载入口停止工作。
5. 下载器和 IMEM 使用现有系统时钟，避免无必要地增加时钟域。

以上约束保持住，CPU 的 Control C1、生产 Datapath 和 `fetch_adapter` 原则上可以不改。

## 4. 最关键的一处：CPU 独立复位

当前 [face_soc_top.sv](../rtl/soc/face_soc_top.sv) 中，CPU、CNN、数据 SRAM、图像桥共用系统 `rst_n`。所以不能靠一直按住全局复位键实现这次需求，否则其他模块也会停。

需要在顶层区分两种复位：

| 名称（示意） | 控制范围 | 什么时候使用 |
|---|---|---|
| `sys_rst_n` | 整个系统 | 外部上电/系统复位 |
| `cpu_rst_n` | 仅 `cpu_core` | 系统复位，或 CPU 程序下载期间 |

下载期间，系统时钟照常运行，`sys_rst_n` 处于释放状态，只有 `cpu_rst_n` 保持有效。CNN、datasram、UART、下载控制逻辑以及 IMEM 写入口均不接这个 CPU 专用复位。

CPU 当前已有 `rst_n` 输入，只需在顶层明确把它接到新的 CPU 专用复位；不能继续让通配接线误接回公共复位。原 `clock_unit` 可以继续提供系统时钟和系统复位，CPU 专用控制可放在下载控制/顶层配套逻辑中。

CPU 内部有同步复位状态，**不能发一个很窄的脉冲后立刻写 IMEM**。下载状态机应等待足够的有效时钟沿，确认 CPU 停止，再给电脑回复“允许下载”；释放也应按系统时钟同步完成，不能从串口输入直接组合生成复位。

当前生产 Datapath 的 `dmem_re/we` 和 `mmio_re/we` 都受其 `rst_n` 门控，取指请求也受复位门控，这是保留现有核心的基础。仍需在改造后的仿真中确认：下载期间这些请求保持为 0。

不能只停 PC 或关闭 `imem_re` 就认为 CPU 已经停住，因为流水线里原先进入的指令仍可能产生写操作。也不建议简单切断时钟，本方案让时钟继续运行，用独立复位清楚地定义停止和启动。

## 5. “不影响其他模块”具体能做到什么

### 5.1 硬件上不连带停止

下载程序只写 IMEM，不写数据 SRAM，不改变 CNN 寄存器，也不触发 CNN 软件复位。

因此，已经收到完整任务并启动的 CNN 可以继续访问 `datasram`、完成计算、保存结果。数据 SRAM 的 RAM 内容、B 侧仲裁和正在返回的 CNN/图像桥读事务都应保留。

**不能为了停止 CPU 而复位 datasram。** 它内部保存着 B 侧在途读的归属和数据，复位可能丢掉其他模块正在等待的响应。本方案中 CPU A 口停止发请求，B 侧继续沿用现有工作方式，不增加外置 SRAM 仲裁器。

停止 CPU 之前已在有效时钟沿完成的写操作不会撤回。“已停止”应指明从哪个时刻开始不再产生新操作，而不能承诺把之前执行的动作回滚。

### 5.2 软件上需要约定交接点

如果 CPU 原程序正在分多次写 CNN 的任务表，写到一半就被停止，CNN 可能看到不完整数据；硬件复位隔离本身不能解决这个问题。

所以正常使用应当在明确的可停机点进入下载，例如：

- CPU 已把本轮任务及数据完整交给 CNN，此后 CNN 可以独立执行；
- 或 CPU 正在约定的空闲等待状态，没有修改其他模块即将使用的数据。

“可停机”不能仅由 PC 没变化推断。第一版可以规定由操作者在已知空闲阶段发起下载；若以后要求任意时刻自动、安全地停止，则要补充 CPU 软件与下载器的握手机制。当前没有现成的“软件已就绪”状态端口，不能直接假定它已经存在。

CPU 停止期间，需要 CPU 才能产生的**新任务、状态处理或后续调度也会暂停**。能够保证的是其他模块不被硬件连带复位，并继续执行它们已经具备条件的工作，不是保证整个应用完全感受不到 CPU 停机。

### 5.3 CPU 重启后，不能把其他模块当成刚上电

CPU 的寄存器和程序入口重新开始了，但 CNN 可能仍然忙，数据 SRAM 里也保留着旧任务和新结果。

新程序应先读取 CNN 状态，并遵守保留数据区的所有权约定。它不能一启动就无条件清空整块 SRAM、复位 CNN，或者覆盖正在使用的图像/权重/结果区。否则即使下载硬件完全隔离，软件仍会影响其他模块。

CPU 新程序的栈、变量及初始化区也应与仍在工作的 CNN 缓冲区分开。普通启动代码对数据区的初始化必须遵守这个布局。

## 6. 图像上传和程序下载怎样共用串口

现有 UART 桥只支持读写数据 SRAM，需要扩展命令以明确区分“程序 IMEM”和“数据 SRAM”。两块存储器默认都从地址 0 开始，因此不能只看地址区分目标。

可以沿用现有 UART 收发器，在桥内部增加命令分发和下载状态机；这样既可保留六个平级大模块的总体结构，也能避免两套发送器同时驱动同一根 TX。

希望图像桥在 CPU 下载期间仍能服务 SRAM 请求，就应按下面的方式组织：

- 每个包注明目标类型，程序包只访问 IMEM，图像/数据包仍走原 `io_mem_*`。
- 下载会话期间允许在完整包的边界插入图像/数据请求，不因等待下一程序块而锁死整个串口桥。
- 所有回复由统一发送控制排队或按顺序发送，不让两个功能同时占用 TX。
- 主机继续遵守“发送一包，等待该包完整回复，再发下一包”的规则；多个上位机任务必须协调同一串口。

**同一串口的带宽要共享。** 程序下载期间，图像传输可以继续被服务，但可用吞吐量和响应时间会受占用影响，不能承诺速度完全不变。如果要求程序下载和图像传输互不占用通信带宽，需要额外独立通信通道，不能只靠共用两根线达到。

程序下载错误应只使本轮程序无效、CPU继续停止，不能自动复位 CNN 或清空 SRAM。现有图像桥发生 SRAM 超时需系统复位的行为属于原有故障边界，不因本方案而被宣称已经消除；扩展状态机时也应检查不同功能的错误隔离。

## 7. 电脑端实际操作流程

以下是拟议流程，命令名称只是说明，不是当前硬件已经支持的命令。

| 步骤 | 电脑做什么 | 硬件做什么 |
|---|---|---|
| 1 | 在允许停机的时刻请求进入下载 | 独立保持 CPU 复位，其他模块保持原状态 |
| 2 | 等待“CPU 已停止”回复 | 确认停止时序完成，才开放 IMEM 下载入口 |
| 3 | 声明程序长度、整体验证信息，分块发送 | 检查包、地址和顺序，再写 IMEM；本轮程序标为未完成 |
| 4 | 请求完成校验 | 确认内容到齐，并核验实际存储内容；不能只检查收包 CRC |
| 5 | 发送启动命令 | 仅在程序有效时接受；关闭下载写入权限 |
| 6 | 等待启动确认 | 确认没有未完成的 IMEM 写入，同步释放 CPU，从 `RESET_PC` 取指 |

可将状态理解为：

```text
运行 → 等CPU停止 → 接收程序 → 核验程序 → 就绪待启动 → 运行
                        └─失败/中断─→ CPU继续停止，允许重新下载
```

每次开始替换程序，应清除本轮“程序有效”标志，检查完整长度和数据顺序，处理重复包/丢包。不能在只收到半个程序时启动，也不能在运行状态下接受写 IMEM。

单份 IMEM 会被新程序逐块覆盖。失败后允许重新下载，但不能直接宣称旧程序还能继续跑；自动回退需要额外保留旧程序的设计。

第一版可选择系统上电/整体复位后先保持 CPU 停止，等待电脑下载并启动；CNN、UART等其他模块按各自正常系统复位流程释放。若需要上电自动执行预装程序，要另外定义预装程序的有效性与启动策略，不能仅凭 RAM 有内容就启动。

## 8. 需要修改的范围

| 部分 | 本方案的变化 |
|---|---|
| IMEM | 新建可写版本；保留原取指接口，增加下载写入和读回校验入口 |
| UART 桥/下载控制 | 扩展程序命令、包分发、整体验证和 CPU 停止/启动控制；保留 SRAM 通路 |
| 顶层 | 替换 IMEM 实例，连接下载入口，给 CPU 单独接复位 |
| CPU 专用复位控制 | 新增同步状态控制；系统复位仍控制全局，下载只控制 CPU |
| CPU Control C1 | 保持现有逻辑 |
| 生产 Datapath / 取指适配 | 保持现有接口和一拍时序，通过已有复位输入重启 |
| CNN RTL、MMIO、原生访存接口 | 保持现有逻辑与接线，不增加下载相关端口 |
| datasram | 保留现有 RAM、仲裁和完成时序，不接 CPU 下载复位 |
| 电脑端工具 | 增加程序格式转换/传输/验证/启动流程，并协调共享串口 |
| 固件及验证 | 明确可停机点、共享数据区和重启接管流程，增加对应测试 |

所以这不是“只给 IMEM 加两根外部线”，而是**给 IMEM 增加受控的下载入口，再让顶层和串口桥配合它**。CPU 的执行逻辑不需要因此重写，CNN 也不需要改成另一套接口。

## 9. 关于“烧录”这个词

这里说的烧录，第一版实际是把机器码下载到 FPGA 内部的可写指令 RAM，不代表已经写入能断电保存的 Flash。

普通 CPU 独立复位不应清除 IMEM；断电或重新配置 FPGA 后，则不能依赖上次下载的 RAM 内容仍然存在。若要求断电保存，需要另行设计非易失存储和启动加载，不属于这次最小改造。

电脑发送的必须是适合本 CPU 的机器码和明确的字节顺序/装载布局，不是直接发送 C 源码。本 CPU 支持的指令范围不因 IMEM 可写而扩大。

## 10. 实现后重点验收什么

下面是后续测试要求，不是本次已经得到的测试结果：

1. 不重新配置 FPGA，经电脑先装程序 A、再装程序 B，CPU 分别执行正确结果。
2. 下载时 CPU 请求全部停止，IMEM 写口正常工作；启动后写口关闭、原取指时序不变。
3. CNN 已经开始的任务跨越 CPU 停机和程序下载阶段，仍能完成并得到正确结果；其复位未被触发。
4. datasram 的 CNN/图像桥在途读不因 CPU 停机而丢失；程序包不会误写 SRAM。
5. 程序包与图像包按规则交替时，地址、响应归属、校验均正确；共享串口的带宽影响单独测量。
6. 错包、漏包、越界、超时和中途断开后不启动半份程序，CNN 不被错误复位，并能重新下载恢复。
7. 新 CPU 程序启动后遵守 CNN 状态及 SRAM 数据所有权，不把仍在使用的数据当作空白区覆盖。

本方案与现有工程接口相容的基础已通过源码核对；在线下载、独立复位和并发保持行为尚需实际实现及上述验证，不能用之前的普通 UART/CPU-CNN 测试代替。
