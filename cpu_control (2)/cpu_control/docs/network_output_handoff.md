# CNN 最终结果交接接口 v0.1

本版新增隔离入口 `rtl/cnn_quant/quant_network_output.sv`。CNN 把最终结果写入 SRAM，发布结果描述；外部读完并确认后，CNN 才允许复用这块缓存。CPU、UART、生产 DATASRAM 的实现仍由各模块负责人对接。本接口不传输图片结果本身。

## 正常流程

1. 配置方写入运算命令、缓冲生命周期，并标记哪些命令产生对外结果。
2. CNN 预约结果槽位，从预约时就禁止提前回收；最终算子完成全部写响应后，发布 `result_valid=1`。
3. 外部观察帧号、地址和字节数，从 SRAM 读取结果。读的过程中保持 `result_ready=0`。
4. **所有读响应都已经返回、数据已存入外部自己的缓存后**，外部拉高 `result_ready`。在 `result_valid && result_ready` 的时钟上升沿完成交接。
5. CNN 解除结果保留。若内部消费者也全部完成，随后产生释放通知，再下一拍槽位可重新预约。外部此后不可继续依赖原地址的内容。

特别注意：这里的 `ready` 表示“已经读完”，不是“准备接收描述符”。不能刚拿到地址就确认，然后再慢慢读。外部若希望使用常规描述符队列，需要自己保留描述符，并把本接口确认延迟到读取结束。

## CNN → 外部的信号

| 信号 | 位宽 | 含义 |
|---|---:|---|
| `result_valid` | 1 | 当前描述有效，对应数据已完成写回；未确认时保持有效 |
| `result_frame` | 32 | 配置方指定的帧号；结果可能按完成顺序出现，不能假定严格按帧号排序 |
| `result_addr` | 32 | SRAM 字节地址 |
| `result_bytes` | 32 | 有效结果字节数，不含槽位尾部保护区 |
| `result_error` | 8 | 当前成功描述为 0；故障结果不发布，错误走全局 `error/cancel` |
| `result_accept` | 1 | 交接成功后的单拍观察脉冲；握手判定以 `valid && ready` 上升沿为准 |
| `compute_done` | 1 | 本批全部计算命令完成，结果可能还没被外部取走 |
| `outputs_pending` | 1 | 存在已预约但未确认的最终结果，包括还在计算的结果 |
| `done` | 1 | 本批计算完成、全部结果已确认、所有缓冲槽已释放 |
| `busy` | 1 | 计算中或仍持有未交接/未释放缓存 |
| `error / cancel` | 各1 | 全局错误/取消。故障时取消未交接结果，不能继续使用旧描述 |

`result_ready` 是唯一新增的外部→CNN 读取确认信号，1 位，同 CNN 时钟域。需要跨时钟时，由系统集成方实现完整握手跨域，不能只独立同步地址和有效位。

`external_hold[7:0]`、`buffer_live[7:0]`、`buffer_release[7:0]`、`wait_buffer` 是调试观察信号。`external_hold` 高表示对应槽不能因内部计算完成而释放。`buffer_release` 是释放条件成立的通知，下一上升沿清除占用；不是结果有效通知。

## 配置方需要提供的内容

沿用 `program_valid && program_ready`，下列信息与同一次命令写入一起采样：

| 新增配置 | 位宽 | 要求 |
|---|---:|---|
| `program_result_valid` | 1 | 本命令是否生成最终对外结果；普通中间命令填 0 |
| `program_result_frame` | 32 | 帧号，建议一批内唯一 |
| `program_result_addr` | 32 | 本命令最终输出的字节地址 |
| `program_result_bytes` | 32 | 非零有效输出长度 |

被标记命令必须预约自己的输出槽，且在其完成时整个结果已有效。当前实现不支持“前一命令预约，后续多个命令继续写，最后一条单独发布”的输出绑定方式；此类图应增加最终复制/后处理命令，或后续扩展独立发布节点。配置编译方负责校验地址/长度处于该输出槽的有效范围，不能把权重区或别的槽标成输出。硬件检查未预约输出、零长度、32 位地址区间溢出，失败通过全局错误停止。

一个槽最多持有一个最终结果，共 8 个槽，当前工作负载的两个工作区只使用其中 2 个最终结果槽。结果选择按槽轮转；描述一旦展示，不会被后来完成的结果替换。单描述接口存在队头等待；不同结果的读取不可在本接口上乱序确认。未展示的结果仍受保留位保护。

## 反压、清除和错误约定

读取方很慢时，已经发布的描述及其数据必须保持；有空闲且依赖满足的其他任务仍可计算。工作区用完则停住等待读取确认，这属于正确反压，不能无限吞入图片。读取方一直不确认时，系统不会自动丢弃结果，也没有自动超时。

`clear`、复位或 `cancel` 会丢弃所有旧批次结果和保留关系。系统必须同步取消/排空外部正在进行的读取，拉低旧的确认，并取消旧 SRAM 写事务后才能开始新批次。本版没有跨复位持久事务编号，不能让旧批次的迟到确认进入新批次。批次错误不会补发失败描述，也不支持仅重试单帧；已确认并复制到外部的结果由外部自行保管。

## 验证范围与复现

使用前一版的六帧小 ROI 数据，两张不同人脸交替；每帧经过真实 NEureka 前三层卷积/后处理和人工残差压力 Add，60 条命令。不是完整 MobileFaceNet，也不是 UART 边输入边计算验证。

`scripts/run_network_output.py --data build/network_buffered_data` 复用已核对哈希的真实 NEureka 编译库，只编译新增控制/包装和测试程序。缓存匹配后加 `--reuse`。两个场景为正常读取、每份描述先等待 90,000 周期再每 7 周期读 4 字节，同时给算子访存加入反压。

测试台从描述地址真实读取每个输出字节，与参考比对；未确认时检查数据不变；释放后立即用 `0xD7` 覆写；确认之后才保存最终输出快照。外部读取采用测试台直接访问 SRAM 模型，没有接 CPU/UART 或实现生产总线读取仲裁，不能据此承诺系统输出带宽。双卷积及后处理均为真实 RTL，测试台不代算。

独立协议测试 `scripts/run_result_handoff_test.py` 覆盖提前 ready、后帧先完成、两个结果同时待交接、描述保持、普通中间缓存释放、逐一确认、clear/cancel、非法配置。原生命周期测试也需回归。数值结果、耗时、波形见 `deliverables/network_output/README.md`。

本步解决最终结果生命周期。下一步仍是完整网络的生命周期规划及小规模验证，再把完整网络接入多算子入口；输入条带、量化准确率和生产 SoC 联调仍单独验收。
