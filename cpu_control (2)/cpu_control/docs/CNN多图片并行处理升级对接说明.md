# CNN 多图片并行处理升级对接说明

日期：2026-10-11  
用途：供 CPU、CNN、存储和图像输入输出合作开发者对齐目标、现状、缺失功能与接口。  
状态：基于当前代码的对接需求与建议方案，**不代表以下新增功能已经实现或接口已经冻结**。本次只形成文档，不修改 RTL。

## 1. 我们为什么做这次升级

最终目标是：外部依次输入多张图片，每张图片在 SoC 内经过一系列预先配置的运算，最后输出指定结果；在数据依赖和存储资源允许的情况下，不同图片、不同阶段、多个算子实例尽可能并行。

示例流程：图片输入 → 卷积 → 激活 → 池化 → 后续特征处理 → 结果输出。

“流程固定但可改变”指：一次运行使用确定的流程，下一批可以通过软件配置不同任务顺序、参数和连接关系。改变流程不等于每次改 RTL；前提是硬件已经具备所需算子。第一版不要求运行中修改正在执行的流程，也不要求动态生成任意任务图。

希望出现的运行状态如下，表格表示一种可能的阶段重叠，不代表每个阶段耗时相同：

| 同一时刻的单元 | 正在处理的内容 |
| --- | --- |
| 图像输入 | 图片 D |
| 卷积 | 图片 C |
| 池化 | 图片 B |
| 结果输出 | 图片 A |

第一阶段优先实现**不同图片之间的阶段重叠**。同一张图片按行或按块边输入边卷积，需要额外的数据就绪粒度、分块和边界处理，作为后续优化，不作为第一版前提。第一版允许整张图片输入确认完成后启动卷积，同时输入下一张图片。

“尽可能并行”不要求所有模块始终忙碌。输入带宽、算子处理速度、SRAM bank 冲突都会形成瓶颈。多个同类实例是否值得增加，应由后续计数和小规模仿真决定。

## 2. 当前代码做到哪里

当前 NEureka 路径以 `rtl/neureka/face_soc_neureka_top.sv` 为 SoC 入口，CNN 实例使用 `rtl/neureka/mobilefacenet_neureka_top.sv`。工程中另有旧版 CNN 和旧演示路径，必须区分，不能把旧版能力直接当成当前 NEureka 路径已启用。

| 部分 | 当前代码状态 | 对本目标的意义 |
| --- | --- | --- |
| CPU 控制 | MMIO 提交队列地址、任务数量并启动，提供批次 busy/done/error | 有软件配置入口，尚无连续提交与逐图片完成协议 |
| 任务描述 | 32 字节；op=11 指向 24 个 NEureka 配置字，op=12 为布局转换 | 有任务格式基础，但需增加或配套提供身份、依赖和存储区域信息 |
| NEureka | 已集成真实卷积核、配置控制与存储桥 | 可保留作为卷积执行单元 |
| 其他算子 | 布局转换，以及 ReLU6、ADD、ReLU、PReLU、池化、重定量对应的执行单元 | 有多阶段处理的基础，不等于完整人脸识别模型已实现 |
| 当前任务控制 | FETCH → ISSUE → EXECUTE → ADVANCE，等待当前任务结束才取下一项 | 当前跨算子任务仍顺序执行 |
| 重叠参数 | `ENABLE_OVERLAP` 在当前 CNN 包装中被声明，但没有参与内部调度逻辑 | 不能以参数为 1 宣称已实现任务重叠 |
| CNN 对 SRAM | 11 路 32 位客户端；0～8 用于 NEureka 宽接口桥，9、10 为共享通道 | 有并发访问基础，但内部部分共享连接依赖串行工作 |
| 旧版调度器 | `streaming_task_scheduler.sv` 有预取窗口、区域冲突判断、执行单元占用和任务编号 | 是可复用资产；当前 NEureka 包装没有实例化它 |

旧版调度器使用固定算子映射和旧阵列上下文，不是已经通用化的任意多实例调度器。旧版 `task_descriptor_info.sv` 也不能直接解析 op=11 的全部卷积数据访问范围。

已有大图验证为 SRAM 预加载下的卷积及后处理；不能作为“UART 连续输入多图、并行处理、连续输出”的整体验收证据。

## 3. 还缺什么，分别由谁推进

下表中的合作人分工是建议职责边界，具体人员由团队安排。**Gemmini（正确拼写，不是 Gemini）依赖管理方向可由项目发起人继续负责，合作人优先推进其他部分，避免双方重复实现调度核心。**

| 编号 | 缺失项 | 要交付的能力 | 建议责任边界 |
| --- | --- | --- | --- |
| A | 任务窗口与依赖管理适配 | 多项任务等待；只派发依赖满足的任务；支持 NEureka 与布局转换；完成后唤醒后继 | 项目发起人继续负责 Gemmini 方向评估、与旧调度器复用整合 |
| B | 多实例分配及统一算子接口 | 按算子类型选择空闲实例，记录正在执行的任务，正确处理同时完成 | 合作人主做，与 A 对齐派发和完成接口 |
| C | 多图片进度和配置管理 | 关联图片、流程版本、任务、阶段及输出；避免不同图片混用配置 | CPU/固件与 CNN 合作开发 |
| D | 缓冲区生命周期管理 | 多组输入/中间/输出缓冲；生产完成才可读；最后消费者结束才可覆盖 | 存储与 CNN 合作开发，第一版可由软件静态分配 |
| E | 并发存储仲裁和响应分发 | 只向获准请求者返回接受信号；记住请求归属；响应只交给对应实例 | CNN 内部接口与 DATASRAM 合作开发 |
| F | 连续任务提交和输入就绪通知 | CNN 忙时能缓存后续工作或明确反压；输入完成后才发布图片可用事件 | CPU、IMAGE_BRIDGE 与 CNN 共同对齐 |
| G | 逐图片完成和结果交付 | 告知 CPU 图片编号、结果位置/长度、状态；定义输出次序和消费确认 | CNN 提供完成事件，CPU/IMAGE_BRIDGE 负责外部交付 |
| H | 错误、复位与可观测性 | 错误停止派发、在途请求处理、状态清理；波形能追踪图片及任务 | 各模块共同实现，集成方验收 |

C、D 不要求全部做成新硬件模块。第一版可以让 CPU 预生成任务描述并分配固定缓冲槽，CNN 只记录有限的在途任务和缓冲状态。最外层继续保持 CPU_CORE、CNN、DATASRAM、IMEM、CLOCK、IMAGE_BRIDGE 六个大模块。

### 3.1 必须先解决的两个存储连接问题

- **通道 9**：目前任务描述读取、NEureka 配置读取和布局 DMA 共用该通道。并行预取或布局转换后，要增加仲裁及响应归属记录，不能继续向所有使用者广播相同 ready/response。
- **通道 10**：目前六类后处理单元共用选择逻辑，多个单元同时请求时，循环中后面的赋值会覆盖前面的请求。必须改为正确仲裁，并只让被选中的单元推进；或重新分配独立客户端。

DATASRAM 的 bank 仲裁不能替代上述 CNN 内部请求归属管理。11 路客户端也不表示每周期必然能完成 11 笔访问。

### 3.2 连续输入不能只靠已有 START

现有 `accelerator_regs.sv` 在忙时锁住队列配置，忙时再次 START 会报错；因此当前接口不是可持续追加任务的提交队列。

第一版可以先采用有限批次：预先放好若干图片对应的任务，另设图片/缓冲就绪状态，输入完成才允许相关任务执行。后续再扩展环形提交队列或带握手的提交接口。即便是有限批次，也必须知道某张图片是否真正输入完成，不能只看到任务描述存在就读取未写完的数据。

UART 串行输入本身不能靠 CNN 的 ready 信号直接暂停。缓冲满时，应由外部协议、请求节奏或信用机制限制下一张图片的发送，具体策略由 IMAGE_BRIDGE 与 CPU 侧确定。

## 4. Gemmini 能借鉴什么、不能替代什么

Gemmini 的 ReservationStation 实现命令等待、已知存储区域的依赖检查、就绪派发及完成后的依赖解除。可借鉴其机制完善 A，但它原版面向加载、计算、写回三类单元，与自身指令和地址格式绑定。

它不会自动补好我们需要的图片编号、同类多实例分配、缓冲分配、SRAM 响应路由或 UART 输入输出协议。

实施时优先检查本工程旧版调度器能复用多少，再决定引入 Gemmini 代码还是借鉴后改写。不要同时维护两个功能重复、状态各自独立的全局任务调度器。

对于 NEureka，op=11 只给出配置表地址并不足以做正确的存储冲突检查。需要二选一或组合：

1. 由 CPU/任务生成器提供准确的读写区域元数据及明确的前驱依赖；
2. 由硬件读取配置后解析实际访问范围。

第一版建议软件生成明确依赖和保守的读写范围，并保证任务描述、配置表和权重在相关任务结束前不被修改。分支流程、共享输入和缓冲复用必须覆盖所有消费者，不能仅按“上一项任务”判断。

## 5. 合作双方应先冻结的接口信息

以下是**语义建议**，不是现有端口名，也未冻结位宽或 MMIO 地址。现有 32 字节描述符不要直接塞入新字段而破坏旧格式；可选扩展元数据表或带版本的新描述符。

| 接口方向 | 必须表达的信息 | 关键约定 |
| --- | --- | --- |
| CPU/任务生成器 → CNN | 提交有效/接受、任务 ID、图片 ID、算子类型、配置位置、前驱依赖或缓冲就绪条件 | 未接受前保持内容稳定；ID 在可能被引用期间不可复用 |
| 输入侧 → 任务管理 | 图片 ID、输入地址/长度、输入成功或失败、可用状态 | 只在约定数据范围写入确认完成后发布就绪 |
| 依赖管理 → 实例分配 | 就绪任务及其参数、接受反馈 | 一项任务只允许被一个实例接受一次 |
| 实例分配 → 算子 | 启动有效/接受、参数、任务身份 | 第一版每实例一次执行一项任务，不抢占；旧 start/busy/done 可外包适配 |
| 算子 → 完成管理 | 完成/错误、任务 ID 或可反查任务的实例 ID | 支持同周期多实例完成；结果写回得到确认后才发布成功 |
| CNN ↔ SRAM | 请求接受、读写地址/数据/字节使能、响应、请求归属和故障处理 | 明确每客户端允许的在途数量；反压时不丢请求、不串响应 |
| CNN → CPU | 图片 ID、结果地址/长度、状态、完成有效/消费确认 | 队列满时不得丢事件；结果在外部消费完之前不能被覆盖 |

建议第一版允许内部乱序完成，外部按图片输入顺序输出；若采用该方式，需在 CPU 软件或完成管理中保存并等待先到图片的结果。也可选择带图片 ID 的乱序输出，双方应先确定，不能默认计算完成顺序就是输入顺序。

流程通过任务及配置数据改变，不把重新开放 IMEM 下载口作为本次升级前提。特征向量、分类分数或最终身份等“指定信息”需要进一步确定模型与输出格式；当前算子集不等于已完成完整人脸识别。

## 6. 开源复用要求

**能找到合适开源实现的，尽量优先找开源，先评估再决定自研。** 优先复用 FIFO、轮询仲裁器、存储接口适配器和已验证算子；同类实例分配这种小规模逻辑，在没有合适现成模块时可以自行实现。

候选模块不能只看项目介绍或论文。交付选型结论时应提供：

- 仓库地址、固定版本或 commit、许可证和所选具体模块；
- 可读源码及所需子模块是否齐全，有无加密或厂商专有依赖；
- 是否有适用于本项目的 RTL 仿真入口，功能模型与逐周期模型要区分；
- 独立小测试的结果、实际编译/运行耗时，以及尚未验证的部分；
- 输入输出接口、要写的适配代码，以及现有代码能否复用。

上述参考项目尚未在本次文档工作中本地编译验收；不要据此承诺移植周期或仿真速度。

## 7. 建议实施和验收顺序

### 第一步：只验证调度和接口

使用一个卷积行为占位单元和两个同类池化占位单元，计数若干周期后完成，不跑真实大图。占位单元仅用于调度测试，不能当作真实算子正确性或性能证据。

至少覆盖：独立任务并发、依赖等待、同类双实例分配、同时完成、存储反压、缓冲不能提前覆盖、完成队列满、非法任务与运行中复位。验证每个任务只执行一次，不能因重复/迟到完成信号误释放其他任务。

### 第二步：接入真实 NEureka 与真实后处理

用三至四张小图，先从 SRAM 预加载开始。必须看到“图片 B 卷积”与“图片 A 后处理”在时间上重叠，并逐图片核对实际输出。不能只看到 busy 同时为 1 就宣称有效计算重叠，要同时检查任务接受、存储事务及结果。

### 第三步：接通连续输入和输出

用 UART 输入若干小图，验证下一张输入与上一张运算重叠、每张图片只输出一次、缓冲满时行为正确。区分 CNN 计算完成与外部结果已经发送完成。

### 第四步：测瓶颈，再扩大规模

记录各实例有效工作和等待周期、输入等待、存储等待、队列占用及完成间隔。确认瓶颈后再增加实例、修改带宽或做图像分块。大图只作为最后验收，避免反复长时间仿真。

每次报告分别给出电脑实际执行耗时和按时钟换算的硬件时间，不将二者混用。
