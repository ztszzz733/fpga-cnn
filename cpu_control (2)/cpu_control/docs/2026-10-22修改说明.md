# FPGA CNN 项目修改说明

**日期：2026 年 10 月 22 日**

**提交分支：`moon`**

**对比基线：`666e9d8`（Add Neureka and Vicuna tiled double-buffer pipeline）**

**本次范围：代码修改、软件调度和功能仿真；暂不进行上板验收。**

## 一、修改目的与范围

本次在已有 Neureka 卷积与 Vicuna 可编程计算、CNN 内部分块双缓冲的基础上，增加连续帧调度，使当前帧计算、下一帧装载以及 CPU 工作能够重叠；同时新增 FX8 并行图像输入入口，为替换 UART 数据传输提供代码实现。

Neureka/Vicuna 接入及 CNN 内部 tile 双缓冲已经存在于上述基线中，**不是今天重新实现的部分**。今天没有重写卷积计算核，也没有采用此前讨论的其他新架构。

## 二、连续帧处理改动

### 1. 图像桥支持 SRAM 描述符

原主动加载桥主要使用固定的源地址、目的地址、长度和 CRC 参数。现在增加可选描述符模式，由 CPU 在 SRAM 中准备任务，再通过原有三线握手触发加载。

描述符默认从 `SRAM_BASE + 0x60` 开始，占五个 32 位字：

| 字段 | 内容 |
|---|---|
| magic | `0x31444c49`，检查描述符有效性 |
| source | 外部存储数据源地址 |
| destination | 本次装载的 SRAM 目的地址 |
| byte_count | 装载字节数 |
| payload_crc32 | 整批载荷 CRC32 |

原固定参数模式保留，描述符模式默认关闭，在 Neureka 连续帧顶层中启用。新增地址范围、长度、溢出、控制区/描述符区重叠、超时及存储错误检查。

### 2. 增加输入/输出帧 A/B 所有权调度

新增 `cnn_frames.h`，管理两套输入帧和输出帧缓冲。主要状态为：

```text
FREE → QUEUED → LOADING → READY → RUNNING → RESULT → FREE
```

只有空闲输入槽可以提交新加载任务；只有校验完成的帧可以提交给 CNN；结果被 CPU 消费并显式释放后，相应槽位才能重用。错误发生时冻结调度所有权，需系统复位恢复。

这里的帧 A/B 缓冲与 CNN 内部卷积、可编程计算之间的 tile A/B 缓冲用途不同，二者同时保留。

### 3. CPU 使用协作式调度

CPU 通过短时轮询推进图像装载、CNN 启动、结果检查和槽位释放，无需在整个计算期间持续等待。新增真实 RV32I C 固件，演示连续四帧处理，并在 CNN 忙时执行数据检查等 CPU 工作。

```text
原固定批次演示：装载一批 → 完成校验 → CNN 计算 → CPU 处理结果

新连续帧流程：
图像桥：装载帧 n+1 → 校验 → 写入空闲输入缓冲
CNN：   使用另一输入缓冲计算帧 n → 写入对应输出缓冲
CPU：   推进调度、检查数据、处理已完成结果、释放缓冲
```

三者可以重叠，但访问同一 SRAM bank 时仍按现有仲裁规则竞争。此修改不等于无限带宽，也不意味着所有周期都能同时完成三个访问。

## 三、FX8 并行图像桥改动

新增独立顶层 `face_soc_neureka_fx8_top`。选择该顶层时启用并行接口，原 UART 顶层继续保留。

| 项目 | 原 UART 图像桥 | 新 FX8 图像桥 |
|---|---|---|
| 外部数据通路 | 串行 RX/TX | 独立 8 位 RX 和 8 位 TX |
| 流控 | UART 字节发送/接收 | 两方向分别使用 valid/ready 握手 |
| 接口时钟 | 波特率分频 | 系统 100 MHz 四分频为 25 MHz |
| 接收与发送缓冲 | 原串行收发逻辑 | RX 512 字节、TX 32 字节跨时钟 FIFO |
| 默认包载荷 | 连续帧回归使用 63 字节 | 最大/默认 256 字节 |
| 写入 SRAM | 每个字节一次写授权 | 拼为对齐 32 位写；首尾不足一字使用字节使能 |
| 协议与校验 | IMIO 请求、IMOR 回复，包/整批 CRC32 | 保留同一协议与校验语义 |
| 错误恢复 | 错误锁存，需复位 | 保留，并清空 FIFO、向对端输出复位 |

对外共有 22 根信号：16 根数据、4 根握手、1 根时钟、1 根低有效复位，另需公共地。理论物理峰值每方向 25 MB/s；这不是实际图像有效吞吐或 CNN 加速测试结果。

包 CRC 通过前不写入该包载荷。整帧 CRC 失败时，已写入空闲缓冲的错误帧不会提交给 CNN。对端停顿时，未被接收的数据与 valid 保持；超时或故障后拒绝迟到数据。

FX8 是连接器上的自定义并行协议。外部控制板或存储控制器需要响应读取命令；裸 Flash、SD 卡或 SDRAM 不能直接当作本协议对端。TX 当前发送读取命令，未新增 CNN 结果自动回传功能。

## 四、六模块接口与保持不变的部分

新并行顶层仍直接实例化六个模块：

1. `clock_unit`
2. `image_bridge_fx8`
3. `cpu_core_autoload`
4. `imem_rom`
5. `datasram_banked`
6. `neureka_pipeline_cnn_top`

FIFO 和协议引擎位于图像桥内部，不增加平级 SoC 模块。CPU 与图像桥的 `load_req / load_complete / load_error`、CPU 本地 `0x40/0x44` 控制/状态、图像桥 `io_mem_*`、CPU/CNN 与 SRAM 的现有接口均保留。

**今天没有修改 CPU Control/Datapath、IMEM、四 bank SRAM 的 RTL，也没有修改 Neureka/Vicuna 算术核及原 tile 调度器。** SRAM 本来支持字节使能，因此 32 位打包在图像桥内完成。变化集中在装载任务来源、CPU 软件调度和新增并行传输入口；板外接口由 UART 两根数据线变为并行信号组。

## 六、验证结果

### 已通过的功能验证

| 回归 | 结果与范围 |
|---|---|
| 连续帧回归 `20261022_165909_947172_neureka_frames` | 4 项 PASS：两种加载/计算时间比例、错误下一帧、描述符故障 |
| 原 UART 自动加载回归 `20261022_165933_472426_autoload_integration` | 6 项 PASS，保留旧入口兼容性 |
| 原 tile 控制回归 `20261022_165933_neureka_pipeline_control` | PASS |
| 最终 FX8 回归 `20261022_182439_335221_fx8` | 6 项 PASS：FIFO、并行桥、描述符、两种四帧运行、坏下一帧 CRC |

最终 FX8 回归使用真实主 CPU、图像桥、SRAM、mailbox 和 tile 调度 RTL，但卷积/PReLU 使用测试模型。每个四帧正常场景比较 **1820 个输出字节，全部一致**；加载 1620 字节，对外读取请求 8 次，图像 SRAM 写授权 408 次。相比逐字节写的 1620 次授权，减少的是写事务数量，不能据此宣称整机加速倍数。

FIFO 验证包含独立时钟、4000 字节传输、指针环绕、满/空、反压和非空复位。并行桥覆盖非对齐写、尾字节、跨包、连续字节突发、SRAM 阻塞、CRC/tag 错误、超时、迟到数据和复位恢复。测试也检查活动 CNN 输入不会被下一帧装载覆盖。

### 尚未通过的验证与本次边界

- 真实 Neureka/Vicuna 曾完成编译和展开，但 XSim 在 `cv32e40x_alignment_buffer.sv:115`、0 ps 出现已有内核崩溃，未取得真实计算核数值 PASS。
- 最终包计数器位宽收窄后的版本通过了功能模型回归，没有重新完成真实核数值验收。
- 板级约束、工程及综合脚本仍是参考草案：最新综合检查在 Gray 寄存器数量断言处失败；此前未布线时序也存在违例。没有生成可交付 bitstream，不能表述为 FPGA 时序或上板通过。
- 按当前要求，本次只交付代码与仿真，不继续开展板级工作。

## 七、复现与交付

在工程 `cpu_control` 目录运行：

```powershell
python scripts/run_neureka_frames.py
python scripts/run_fx8.py
```

真实核尝试入口为 `python scripts/run_fx8.py --real-cores`，需要已有固定版本的第三方依赖，并受上述 XSim 问题影响。使用现有 Vivado XSim 和 RV32I 工具链，相关路径配置见项目脚本。
