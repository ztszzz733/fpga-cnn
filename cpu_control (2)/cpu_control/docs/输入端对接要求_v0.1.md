# 人脸图像输入端对接要求 v0.1

当前能力与首次联调总览见 [CNN当前能力与模块对接说明](CNN当前能力与模块对接说明_v0.1.md)，其中明确区分图片前三层入口与残差中间特征入口。

日期：2026-10-22。对接对象：图像输入/IMAGE_BRIDGE 负责人、CNN 负责人、存储负责人。

后续实现补充（同日）：CNN实验入口已增加第三个INT32临时槽，验证双卷积与后处理同时执行，见 [三槽结果](../deliverables/mobilefacenet_triple/README.md)。以下两槽描述保留为本文编写时基线；输入协议、行就绪和流式接收仍是待对接要求，尚未因三槽改动自动实现。

残差调度开发补充（2026-10-22）：新增隔离残差实验入口，真实MobileFaceNet双输入汇合与多消费者释放的正常、回收覆盖限速、复位重启三项小数据验证已通过；详见 [残差接口与生命周期](mobilefacenet_residual_design.md)。该实验为保留对照数据使用512 KiB模型，不改变本文生产256 KiB基线；新增释放通知尚未接入正式存储分配器、输入桥或CPU。最终验证结果以 [残差实验报告](../deliverables/mobilefacenet_residual/README.md) 为准。

**目的：连续输入多张已裁剪、对齐的人脸；每张图收到一部分后即可计算，最终结果仍与整张预加载一致。** 输入端负责可靠接收与提交数据，CNN 根据行就绪和任务依赖自动派发，输入端不指定使用 NEureka 0 还是 1。

本文的“现有”依据已验证代码；“建议接口/要求”是下一阶段对接草案，**尚未实现，也未作为双方已经确认的端口协议**。同学可据此评审并填写末尾确认表。本轮仅编写文档，不修改 RTL。

## 1. 当前已有与本次缺口

| 项目 | 当前情况 |
|---|---|
| 计算侧 | 两套真实 NEureka、一套量化/激活后处理、两个 INT32 临时槽；按依赖和空闲实例自动派发 |
| 验证范围 | 两张真实人脸的前三层局部区域，全部64输出通道；不是整张112×112的完整硬件推理 |
| 输入来源 | 测试平台提前把图像、权重和参数装入 SRAM，CPU/UART 在这项测试中未接入 |
| 缺少的功能 | 帧接收协议、分批写入、已提交行通知、缓冲反压、坏帧撤销与完成通知 |

第一阶段先让**两张小区域测试图分批输入**并通过数值对照；随后扩到112×112的输入接收测试。收到完整112×112不代表整网计算已实现。

## 2. 图片和数值格式

| 项目 | 建议约定 |
|---|---|
| 模型输入目标 | 112×112，3通道，已经裁剪并对齐的人脸；第一版不做板内人脸检测、裁剪、对齐 |
| 排列 | HWC，按行从上到下、列从左到右、通道 R→G→B；每元素1字节 |
| 长度 | 112×112×3 = **37,632字节/帧**；不含头部、校验、内部边界填充和对齐空间 |
| 压缩 | 不直接接收 JPEG/PNG 文件字节作为张量；发送方先解码 |
| 首版帧顺序 | 帧内不交错、不乱序；按frame_id逐帧输入，允许前一帧仍在计算时接收后一帧 |
| 帧间参数 | 一批图共用同一个已加载模型及量化版本，不能按每张图临时改变尺度 |

### 2.1 必须区分 RGB 字节与 CNN 输入字节

当前真实权重测试的 CNN 输入为 **归一化后量化的 UINT8**，并非相机原始RGB。建议第一阶段由发送侧工具生成该量化张量，输入桥按字节接收和搬运；这样先验证流式控制，不另外增加板内预处理硬件。

当前实验 profile 的计算约定如下（来自现有生成器，不是最终准确率校准结果）：

```text
u = RGB / 255
z[c] = (u[c] - mean[c]) / std[c]
mean = [0.485, 0.456, 0.406]
std  = [0.229, 0.224, 0.225]
q[c] = clip(round_to_even(z[c] / (3/127)) + 128, 0, 255)
```

发送格式建议命名为 `QINPUT_U8_HWC`，由 `profile_id` 固定对应模型、预处理、量化、RGB顺序和尺寸。原始RGB格式 `RAW_RGB888` 如需支持，必须另行指定预处理实现及负责人；**不得仅改格式标签就把原始RGB直接送入上述 CNN 配置**。

图像传输不包含卷积边界 padding。边界由 CNN 输入适配/布局模块按层参数补齐；本 profile 的“实数0”编码为128，不能把 padding 填成字节0。内部13×13小测试块包含边界填充，不是对外图片尺寸。

## 3. 输入端要交付的行为

1. 接收新帧前，确认 CNN/存储侧已提供合法帧槽、地址范围和 profile；槽未释放不得复用。`frame_id` 在仍有旧任务/响应时不得重用。
2. 检查帧头、长度、格式、分包顺序和校验；只把合法载荷写入指定输入区，不能由外部包随意覆盖权重、配置或输出区。
3. 每个字节只接收一次、只计数一次。暂停时保持当前字节及边界标志，直到握手成功。
4. 一行的全部有效字节已校验、所有相关 SRAM 写响应都返回后，发送“行已提交”事件。
5. 支持缓冲不足时反压，以及超时、坏包、短帧、长帧后的帧失效处理。不得把无效帧继续当作正常结果提交。
6. 通知接收完成；只有收到释放通知后，才能覆盖该帧输入区。输入完成、计算完成、槽释放是三件不同的事。

## 4. 建议内部接口（待共同确认，非现有端口）

以下均建议在 SoC 同一时钟域中使用；外部 UART 接收逻辑在桥内完成同步。若采用独立时钟，应由接口方增加可靠 CDC/FIFO，不能直接跨域传脉冲或多位地址。

### 4.1 接收桥 → 输入写入适配模块

| 信号 | 位宽 | 方向 | 含义 |
|---|---:|---|---|
| frame_valid / frame_ready | 各1 | 桥→适配 / 适配→桥 | 帧头握手；成功后才能发送本帧数据 |
| frame_id | 32 | 桥→适配 | 帧标识；执行中的任务和结果必须带同一身份 |
| profile_id | 16 | 桥→适配 | 双方事先登记的模型/数值格式版本 |
| width / height | 各16 | 桥→适配 | 实际有效图片尺寸，小测试模式可与112×112不同 |
| channels / format | 各8 | 桥→适配 | 通道数、格式编号；数值编号另行冻结 |
| payload_bytes | 32 | 桥→适配 | 有效载荷字节数，必须与尺寸和格式一致 |
| data_valid / data_ready | 各1 | 桥→适配 / 适配→桥 | 字节握手，仅两者同时为1时接收一个字节 |
| data | 8 | 桥→适配 | 一个通道值；3次成功握手组成一个RGB像素 |
| data_eol / data_eof | 各1 | 桥→适配 | 与本行/本帧最后一个有效字节同时传输，只在数据握手时生效 |

帧头和数据接口均采用“valid未被ready接受时保持字段不变”的约定。`data_ready=1`本身不表示已经收到数据。EOL/EOF必须与计数相符；正常最后一字节同时带EOL和EOF。

### 4.2 输入写入适配模块 ↔ CNN 行就绪管理

| 信号/事件 | 字段 | 方向 | 生效条件 |
|---|---|---|---|
| row_commit_valid / row_commit_ready | 各1位 | 写入端→CNN / CNN→写入端 | 事件握手，不能是可能丢失的一拍脉冲 |
| row_commit_frame / row_commit_y | 32位 / 16位 | 写入端→CNN | 指定哪一帧的哪一逻辑行已完整提交 |
| frame_rx_done | 携带frame_id及成功状态 | 写入端→CNN/控制端 | 全帧长度和校验通过，最后写响应完成；需可靠握手或可读状态保持 |
| frame_abort | 携带frame_id及错误原因 | 写入端→CNN | 取消该帧有效性；CNN停止派发并按恢复流程处理 |
| frame_release | 携带frame_id | CNN→输入/存储管理 | 该帧全部输入读事务已完成，后续不再使用输入区，可安全重用 |
| row_release（后续阶段） | frame_id、逻辑行号、物理槽号/代次 | CNN→输入缓冲管理 | 所有引用该行的任务及读事务已结束，才允许回收环形槽 |

首版通过帧描述符预先约定输入基址和行跨度，行提交事件不重复携带可任意变化的写地址。环形缓冲的逻辑行到物理地址映射接口后续再定义，不能假设当前 NEureka 已支持地址回绕。

## 5. 收到多少才能开始计算

CNN 负责根据卷积核、步长、padding、输出条带范围计算输入依赖。对于竖直方向，输出行 `oy` 需要输入行：

```text
oy × stride - pad_top ... oy × stride - pad_top + kernel - 1
```

多个输出行需要这些范围的并集；越界部分由内部 padding 提供，不要求外部发送负行号。例如3×3、stride=2、pad_top=1的首个两行输出条带，需要真实输入行0～3和虚拟行-1，不能照搬“第三行第三个数来了就开始”的旧 Sobel 规则。

**这只是数学依赖。** 当前 NEureka 存储桥一次读取36字节且有对齐和内部块访问，实际任务还必须满足配置产生的物理读取范围。CNN适配方要核对实际读地址，准备padding/安全尾部，不能允许读取尚未提交的有效数据。输入方只承诺已提交行，不负责猜测PE何时消费。

## 6. 先连续地址，再循环行缓冲

第一阶段：每个在途帧使用连续输入区，逐行写入、逐行标记就绪。即使预留了整帧空间，也不必等整帧写完才计算；这样能直接复用 NEureka 的线性地址访问方式。

第二阶段：减少占用，增加循环行缓冲。此时必须同时具备逻辑行/物理槽映射、引用计数或等价生命周期管理，以及卷积窗口跨回绕处的处理。可选择将就绪条带复制到连续工作区，或实现经过验证的地址转换；**不能只把写指针取模，而让 NEureka 继续线性读取**。详见 [存储要求](存储端对接要求_v0.1.md)。

## 7. UART/外部传输要求

内部 `data_ready` 不能直接暂停已经在 UART 线上的字节。若沿用仅RX/TX的串口，应采用“分包＋确认/额度”的发送规则：发送端只发送已获接收空间额度的数据包；接收FIFO必须容纳已授权但尚未处理的在途数据。若改用RTS/CTS，须双方明确物理连接及行为。

现有工程 UART 协议不自动等于上述新流式协议。本次不冻结线上包头布局、CRC算法或波特率，输入端负责人需要交付协议说明及发送工具，双方一起确认。建议首版逐包校验后再提交其覆盖的完整行；跨包的一行必须等待全部数据可靠落存。

如果整帧最终校验失败时已开始计算，产生的中间数据只能视为暂存结果，必须禁止对外发布“识别成功”。第一版建议终止该批次、排空/取消事务并重新初始化；帧级隔离恢复需要新增机制，当前调度器只有全局clear。

## 8. 分工与验收

| 负责人 | 需要交付 |
|---|---|
| 输入/桥接同学 | 接收与分包说明、发送工具/仿真驱动、字节握手、长度/校验/超时检查、反压机制 |
| CNN方 | 数值profile与参考张量、任务所需行范围、行就绪判断、禁止早读、实例派发、释放/失效处理 |
| 存储方 | 帧槽地址与容量、写完成语义、并发仲裁、取消语义、后续回绕支持方案 |
| 三方共同 | 接口位宽/时钟、帧身份、格式版本、错误码、内存图、时序示例和测试数据 |

验收至少包含：两张图连续分批输入；输入停顿和存储反压；不足所需行时绝不发射；有条件启动时EOF之前确实开始卷积；帧间不串数据；短帧/长帧/坏包不正常完成；在途帧槽不被提前覆盖；最终输出与同profile的预加载参考逐字节一致。

波形应包含帧ID、data_valid/ready/eol/eof、行提交、输入槽状态、两实例任务启动/忙、后处理写握手、接收完成和计算完成。每根信号每个视图只出现一次，按模块分组着色。
