# CNN 并发与流式输入的存储端对接要求 v0.1

日期：2026-10-22。对接对象：DATASRAM/仲裁负责人、输入桥负责人、CNN负责人。

**目的：让两路卷积、后处理和图片写入安全共享存储，保证未写完的数据不会被计算使用、未读完的数据不会被覆盖。** 多接口只是并行访问的条件，实际吞吐仍由bank数量、冲突和响应延迟决定。

本文分为现有接口事实及下一阶段要求；建议部分是对接草案，尚未实现或共同冻结。本轮只交付文档，不改变生产顶层和地址图。

## 1. 现有验证基线

| 项目 | 已验证实现 |
|---|---|
| 存储模块 | `rtl/overlap/datasram_banked.sv`；独立双NEureka测试入口使用它，不能等同于所有历史SoC入口 |
| 容量/基址 | 本测试256 KiB、字节地址基址0 |
| bank | 4个，按32位字低位交织，每bank每拍最多一个访问 |
| CNN客户端 | 参数CLIENTS=21，各有独立请求接受和响应归属 |
| 另外两个接口 | CPU固定时延访问、图像桥io_mem接口；本次双实例测试均空闲，尚未验证三方同时访问 |
| 仲裁 | CPU合法访问优先占其bank，其余CNN客户端和图像桥按bank轮询 |
| CNN组织 | 两卷积实例＋单后处理＋两个INT32临时槽，各帧各层UINT8特征区保留 |

客户端分配如下，不需要额外增加21个顶层大模块：

| 客户端 | 用途 |
|---|---|
| 0～8 / 9 | NEureka 0九个32位数据请求 / 配置字读取 |
| 10～18 / 19 | NEureka 1九个32位数据请求 / 配置字读取 |
| 20 | 后处理读取参数及INT32结果、写UINT8特征 |

一笔288位NEureka读取拆为九个32位存储请求，收齐后再返回核心；不表示九个像素或九个3×3卷积位置。4个bank不会因为有21个客户端而变成每拍21次访问。

## 2. 现有 CNN 存储端口契约

令客户端数为N（本测试N=21），第i路地址/数据取打包总线 `[i*32 +: 32]`。

| 信号 | 位宽 | 方向 | 语义 |
|---|---:|---|---|
| cnn_valid | N | CNN→存储 | 该路请求有效 |
| cnn_write | N | CNN→存储 | 1写、0读 |
| cnn_byte | N | CNN→存储 | 1单字节访问、0完整32位字访问 |
| cnn_addr / cnn_wdata | 各N×32 | CNN→存储 | 字节地址/写数据 |
| cnn_ready | N | 存储→CNN | 与valid同拍为1时接受一次请求 |
| cnn_response | N | 存储→CNN | 对应路已接受事务完成，**读和写都有响应** |
| cnn_rdata | N×32 | 存储→CNN | 响应数据；写响应数据为0 |
| cnn_cancel | 1 | CNN→存储 | 取消/排空旧事务，防止旧响应进入新批次 |
| cnn_mem_fault | 1 | 存储→CNN | 非法CNN地址/未对齐整字访问触发的全局粘滞错误，当前需复位清除 |

具体规则：

- 当前SRAM模型在请求被接受后的下一周期给出响应，接口没有response_ready，接收方必须能接收返回。新存储如增加延迟，应保持每路响应归属和约定，不得无确认地改成任意乱序；本轮尚未验证长延迟存储。
- 每个现有CNN客户端最多保留一笔未完成事务；九个数据客户端可各自有一笔。不能把整个NEureka宽读取误当成只允许一个32位请求在途。
- valid被反压时，请求地址、方向、访问宽度和写数据保持稳定，直到接受或统一cancel。
- `cnn_byte=0`要求4字节对齐；整字使用低地址存低8位的小端字节布局。字节写只使用wdata低8位，其他字节不能被破坏。
- 当前字节读会把bit7符号扩展到32位；UINT8使用者必须取低8位/显式无符号解释，不能把返回的32位直接当作无符号像素值。
- CNN侧没有逐请求错误返回或byte-enable字段。部分字节写由NEureka桥拆分成单字节写；若改接口需同步适配，不能直接删掉错误语义或把未对齐请求静默对齐。
- 写请求被ready接受并不等于调度依赖可发布；**必须等相应写response完成**。末笔响应前不得发条带完成/行提交/释放槽。

NEureka核心侧要求授权后规定时序返回；现有 `neureka_banked_bridge` 先收齐SRAM事务再给核心授权，以保持核心侧时序。变更外部存储时延应保留这层约束，不能把可变延迟SRAM直接接到核心授权/返回接口。

## 3. 图像桥写入与 CPU 访问

现有图像桥口：请求 `io_mem_req/we/addr[31:0]/wdata[31:0]/be[3:0]`；返回 `io_mem_gnt/rvalid/rdata[31:0]/error`。地址要求整字对齐；读请求be=0，写请求be不能为0。be选择真正更新的字节，禁止为不足4字节的尾包覆盖邻接数据。

**关键差异：当前io_mem口只有读返回rvalid，写入是在成功gnt时直接完成，非法写的error也在接受时报告；它没有CNN式写response。** 输入适配层必须明确这个契约：沿用当前直写SRAM时以`gnt && !error`计为已提交；若换成排队/跨总线/可变时延写入，必须新增写完成通知或可靠的排空屏障，不能继续把gnt当作已经落存。对CNN发布的row_commit一律表示真实写完。

CPU读接口目前为固定时延，没有等待握手。不能直接增加响应周期而不同时修改CPU适配。CPU和CNN若访问同一共享区，也必须服从所有权规则；“CPU优先”不等于可以随意覆盖CNN正在读的数据。

现有CPU优先策略不能保证在CPU无限连续占同一bank时CNN仍有严格等待上限。系统级对接需约定CPU访问配额/阶段限制，或另行设计不破坏CPU接口的公平方案；吞吐测试必须包含输入桥和CPU真实负载。

## 4. 数据区划分与容量

| 区域 | 写入者 | 读取者 | 生命周期 |
|---|---|---|---|
| 模型权重、配置、量化参数 | 初始化加载方 | 卷积/后处理 | 有任务运行时只读，切模型需整批排空 |
| 输入帧区 | 输入适配方 | 一个或多个卷积任务 | 行写完才可消费；最后读事务结束后可释放 |
| INT32临时槽 | 对应卷积实例 | 后处理 | 槽独占，最后后处理写响应返回才释放 |
| UINT8中间特征 | 后处理 | 后继卷积/未来残差分支 | 所有消费者完成前保留 |
| 最终结果区 | 末级计算单元 | CPU/外部输出方 | 结果消费者确认取走后再复用 |

所有地址以字节计，合法范围为`[base, base + size)`。建议各区基址64字节对齐，INT32/配置字至少4字节对齐；对齐、保护区和实际过读范围都计入容量。输入格式参考 [输入要求](输入端对接要求_v0.1.md)。

当前测试的临时槽是`0x38000`、`0x3A000`，各8 KiB；条带配置表从`0x34000`开始。这些是**小测试地址，不能直接当作全网固定内存图**。正式地址表应由统一生成器导出，输入、CNN、CPU使用同一份版本。

256 KiB是否够用不能只看输入图：一张112×112×3需要37,632字节；两张输入加一个56×56×64的UINT8特征图，再加两个8 KiB临时槽，已经是 **292,352字节（285.5 KiB）**，还没算权重、参数、其他层和对齐。因此整网必须选择扩大存储、分阶段加载/复用或条带/行缓冲方案，不能承诺现有容量能完整保存所有图和特征。

## 5. 就绪与释放：谁说了算

**输入行状态：空闲 → 写入中 → 已提交 → 被读取/保留 → 可回收。**

- 输入方负责正确写入并通知提交；CNN方负责计算引用关系和通知释放；存储模块负责访问时序、边界检查和仲裁。裸SRAM不自行猜测“这行以后还用不用”。
- 行写完是最后相关写事务完成，且相应输入数据校验通过。CNN不能仅凭接收字节计数或UART EOF判断SRAM已经可读。
- 释放必须涵盖所有消费者：两个NEureka实例、一个条带的两个通道组、共享halo相邻条带，以及未来残差分支；不能因第一个消费者完成就回收。
- “任务发出最后读请求”还不够；所有该行相关读响应也必须收齐。下一代槽复用时要有frame_id/逻辑行号/代次，避免旧响应或旧提交事件误命中新图。
- 当前调度器只复用INT32槽，尚未实现输入行或全部中间特征的引用计数；本节是新增要求，不是现成功能。

**临时槽状态沿用：FREE → READY → CONV → POST_READY → POST → FREE。** 两个32通道组之间槽仍属于同一条带和卷积实例，不得交给另一个任务。两槽不支持“两路卷积＋一路后处理”同时占用三个独立条带；若要三者并行，需要增加槽及配置寻址能力并重新验证。

## 6. 连续地址与环形缓冲方案

### 阶段A：连续帧区＋行就绪（优先对接）

为有限数量在途帧预留连续输入区，按行写入，CNN在依赖行提交后提前发射。槽满则反压新帧。这个阶段已经能做到边输入边计算，不要求先实现复杂的地址回绕；先用现有小区域数据验收。

### 阶段B：循环行缓冲（减少容量时再增加）

必须先冻结：每槽行跨度、每帧行数容量、逻辑行到物理槽映射、槽代次、释放条件及跨回绕窗口读取方式。当前NEureka的线性/步长地址发生器不能自动把任意环形内存当作连续图片。

可选实施方式：①把所需行/条带复制到连续工作区；②增加并验证读地址转换层；③使用保证每个任务窗口连续的分块布局。三方选定一种后再编码，不能只修改输入写指针。

缓冲大小按最大存活输入范围和实际访存计算，不能简单写成“3×3所以3行足够”。一个两行输出条带、3×3核、stride2本身覆盖5个输入行位置；并行任务和边界/对齐还会增加占用。

NEureka桥按4字节对齐基址进行36字节宽读取，内部块配置还可能访问额外位置。CNN适配方提供并验证每任务实际读取范围；存储方分配合法padding/保护区域。不能仅保留有效像素后让宽读越界，也不能把未来尚未接收的有效像素当成padding使用。保护区大小必须根据实际地址轨迹核对，不在本文拍板固定值。

## 7. 错误、取消及复位

- 地址越界、非法整字对齐、输入包校验失败、超时和所有权冲突都要终止正常完成路径，并记录可定位的原因/帧号/地址。
- 当前CNN存储错误为全局粘滞fault，统一复位恢复；`clear`本身不清除这个存储fault。当前调度器也没有帧级独立取消。
- 统一取消时停止新请求、丢弃/排空旧响应、清除依赖和槽有效标记；已写SRAM不会自动恢复。必须约定清除结束条件后才能重新编程。
- 流式帧最终校验失败时，即使已有中间计算，也不得对外发布有效结果。第一版采用整批中止并重新初始化，局部容错后续单独设计。

## 8. 必测场景与需要交付的文件

| 场景 | 验收标准 |
|---|---|
| 两卷积＋后处理共享存储 | 输出逐字节正确，响应不串客户端，临时槽互斥 |
| 加入输入桥持续写、CPU典型访问 | 不破坏已提交数据；记录各端等待、接受数和完成时间 |
| 同bank热点冲突 | 无丢请求/重复写/响应错路；等待行为符合约定CPU负载下的公平性 |
| 尾包/字节写 | 邻接字节不改变，按小端组装正确 |
| 行写完与计算启动临界点 | 最后写完成之前不允许依赖该行的任务启动 |
| 多消费者/两通道组/halo | 最后消费者和读响应结束前，不覆盖输入或中间结果 |
| 取消与重启 | 不接收旧响应，错误后不虚报done，重新初始化后结果正确 |
| 环形回绕（阶段B） | 窗口跨尾首仍等价连续布局，旧代次事件不能释放新数据 |

请存储方提供：接口时序图、参数化模块、地址/容量表、仲裁与CPU优先说明、字节/整字行为、错误与取消语义、反压测试和带宽计数。CNN方提供任务地址轨迹、访问范围、读写依赖及金标准；输入方提供分包与提交时序。

性能报告至少区分：硬件周期、电脑仿真耗时、各端接受请求数、等待周期、bank冲突、两核计算重叠和后处理写回。先保证正确性，不以“客户端数更多”代替吞吐测量。
