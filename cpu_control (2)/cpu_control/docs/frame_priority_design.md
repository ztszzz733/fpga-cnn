# 按图片提交顺序推进：调度试验

## 目的

用户希望图片依次进入CNN后尽可能并行计算，结果可以错开返回；更关心首张响应和后续输出间隔，不要求十张一起完成。“100ms输出一张”目前是举例，不是已承诺性能。

原十图完整仿真前九张结果直到约2001ms才开始返回，最后一张约2006ms。任务表轮转倾向于让许多图片在相似层附近等待。只提高DW3的类别优先级，不能同时解决后处理等共享算子的排队问题。

## 实现

`stream_dispatch.FRAME_PRIORITY=1`选择新的策略，默认0保留原模式；通过self_stream_top、self_fixed_network_top和self_full_sim_top传入。runner使用`--frame-priority`，与`--dw-priority`互斥，独立编译缓存。

输入完成握手时，为该帧记录递增的提交序号；它不依赖外部frame_id大小或上下文slot编号。每轮扫描全部已加载任务，在依赖完成、图像已提交且tag匹配、目标算子空闲、缓存可以预约的候选中，选择提交顺序最早的图片。选择后再次核验这些条件，再发射并预约缓存；若条件改变则不发射，重新扫描。相同图片候选保持任务表顺序。

正在运行的任务不抢占。较早图片等待K3时，后来的图片仍可使用空闲K1、Post等；较早图片自身依赖尚未就绪或没有可用缓存时，也不会阻止其他可执行任务。算子池保持K3×2、K1×4、DW7/Post/Add/Pad各1，算术和存储接口不变。

这是按扫描时观察到的就绪状态选优。候选刚被扫过后才就绪，需要下一轮；一次选择最多扫描完整任务表再发射，不是零延迟仲裁。完整十图有1310条任务，每轮约1311拍，开销必须计入真实RTL结果。

## 验证与比较口径

1. 控制级用不同slot/tag顺序检查真正按提交次序选择，覆盖依赖、迟到输入、缓存阻塞回退、跨算子并行、不抢占、发射重查、clear和fault恢复。控制级算子仅延迟模型，不是算术验证。
2. 真实算子先运行十图8×8 ROI前三层，分别正常重叠、串行输入、预加载及反压压力；核对每次输出和独立整数参考。
3. 通过同源码/同可执行程序的小门槛后，复用程序运行十张112×112完整MobileFaceNet。使用同一输入、权重、算子数量和输入pace80与上一轮对比。
4. 同时报告首个结果时间、各图片输入提交到结果取走的延迟、相邻结果的九个间隔，以及整批时间；不能把更早出首张等同于吞吐提高，也不能把最后几张集中输出的短间隔称为稳定帧率。

`scripts/analyze_self_ten_scheduling.py`只用旧任务时长做策略筛选，忽略新访存争用及调度开销；其输出不是RTL验证或性能结论。最终结论只依据新完整PASS记录。

## 尚未覆盖的连续运行要求

当前仍是有限十上下文批次；结束后需要clear，不能在结果取走后直接循环复用frame_slot接收第十一张。没有以固定节拍人为扣留结果，也没有入口限速或无限连续帧调度。若要证明稳定每隔某个时间输出，后续需实现上下文循环回收、输入反压和持续多批测试，再观察预热后的平均、最大和分位输出间隔。更均匀的调度不能凭空增加硬件吞吐。

本次仿真使用32MiB SRAM、合成测试图片和诊断量化，不包含CPU/UART、同帧分块输入、识别准确率、512KiB适配或整机上板时序保证。100MHz仅用于周期换算。
