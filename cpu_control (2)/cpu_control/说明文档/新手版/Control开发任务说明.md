# 你负责开发什么，交付什么

原文件是一份实施任务书，描述“应该完成哪些工作”。它不是测试通过报告，也不表示所有目标已经实现。本页把任务整理成便于理解的步骤。

## 你的开发范围

负责 CPU 控制模块、测试代码、简化测试模型、连接说明和 CNN 软件调用示例。正式数据通路和 CNN 硬件属于其他负责人。

控制模块根据当前输入产生控制，不保存另一套隐藏的流水状态；指令和数据的跨阶段保存由数据通路完成。

## 分六步推进

1. 阅读系统规格和架构图，列清接口中缺少的信息。
2. 与对方统一端口、共享信号取值和执行时序。
3. 按指令识别、运算选择、数据依赖、跳转和执行安排拆分代码。
4. 写自动测试，先有独立预期结果，再与实际输出比较。
5. 提供统一运行脚本，生成真实测试日志和波形。
6. 写清使用步骤、验证范围、待确认事项及接入清单。

## 最后应交付哪些东西

| 内容 | 作用 |
|---|---|
| 控制代码和共享定义 | 给对方真正接入工程 |
| 指令与接口说明 | 让双方知道每条指令、每根信号的含义 |
| 自动测试及运行脚本 | 修改后能够重复检查 |
| 连接示例和测试模型 | 在真实数据通路缺席时验证控制行为 |
| 波形与日志 | 保存实际执行证据 |
| 新手教程和未完成清单 | 让其他人能运行，并知道哪些结论尚不能下 |

## 测试必须关注什么

覆盖基础指令、非法编码、结果传递、等待、分支跳转、错误路径取消和复位；同时检查寄存器 0、无效指令及不支持输入。既要有固定例子，也要有可复现的随机输入。

失败要记录具体场景、实际值和预期值；超时、编译失败或要求绘图却绘图失败时，不能报告成功。波形要从本次实际仿真数据生成。

## 对当前项目的理解

上述控制代码和测试已有实现，当前结果见 [测试结果说明](测试结果说明.md)。真实数据通路没有提供时，只能报告控制和测试模型验证，不能用常数补齐缺失反馈来冒充真实联调。

CNN 调用示例只说明先写参数、再启动、再查询的顺序，不能替代 CNN 计算和真实内存访问验证。
