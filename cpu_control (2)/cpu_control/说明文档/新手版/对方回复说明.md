# 对方的回复是什么意思

这份回复来自数据通路负责人。C1 是控制侧接口方案的编号，D1 是对方回复的编号。它们不是软件参数。

## 对方已经原则接受什么

- 控制模块的全部端口及信号取值，双方使用同一份共享定义。
- 控制跟着指令进入下一阶段，反馈信息也来自对应阶段。
- 执行阶段比较和跳转，最新结果优先传递，跳转优先于后续等待。
- 实现约定的 37 条基础指令；不支持的指令先按安全空操作处理。
- 显式处理“同一拍写回又读取同一个寄存器”的情况，让读取方拿到新数据。

“原则接受”表示愿意按这个方案继续开发，并不表示真实代码已经接起来跑通。

## 对方提出的建议

| 建议 | 当前状态 |
|---|---|
| CPU 默认从地址 0 启动 | 等三方最终确认 |
| 指令与数据存储器固定一周期同步读取 | 等真实连接和边沿测试 |
| 第一版访问 CNN 寄存器不额外等待 | 待确认实际时序 |
| 半字地址为 2 的倍数，字地址为 4 的倍数 | 项目已写入第一版使用限制 |
| 统一同步低有效复位 | 双方候选一致，仍需系统顶层统一 |

CNN 张量起始地址继续要求 4 字节对齐。控制模块没有地址异常输入，不能替软件修正不支持的访问。

## CNN 相关分工

CPU 用普通读写指令访问 CNN 寄存器。数据通路把启动和软件复位写入转成一拍脉冲，把 CNN 状态只读返回给 CPU。

CPU 访问 SRAM 的 A 口，CNN 的数据搬运部分访问 B 口。寄存器偏移为 0x00 到 0x20，但完整起始地址还没定。控制模块不增加直接连接 CNN 状态的端口。

## 对方以后计划提供什么

真实数据通路及其内部模块、存储时序说明、逐根端口连接示例、测试命令和日志，以及差异与未验证清单。这是计划交付清单，不是已经收到的文件。

所有保留问题解决后才能更新最终确认状态；接口确认和真实运行验证要分别记录。我们的处理见 [本次对接说明](本次对接说明.md)。
