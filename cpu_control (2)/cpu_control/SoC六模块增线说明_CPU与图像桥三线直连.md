# SoC 六模块增线说明：CPU 与图像桥三线直连

日期：2026-10-08。适用目标：外部设备通过 UART 提供数据，设备上电后由固定固件自动安排加载和 CNN 计算，无需电脑运行时控制。

**本文是增线设计说明，尚未修改 RTL。采用 CPU 与图像桥直接握手的方案，不采用上一份文档的顶层 MMIO 分流方案。旧版实现与说明保留。**

## 1. 画图时怎样改

你的图里继续画原来的六个方框：

1. `clock_unit`
2. `imem_rom`（IMEM）
3. `cpu_core`
4. `image_bridge`
5. `datasram`
6. `mobilefacenet_accelerator_top`（CNN）

**保留原连线，只在 cpu_core 和 image_bridge 之间增加三根单向信号线。** 不增加“顶层选择器”方框，不增加第七个功能模块。

新增部分单独画成这样即可：

```text
              cpu_core                           image_bridge
          ┌──────────────┐                    ┌──────────────────┐
          │              │── load_req ───────→│                  │
          │              │←─ load_complete ──│                  │
          │              │←─ load_error ─────│                  │
          └──────────────┘                    └──────────────────┘
```

如果画成一条总接口箭头，可以标注：

**“加载握手：CPU → 桥 1 位；桥 → CPU 2 位，共 3 位”**。

实际每根线都是单向的，不是同一根线由双方同时驱动。

## 2. 三根新增线逐根说明

| 线组 | 信号名 | 位宽 | 输出模块 → 输入模块 | 含义 |
|---|---|---:|---|---|
| 控制 | `load_req` | 1 | cpu_core → image_bridge | 请求加载一整批约定资料，并保持请求 |
| 状态 | `load_complete` | 1 | image_bridge → cpu_core | 本批次处理已经结束，结果可以读取 |
| 状态 | `load_error` | 1 | image_bridge → cpu_core | complete有效时，0表示成功，1表示失败 |

其中“一整批”是约定的一份加载清单，例如本轮所需图像、权重、参数及任务描述符；不是只收到一个串口包。

**complete 表示结束，不一定成功。** CPU 必须同时检查 error，不能仅看到 complete=1 就启动 CNN。

`load_complete` 和 `load_error` 应保持到 CPU 确认，不做一个周期就消失的脉冲，这样 CPU 用程序轮询也不会轻易漏掉结果。

## 3. 两边新增哪些模块端口

在 cpu_core 的外部端口上拟新增：

```systemverilog
output logic load_req;
input  logic load_complete;
input  logic load_error;
```

在 image_bridge 的外部端口上拟新增：

```systemverilog
input  logic load_req;
output logic load_complete;
output logic load_error;
```

以上只是端口示意，不是已经提交的 RTL。实际声明类型按后续实现统一。

六模块外层的 `face_soc_top` 只需声明这三根内部线，再把双方同名端口一一连接。原 CPU ↔ CNN 的 MMIO 继续直接连接，**不新增 CPU 在 CNN 与图像桥之间选择目标的顶层逻辑**。

clock_unit 继续给两边提供现有 clk/rst_n；三根线与两模块处于同一系统时钟域，不增加独立时钟或复位域。

## 4. 一轮加载怎样握手

采用“请求拉高 → 完成拉高 → 请求拉低 → 完成拉低”的四阶段握手。

| 阶段 | load_req | load_complete | load_error | 含义 |
|---|---:|---:|---:|---|
| 系统复位/空闲 | 0 | 0 | 0 | 没有本轮请求，桥可以准备下一批 |
| CPU提出请求，桥开始加载 | 1 | 0 | 0 | 正在加载或等待外部设备，本轮还没有结果 |
| 成功结束 | 1 | 1 | 0 | 所有必要资料已经成功加载 |
| 失败结束 | 1 | 1 | 1 | 本轮失败，数据不得当作有效输入 |
| CPU确认结果 | 0 | 1 | 保持原值 | CPU已经保存结果并撤销请求，等待桥收尾 |
| 桥清除结果并重新就绪 | 0 | 0 | 0 | 本次握手结束，可以开始下一次 |

具体工作过程：

1. CPU 完成初始化，确认目标缓冲区可写、CNN不再使用这些数据，再通过本地控制寄存器把 load_req 置1。
2. 图像桥在空闲状态接受这次请求，按预置清单通过UART读取资料，写入datasram。
3. 桥在加载期间只处理这一批。load_req持续为1不能造成重复启动。
4. 全部资料到齐、校验通过、最后一笔SRAM写入成功完成后，桥给出 complete=1、error=0。
5. 如果本轮发生协议、校验或访问错误，桥在明确结束/隔离本轮事务后给出 complete=1、error=1，不能把残留事务留到下一批。
6. CPU读取并保存结果，撤销load_req；桥看到请求撤销后清除complete/error。
7. CPU看到complete回到0，确认握手结束。成功后才按原MMIO启动CNN；失败则执行错误处理。

本协议不把提前拉低load_req定义为“安全取消”。CPU不能在加载中随意撤销请求后立刻重启另一批；取消、超时及外部迟到响应需要专门处理。

普通可恢复传输错误可以在协议收尾后允许重新加载；现有SRAM内存超时或CNN存储故障仍可能需要系统复位。不能把error清零理解为底层故障必然已经恢复。

## 5. 为什么三根线就够，以及它的前提

三根线只负责表达“开始、结束、成功或失败”，**不携带图像数据，也不携带每段的地址和长度。**

要只增加这三根线，下列信息必须能由图像桥自己获得：

- 外部读取位置或对象编号；
- 内部SRAM目标地址；
- 每段长度、校验规则和读取顺序；
- 哪些段属于本轮必须加载的资料。

可以把这些信息配置在桥内部的参数/清单中，或由桥按约定读取外部清单并检查合法性。固定固件也必须知道与之匹配的队列和结果地址。

**若要求CPU每一轮都任意指定源位置、目标地址、长度，三根线就不够。** 那时需增加配置数据接口；本稿先按“预先约定完整加载计划”的简单版本说明，不暗中把地址数据塞进一位请求线。

单批加载期间，默认不与CNN对同一数据区域并发操作。CPU负责业务阶段安排，三根线自身不提供CNN访问区域的硬件锁。

## 6. CPU 怎样发请求、怎样知道结果

CPU不能仅因为端口上接入了complete/error，就自动改变软件流程。还需要在 **cpu_core封装内部**增加供固定固件访问的本地控制/状态寄存器。

```text
cpu_core 内部

原 cpu_control + cpu_datapath
            │ 普通读写指令
            ▼
新增本地加载控制/状态寄存器
            ├─ 保存请求位 ───→ load_req
            └─ 读取结果位 ←── load_complete / load_error
```

建议的软件动作是：

- 写本地请求位，拉高load_req；
- 读本地状态，等待load_complete，并检查load_error；
- 保存本轮结果后清请求位，等待桥清除complete；
- 成功后执行原CNN配置和启动程序。

这需要设计本地寄存器地址、读写译码和返回路径。**地址判断和读回选择在CPU封装内部仍然需要存在**，只是六模块之间改成直接握手，图中不再增加公共MMIO选择节点。

本地寄存器访问不能同时被转发成一次SRAM写入或CNN寄存器写入，也不能破坏原Datapath所依赖的读返回时序。现有CPU还没有这组本地寄存器，具体集成方式和地址应在实现前确定。

Control C1不增加load_req/complete/error端口，不新增CPU指令。原执行流水线可以继续使用，但必须补CPU封装内的状态访问逻辑和固件，不能承诺只增加模块端口就能运行。

## 7. image_bridge 内部需要补什么

图像桥保持原有UART和SRAM连接，在内部增加自动批次加载状态机：

```text
等待load_req
    ↓
与外部UART设备确认就绪，按其协议请求数据
    ↓
接收、校验、分块写入SRAM
    ↓
继续加载清单中的下一段
    ↓
整批成功或明确失败 → 保持complete/error
    ↓
等待CPU撤销load_req → 清状态 → 回到空闲
```

若外部设备主动推送数据，则用双方支持的接收授权/分块确认机制协调；不能只因为兼容UART，就认为其应用协议与旧IMIO相同。

UART接收到最后一个字节、最后一个包CRC正确，都不能单独作为complete条件，还必须确认所有必要段有效且SRAM最后一次访问完成。

桥内部需要计数、校验、缓冲、超时以及回复/请求发送管理。该状态机仍属于image_bridge，不增加第七个平级模块。

加载失败可能已经改写一部分SRAM，因此CPU应拒绝使用本轮输入，而不是把error当作“内存完全没有变化”。

## 8. 六模块完整连线清单：原五组保留，新增第六组

| 编号 | 两端模块 | 线组 | 请求 / 返回位宽 | 变化 |
|---|---|---|---|---|
| ① | CPU ↔ IMEM | imem_addr、imem_re、imem_rdata | 33 / 32 | 保留固定一拍取指 |
| ② | CPU ↔ datasram | dmem_addr/wdata/re/we/wstrb、dmem_rdata | 70 / 32 | 保留数据A口 |
| ③ | CPU ↔ CNN | mmio_addr/wdata/re/we、mmio_rdata/ready | 66 / 33 | 保留直接MMIO连接，不经新顶层分流 |
| ④ | CNN ↔ datasram | mem_addr/wdata/read/write、mem_rdata/ready | 66 / 33 | 保留CNN原生访存 |
| ⑤ | image_bridge ↔ datasram | io_mem_addr/wdata/req/we/be、io_mem_rdata/gnt/rvalid/error | 70 / 35 | 保留error及原B侧完成语义 |
| **⑥** | **CPU ↔ image_bridge** | **load_req、load_complete、load_error** | **1 / 2** | **新增三根握手线** |

时钟复位仍画公共线：clock_unit向其余五个模块提供clk/rst_n，不重复计入上述每组接口。

SRAM B侧的选择和返回归属仍在datasram内部，不增加独立仲裁器。IMEM仍只保存固定程序，UART不写IMEM。

## 9. 外部引脚有没有增加

没有因这三根握手线而增加外部引脚，它们全部在FPGA内部。

| 原顶层引脚 | 位宽 | 用途 |
|---|---:|---|
| sys_clk | 1输入 | 系统时钟 |
| rst_n_in | 1输入 | 系统复位 |
| uart_rx | 1输入 | 接外部UART数据设备TX |
| uart_tx | 1输出 | 接外部UART数据设备RX |
| led_ready | 1输出 | 桥就绪状态，自动模式含义需明确 |
| led_busy | 1输出 | 桥加载/通信忙，不是CNN busy |
| led_error | 1输出 | 桥或CNN存储故障 |

仍为3输入、4输出，共7根数字IO；不包含电源、地及JTAG等专用连接。前提是外部设备可以只用TX/RX完成必要的通信和流量协调，不强制额外握手引脚。

## 10. 实现范围与后续验收

| 部分 | 后续需要做的事 |
|---|---|
| cpu_core集成封装 | 新增1输出、2输入；实现本地控制/状态访问与请求保持 |
| image_bridge集成版本 | 新增1输入、2输出；实现整批自动加载和四阶段握手 |
| face_soc_top接线 | 三根信号点对点直连；不增加顶层MMIO选择节点 |
| 固定固件 | 上电初始化、发加载请求、检查结果、按原接口启动CNN |
| IMEM | 接口保持，提供正确的固定程序初始化内容 |
| CNN、datasram、clock_unit | 原接口和主要职责保持，结合新流程做回归 |

重点验证：持续请求只加载一次；CPU轮询不会漏完成；复位后三线状态正确；错误不启动CNN；必须经历请求/完成清零后才能开启下一批；完成不早于最后一次SRAM提交；本地寄存器访问不误写其他目标；UART超时和迟到数据不会串到下一批。

原始伙伴源码、旧RTL和旧接线文档均保留。新增信号、CPU本地寄存器和桥内状态机都还需要实际实现、编译和验证；本文不宣称三线方案已运行通过。
