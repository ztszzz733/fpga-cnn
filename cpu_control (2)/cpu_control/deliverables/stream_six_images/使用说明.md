# 六张图片的 UART 流式特征提取仿真

本版实现了同一张图片内的边接收边计算。UART 输入 6 张不同的 524×524 灰度测试图，每个像素 8 位；CNN 产生两路方向梯度特征并写入 DATASRAM。输入包不包含任务描述符或权重。

## 固定计算流程

输入按行从左到右、从上到下发送，像素是无符号 0～255，不是 JPEG 或 PNG 文件的压缩字节。PNG/PGM 仅用于展示和生成外部设备模型的像素数据。

两路卷积使用固定 Sobel 核：

```text
水平梯度 Gx             垂直梯度 Gy
-1   0   1              -1  -2  -1
-2   0   2               0   0   0
-1   0   1               1   2   1
```

每路随后做 abs(G)/4，整数向下取整，再进行 2×2 最大池化，步长为 2。卷积无边界填充，524×524 变成 522×522；池化后每路为 261×261。它们分别表示沿 x、y 方向的亮度变化，常用于提取边缘与纹理。

这是固定卷积特征提取链，没有训练权重，也不表示已经实现人脸识别。新入口是 face_soc_stream_top，CNN 为专用流式实现，固定系数用加减和移位实现；它没有调用旧版通用 8×8 脉动阵列。旧 face_soc_overlap_top 和 19 任务演示完整保留，不能直接把两种不同计算负载的耗时当成加速比。

## 六个大模块如何协作

CPU 从 IMEM 执行固定程序，先设置 CNN 输出起址并启动 CNN，然后通过 load_req 请求六帧像素。CNN 此时已经就绪，等的是像素流，不再等待整张图片的 load_complete。

IMAGE_BRIDGE 使用两个包缓冲。一个接收 IMOR 回复并验证包 CRC，另一个通过 pixel_valid/pixel_ready 向 CNN 发送已校验像素。当前每包最多 1024 字节；每帧 269 包，最后一包 144 字节，共 1614 包。每个回复的地址、长度和 tag 都要与请求匹配。UART 仍保留 IMIO 请求、IMOR 回复及每包 CRC32，25 Mbps、8N1。

CNN 内部保存两行历史像素、滑动窗口和池化上一行的数据。第一个有效卷积窗口所需像素齐全后立即计算；包校验会增加少量启动等待。没有整帧输入缓冲，也不把整幅原图写入 DATASRAM。结果写回期间通过 ready 反压像素流；两个包缓冲都占用时，桥不再请求下一包。

DATASRAM 沿用四存储体实现，本版容量为 1 MiB。CNN 的通道 0 和 1 分别写入水平、垂直特征，保留 11 路总线形式，其余通道不使用。两个相邻特征字节可能命中同一存储体，会由仲裁器顺序接受。所有实际输出数据都通过正常 SRAM 写接口提交，测试平台没有向 DUT 内存灌入图片或结果。

## SRAM 结果怎么存

每帧 261×261×2 = 136242 字节，6 帧总计 817452 字节，全部同时保留在 SRAM 中。输出基址是 0x1000。

```text
frame_base = 0x1000 + frame_id × 136242
address    = frame_base + (y × 261 + x) × 2 + channel
channel 0  = 水平梯度特征
channel 1  = 垂直梯度特征
```

frame_id 从 0 到 5，x 和 y 从 0 到 260。actual.bin 是从本次仿真实际 SRAM 读出的完整结果，按以上排列；feature_01_x.png 等输出图片从 actual.bin 生成，不是参考计算图。

CPU 使用 MMIO 的 OUTPUT_BASE（0x40000008）设置起址，向 CONTROL（0x40000000）写 1 启动。STATUS（+0x04）的 bit0/1/2 分别为 busy/done/error；+0x0C 返回完成帧数，+0x10 返回累计消费像素数。+0x14 是每帧输出字节数，+0x18 是高16位高度/低16位宽度，+0x1C 是固定帧数。CONTROL bit1 可取消 CNN，但不会回滚已写入的结果；流协议故障恢复需硬复位。

全部计算完成后，CPU 逐个读取 16 位特征对，计算累加校验和写入 0x80，完成标志写入 0x88。0x600D 表示固件正常结束，0xDEAD0001 表示检测到错误。CPU 固件不预存图片内容或期望特征；测试平台用独立参考结果核对 CPU 校验和和全部输出字节。

## 波形怎么判断确实重叠

先看 pixel_frame 和 frames_done：前者表示桥当前提供像素的帧号，后者表示 CNN 已完成帧数，最终为 6。frame_done 是逐帧完成脉冲，cnn_status_done 是整批完成脉冲。

在接口细节视图中看 IMAGE_BRIDGE 的 rx_receiving 和 CNN 的 compute_fire。rx_receiving 高表示桥正在接收回复，compute_fire 高表示上一拍实际处理了一个卷积窗口。再看 uart_rx 的变化、pixel_valid/pixel_ready 的握手和 cnn_valid/cnn_ready 的写回接受。

rx_receiving 也包括包头和 CRC，不能单凭它就把所有周期都算成接收图片像素；报告中的 591408 个重叠周期额外要求外部设备模型确实处在发送像素的阶段。CNN 的 WORK/busy 包含等待像素的时间，不能将它们当成每拍计算。

状态仍为 RESET=0、IDLE=1、WORK=2、FAULT=3。正常结束后 CPU 仍可能循环取指，所以 CPU 和 IMEM 仍显示 WORK。当前 led_busy 表示桥或 CNN 任一忙，与旧演示只表示桥忙的定义不同。

## 错误和反压检查

CRC 错误和超时定向测试分别在第 3 包注入故障。前两包可以已经计算并留下部分结果，但坏包不会发布给 CNN，最终 done 不会置为成功，CPU 报告失败；硬复位清除观察状态和故障位。部分 SRAM 内容不会自动回滚，因此失败批次不能作为有效输出使用。本版采用逐包 CRC 和严格地址/长度/序号检查，没有额外整帧 CRC。

另一个定向测试先阻塞消费者，填满两个包槽，确认请求停止在第 2 包；恢复并周期性节流后，12 包、768 个像素及所有帧首帧尾标记仍按顺序通过。

## 复现与工程入口

```powershell
# 完整六帧，默认 524×524、GRAY8、每包 1024 字节
.\scripts\run_stream_sim.ps1 -Waves

# 快速六帧预验证
.\scripts\run_stream_sim.ps1 -Width 64 -Height 64 -Waves

# 小图的 CRC 错误和接收超时
.\scripts\run_stream_sim.ps1 -Width 32 -Height 24 -Chunk 128 -Fault 1
.\scripts\run_stream_sim.ps1 -Width 32 -Height 24 -Chunk 128 -Fault 2
```
