# 两张完整人脸并行：缓存计划与控制验证

## 本轮状态

两张不同的 112×112 RGB 人脸分别经过同一个完整 MobileFaceNet，目标是各输出一个 128 维量化特征。输入采用 SRAM 预加载，两张图的任务一起可用，由 CNN 根据依赖和算子空闲状态发射。每张图内部仍逐层执行，两图之间可以并行。本轮没有连接 UART，也没有要求外部同一拍传两个像素。

已完成完整网络的存储计划及真实调度控制 RTL 验证。**尚未执行这套新地址布局下的完整两图数值仿真。** 控制测试中的卷积等算子使用延迟模型，不能据此宣布特征计算正确、推断性能或给出真实网络硬件耗时。

## 数据与任务

- 图片：`D:/code/facemodel/person_1.jpg`、`person_2.jpg`，内容哈希不同。
- 每张图：51 个卷积、12 个 Add，包含补边、分组卷积及后处理的 373 条底层命令；两张共 746 条。
- 两张图沿用第一张图诊断生成的同一套逐层量化尺度，第二张图没有单独重新选择尺度。仍不是独立数据集校准，不能宣称识别准确率。
- 第一张图的旧顺序入口曾完整数值 PASS；第二张图本轮只生成了软件整数参考。
- 新布局的中间缓存初始值全部为 `0xA5`；参考输出保存在独立 `expected.bin`，不能加载进模拟 SRAM。

计划数据在 `build/mobilefacenet_pair_plan`。`jobs.bin` 采用 16 个32位字/命令；`leases.bin` 为156字节/命令；新增 `results.bin` 为16字节/命令，依次是发布标志、帧号、结果地址、有效字节数。只有节点744、745发布结果，分别128字节。后续数值测试台必须读取这些元数据，不能套用上一版六帧ROI测试里“每10条命令一帧、每帧1024字节”的写死规则。

## 存储计划

根据实际算子读写地址分析生命周期，包括所有卷积通道分组写入和残差 Add 的两个输入。首次写入命令预约输出槽；后续分组写入必须检查相同生产者代号；最后一个读者/写者完成后才能释放。最终输出还要等待外部读完确认。

两组互相独立的工作区，各保留4个槽位编号，本网络实际用3个，另一个为64字节占位。每组槽容量依次为：

| 槽 | 含尾保护区的容量 |
|---|---:|
| 0 / 4 | 1,605,696 字节 |
| 1 / 5 | 802,880 字节 |
| 2 / 6 | 401,472 字节 |
| 3 / 7 | 64 字节（未使用） |

中间工作池共 **5,620,224 字节，约5.36 MiB**。每张图最多同时保留3个中间张量，两张图共262次预约。容量根据各槽曾容纳的最大完整张量确定，包含64字节宽读取尾保护；这只是当前合法规划，不是最小容量证明。

若把两图所有中间张量都保留下来，逻辑负载合计38,674,584字节。新布局另外有2,752,512字节只读区域，整个实验地址空间8,372,736字节，约7.99 MiB；只读区域目前保留两份权重/参数、输入、对齐间隙和历史描述表副本，没有做权重共享。硬件命令表和生命周期控制表不包含在这个 SRAM 容量里。

生产存储器没有扩容。本方案仍是完整层张量读写 SRAM；要进一步降低容量与带宽，需要后续条带/分块和局部数据复用，不能用这次计划宣称已实现层间直通流水。

## 已完成的验证

1. 静态校验：全部746条命令的槽位归属、生产者代号、消费者保留位、依赖顺序和带保护区的输出范围通过；覆盖 Conv、Post、Add、DW7、Pad。
2. 控制 RTL：实际 `network_dispatch_buffered`、`network_buffer_leases`、`network_result_handoff`，算子使用不等时延模型；先执行部分命令、clear后重新装表，再完整运行。
3. 完整运行检查：746命令完成、262次分配/262次释放、两份结果先保留再确认；所有释放都检查声明的读者和写者已完成。
4. 双卷积实例各收到292条命令，后处理126条、DW7两条、补边34条；存在双实例重叠。上述分配是控制模型结果，不能当作真实计算负载均衡结论。

控制测试编译8.638秒，运行0.269秒，总8.908秒。无长时间仿真或定时检查在运行。控制测试日志中的模拟时间取决于人为延迟，不是完整网络实际耗时。
