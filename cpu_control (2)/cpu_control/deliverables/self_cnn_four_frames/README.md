# 四图固定流程并行 / 流水验证

已经实现：CNN 接收一份固定流程和图片地址表，自主展开任务、处理层间依赖、分配算子。默认 **3×3 四套、1×1 两套，DW7 / Post / Add / Pad 各一套**。真实接入 bai-datasram 的四 bank、256 KiB SRAM；没有 NEureka 运行依赖。

四图重叠执行 **83,201 拍**；同配置逐张算完再输入下一张 **276,229 拍**，整批吞吐加速 **3.320×**。相对两套 K3、一套 K1 的重叠基线，周期减少 **36.86%**。串行对照包含每张相同输入传输和读结果成本，因此这是批次端到端对照，不能当作单层 MAC 加速比。

这轮为四张不同 7×7 RGB、诊断权重、每图 11 步短流程。所有算子都是实际 RTL。不是完整 MobileFaceNet、识别准确率或上板验收；完整综合的旧 Post / DW7 RAM 推断问题尚待解决。

## 确实发生的重叠

- 最多 4 张图同时有在途任务；跨图片的实际 MAC / 接受写回同拍发生 19,642 拍。
- 多套 K3 同拍 MAC 共 14,528 拍，峰值 3 套；配置了四套不代表每拍四套都在 MAC。
- 不同种类算子实际工作同拍 4,604 拍，体现跨图阶段流水。
- 后续图片输入期间，已有图片实际 MAC 4,645 拍；IO 写接受与算子工作同拍 60 拍。
- busy 含等待：多图在途 73,930 拍，不把它计作实际运算次数。

每个场景检查 44 个硬件展开命令、28,812 个中间/最终字节、44 次槽分配和释放、四份真实 IO 读取的最终结果，以及输入/只读保护、槽尾保护、请求反压稳定、写响应排空后完成、慢读期间结果保持。结果总计 32 字节，SHA256：`d961e0eb6f303e1f4e49a9792e92778ba2d4f5b4ee6600976d3417ee6f9d08f0`。

预期中间值只在 checker 中；初始工作区和流式输入区为 A5。流式场景图像通过实际 SRAM IO 写入，preloaded 场景经 CPU A 口预装。CPU A 口初始化与背景访问是真实端口请求；压力场景制造同字 CPU 读碰撞，不能将其描述成完整 CPU 指令执行。清除场景在第二张图片部分写入、计算有未完成访问时取消并重启；内存故障场景使用全局复位恢复 bai 的锁存 fault。

独立地址展开控制测试还覆盖 1、2、3、4 张图、配置反压，以及四类非法配置。1～3 张的这项测试是控制验证，四张才是本轮完整短流程算术回归。
