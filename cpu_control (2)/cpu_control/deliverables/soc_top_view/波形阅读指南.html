六模块 SoC 波形阅读指南

适用版本：face_soc_overlap_top　｜　整理日期：2026 年 10 月 10 日

这份指南配合本目录的 GTKWave 波形使用。建议先看六个模块的状态，再跟踪一笔数据从请求到完成的过程，最后检查 CNN 多通道访存。第一次阅读按第 1 至第 5 部分操作即可；每根线的完整定义见同目录《信号与状态说明.md》。

1 先打开正确的波形

在 deliverables/soc_top_view 文件夹中双击下列入口。启动文件会一起加载波形、颜色、分组和状态文字；只打开 VCD 或 FST 不会自动得到这些显示设置。

入口文件什么时候用
open_module_states.cmd第一次看，先了解六模块的完整工作过程
open_all_modules.cmd看接口细节，默认定位在 CNN 运行附近
open_power_on.cmd从上电复位开始看，初始窗口较小，需缩小查看全程
open_fault_reset.cmd看单独的 UART 超时与硬复位恢复用例

GTKWave 窗口怎么读

左侧信号列表显示名称以及时间光标处的值；右侧是随时间变化的轨迹。先在波形区单击放置时间光标，再对齐查看同一时刻的请求、地址、数据和响应。上下滚动查看其他模块，左右滚动查看其他时间段。

用工具栏的放大、缩小和全程缩放按钮调节时间范围。先找到目标事件，再放大到几十或几百 ns 查看总线；看 UART 字节可放大到几百 ns 至几 μs。信号名称截断时，把信号列表和波形之间的分隔线向右拖。

地址和数据通常用十六进制阅读；cnn_valid、cnn_ready、cnn_response、soc_active、soc_fault 改用二进制更容易看清每一位。选择信号后在 Data Format 菜单中选择 Hex 或 Binary。状态保留 RESET、IDLE、WORK、FAULT 的文字显示。

时间单位与颜色

时钟是 100 MHz，即一拍 10 ns。1 μs = 1000 ns；1 ms = 1000 μs。VCD 的记录单位是 ps，GTKWave 显示时可能换算单位：3781925000 ps = 3781925 ns = 3.781925 ms。

模块波形颜色优先关注
CPU CORE蓝色取指、load_req、CNN MMIO 配置
CNN红色busy、done、多通道访存请求
DATASRAM黄色就绪、响应、返回数据、故障
IMEM靛蓝指令返回 imem_rdata
IMAGE_BRIDGE紫色UART 发包、加载完成、写 SRAM
CLOCK橙色内部时钟与复位释放

完整视图有 61 根信号，每个信号名只列一次。共享连线归入输出端模块，例如 cnn_valid 在 CNN 组，cnn_ready 在 DATASRAM 组。TOP STATES 是状态观察区；EXTERNAL INPUTS 和 TOP OUTPUTS 是外部引脚观察区，它们不是新增硬件模块。图中合并标注的多根线在波形中分别显示。

2 先用状态看懂整段流程

打开 open_module_states.cmd，从左到右看六路状态。它们是并行的观察状态机，可以同时处于 WORK，并不是系统一次只允许一个模块工作。

显示文字原始值怎么理解
RESET0正在复位
IDLE1没有监测到活动；CLOCK 表示等待内部复位释放
WORK2有活动或事务在途；CLOCK 表示内部复位已释放
FAULT3监测到了该模块支持检测的故障

正常流程为：复位释放 → CPU 请求加载 → 桥通过 UART 获取资料并写入 SRAM → CPU 配置 CNN → CNN 执行 19 个任务 → CPU 读回校验并写完成标志。

事件当前正常波形中的时间要看什么
请求加载225 nsload_req 拉高，随后 bridge_busy 有效
加载结束3781675 nsload_complete=1，同时 load_error=0
CNN 开始忙3781925 nscnn_status_busy 拉高
CNN 队列完成3818035 nscnn_status_done 出现完成脉冲
波形记录结束4002570 ns此前 CPU 继续执行结果校验

以上是已交付正常波形的定位点，换任务或参数重新仿真后可能改变。计算区间只有约 36.1 μs，在约 4 ms 的全程图里显得很窄；默认的 all_modules 入口已经定位到这一带。

这些状态不能这样解读

CPU 轮询状态寄存器或执行末尾自跳转时仍然取指，cpu_state 和 imem_state 仍可能保持 WORK。cnn_state=WORK 包括调度、等待存储器和收尾，不能直接换算为乘加利用率。sram_state=WORK 也可能包含尚未获准的请求。

状态在时钟上升沿采样后更新。比较状态和接口时，要查看该边沿之前用于采样的接口值，不能要求状态与边沿后变化的组合信号瞬时一致。CPU、IMEM 和 CLOCK 当前没有独立故障检测源，因此它们没有 FAULT 也不能证明内部所有情况都正常。

总览位图怎么读

soc_active 和 soc_fault 的 bit0 至 bit5 依次对应 CPU、CNN、DATASRAM、IMEM、IMAGE_BRIDGE、CLOCK；二进制显示时 bit0 在最右边。soc_active 的某位为 1 表示对应状态是 WORK。soc_fault 的某位为 1 表示对应状态是 FAULT。

soc_module_state 每两位表示一个模块，依次为 [1:0] CPU、[3:2] CNN、[5:4] SRAM、[7:6] IMEM、[9:8] BRIDGE、[11:10] CLOCK。初学时直接看六路文字状态更方便。

3 跟踪 UART 加载和 CPU 启动 CNN

先看三线加载握手

1. CPU 将 load_req 拉高，表示请求加载一批资料。

2. IMAGE_BRIDGE 工作期间 bridge_busy=1，UART 有请求和回复。

3. 桥将 load_complete 拉高，CPU 同时检查 load_error。只有 load_error=0 才表示加载成功。

4. CPU 撤销 load_req，桥再撤销 load_complete，完成这轮四阶段握手。

load_complete 表示加载流程结束，成功和失败都会结束。不要只看到它变成 1 就认定成功。

UART 为什么是一串密集脉冲

uart_tx 是 SoC 发给外部设备的请求，uart_rx 是外部设备送回 SoC 的数据。当前仿真为 25 Mbps、8N1，每位 40 ns，一个字节包含 1 个起始位、8 个数据位和 1 个停止位，连续发送至少需要 400 ns。空闲为高，起始位为低，8 位数据低位先发，最后停止位为高。

8 KB 资料分为 32 个 256 字节的数据包，还包含协议头、CRC、处理和握手时间。因此全程上 UART 看起来很密集并且持续很久，这是串行传输的正常表现。要读具体字节，应放大到约 400 ns 的尺度。25 Mbps 是本次仿真配置。

确认接收的数据真的写入 SRAM

同时查看 IMAGE_BRIDGE 组的 io_mem_req、io_mem_we、io_mem_addr、io_mem_wdata、io_mem_be，以及 DATASRAM 组的 io_mem_gnt、io_mem_error。

在一个 clk 上升沿之前，req=1 且 gnt=1 表示接受这笔访问；若同时 we=1，就是写入。该边沿处 error=0 才是正常写入。be 的 bit0 至 bit3 分别选择 wdata 的第 0 至第 3 个字节。若 req=1 而 gnt=0，表示还在等待，不能把每个等待周期都算成新写入。

当前加载主要进行写操作，写完成看 gnt，不需要等待 io_mem_rvalid。rvalid 是桥的读操作返回有效信号，不能因为它一直为 0 就认定 UART 没有写入。

CPU 如何启动 CNN

加载成功后看 cnn_mmio_addr、cnn_mmio_wdata、cnn_mmio_we 和 cnn_mmio_ready。写使能和 ready 在上升沿同时有效时，这笔寄存器写入才被接受。本次固件依次执行：

寄存器地址写入值含义
0x400000080x00000100描述符队列起始地址
0x400000180x0000001319 个任务，十六进制 13 等于十进制 19
0x400000000x0000003D本次队列启动配置

随后 CPU 读取 0x40000004 的 STATUS：bit0 是 busy、bit1 是 done、bit2 是 error。读数据只在 cnn_mmio_re 与 cnn_mmio_ready 同时有效时解释。顶层 cnn_status_done 是完成脉冲，与 STATUS 中保持的 done 位不同。

4 看懂 CNN 多通道访存

cnn_valid、cnn_ready、cnn_response、cnn_write、cnn_byte 各有 11 位，每一位对应一条通道。cnn_addr、cnn_wdata、cnn_rdata 各有 352 位，都是 11 段 32 位数据拼在一起；通道 0 在最低位。

通道编号使用者32 位地址或数据的位置
0描述符读取[31:0]
1 和 2计算上下文 0 加载和写回[63:32] 和 [95:64]
3 和 4计算上下文 1 加载和写回[127:96] 和 [159:128]
5ReLU6[191:160]
6ADD[223:192]
7ReLU[255:224]
8PReLU[287:256]
9MaxPool[319:288]
10Requant[351:320]

一般公式是通道 i 使用 [32i+31:32i]。十六进制总线中，每 8 个十六进制数字是一段 32 位值，从最右侧开始数通道 0、1、2。显示空间不足时，拉宽数值栏或选中目标时间查看完整值，不必把总线再次展开成重复轨迹。

一笔访问按三步判断

第一步看请求：valid[i]=1 才说明该通道提出请求。write[i]=0 为读，=1 为写；byte[i]=1 为字节访问，=0 为对齐的 32 位字访问。读取对应段的地址，写入时再读取对应段的 wdata。

第二步看接受：在 clk 上升沿之前，valid[i] 与 ready[i] 同时为 1，这一笔才被接受。valid=1、ready=0 是等待仲裁。看上升沿附近的信号时，应区分边沿前的请求与边沿后更新的下一笔值。

第三步看响应：后续 cnn_response[i]=1 表示该通道完成响应。读和写都会有 response；读事务此时检查 rdata 对应的 32 位段。字节读是符号扩展，例如有符号 8 位的 0xFF 可能返回 0xFFFFFFFF，即 -1。

用一个数字例子理解多路接受

假设某个上升沿前 cnn_valid=0x00A、cnn_ready=0x00A，两者按位与为 0x00A，表示 bit1 和 bit3 同时有效，即两个计算上下文的加载通道同时被接受。这个例子仅解释编码，不是指定时刻的截图值。

判断并行访存要看 valid 与 ready 的按位与中有多少个 1，不能只数 valid 的 1。当前有 4 个存储体，CPU 优先占用它访问的存储体；其他请求若争用同一存储体就会等待，因此并非 11 路都能同拍完成。

5 判断重叠执行和最终结果

顶层波形能直接看到什么

在 CNN 运行窗口内，观察 cnn_valid 与 cnn_ready：多个通道同拍接受表示并行访存；加载通道 1 或 3 与写回通道 2 或 4 同拍接受，表示加载和写回发生重叠。期间 cnn_status_busy 应保持任务仍在处理的含义。

不过，busy=1 加上有访存，不能单独证明那个周期的 PE 正在做乘加。当前 61 根信号只展示大模块接口，没有加入 CNN 内部 PE 信号。实际乘加与加载、写回的重叠由测试平台内部监测，结果记录在 simulation_result.json 中。

当前正常用例指标数值表示什么
tasks19完成并验证的任务数
cnn_cycles3613测试平台统计的 CNN 阶段周期数
load_compute206加载访问被接受与实际 PE 计算重叠的周期数
store_compute163写回访问被接受与实际 PE 计算重叠的周期数
load_store127加载和写回访问同时被接受的周期数
multi_bank700测试平台统计的多路 CNN 访存接受周期数
max_grants4同拍接受 CNN 通道数的峰值

本次固件先通过 UART 加载完整资料，再启动 CNN。因此不应期待 uart_rx 接收本批资料时 CNN 同时计算本批任务。这里的搬运计算重叠指 CNN 内部从 SRAM 加载数据、执行计算、向 SRAM 写回结果之间的重叠。

算一算计算花了多久

在波形中定位 busy 首次拉高与 done 脉冲，读取时间后相减：3818035 − 3781925 = 36110 ns = 36.11 μs。报告的 3613 周期约为 36.13 μs；报告采用测试平台内部起止计数，与这两个可见标记的边界相差 2 拍，不能把两种口径直接当成同一个测量值。

完成之后还要看 CPU 校验

done 表示 CNN 队列完成，之后 CPU 仍会读取 SRAM 并校验。看 dmem_re、dmem_addr 与 dmem_rdata；CPU 数据读为固定一拍返回，没有另外的 ready 或 rvalid 信号。

当前固件最后写入地址 0x00000088：在 dmem_we 有效的上升沿，dmem_wdata=0x0000600D 表示固件校验成功，0xDEAD0001 表示失败。还应结合 simulation_result.json 的 PASS 和逐项数据检查判断结果；只看状态都不忙无法证明计算正确。

正常用例已验证 8192 字节的数据区域及 19 个任务。这里是多任务小规模 RTL 仿真，不等同于完整人脸识别模型的验证。

6 遇到异常按这个顺序检查

看到的现象首先检查
打开后一直是 RESETrst_n_in 是否释放，再看 CLOCK 输出的 rst_n；内部复位需同步释放
UART 很密集或像一块实心区域缩放范围太大，放大到每位 40 ns、每字节约 400 ns
bridge_busy 很久不结束uart_tx 是否发请求、uart_rx 是否收到回复，再看 bridge_error 和 load_error
load_complete=1 但 CNN 没启动先确认 load_error=0，再检查 load_req 撤销及 CNN MMIO 配置
cnn_valid 有值但数据没写进去查看同一通道的 ready 是否同时有效，以及 write、地址和数据段是否对应
cnn_status_done 看不到它是短脉冲，放大 3818035 ns 附近；不要只看全程缩小图
led_busy=0 但 CNN 仍在运行led_busy 表示 bridge_busy；CNN 工作看 cnn_status_busy
地址或数据停在一个旧值没有有效事务时可以保留旧值，先看对应请求和响应信号
状态显示 0 1 2 3用本目录启动入口重开，确保 state_names.txt 仍在原目录
出现 X 或 Z查看复位和驱动连接；X 是未知值，Z 是高阻态，不是普通有效数据

用故障波形练习定位

打开 open_fault_reset.cmd。这是单独的外部 UART 不回复用例，故意制造超时，不要与正常波形混为一谈。约 106935 ns 处 bridge_error 与 load_complete 拉高，随后 bridge_state 进入 FAULT；结合 load_error 判断失败。soc_fault 中 bit4 对应 IMAGE_BRIDGE。

故障后观察 rst_n_in 再次拉低，六路状态进入 RESET、故障位图清零，内部 rst_n 随后同步释放。这个用例验证的是超时检测和硬复位清除，不表示已重新加载资料并完成 19 个任务。

看完一遍应能回答的五个问题

1. 请求加载是什么时候发出的，最后成功还是失败？

2. UART 数据是否经过桥写入 SRAM，写入接受依据是什么？

3. CPU 是否正确设置队列并启动 CNN？

4. 是否存在同拍多通道接受，哪些通道在加载、哪些在写回？

5. CNN 是否完成，CPU 校验是否成功，仿真报告是否 PASS？
