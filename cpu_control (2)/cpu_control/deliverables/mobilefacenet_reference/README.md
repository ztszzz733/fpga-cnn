# MobileFaceNet 真实图片软件基准与 NEureka 对接清单

后续进展：DW stride2 在关闭内部预取后已有通过配置，真实权重前三层的局部区域及量化后处理也已通过 RTL；见 [最新小链条交付](../mobilefacenet_chain/README.md)。下面保留本轮最初的验证范围和预取开启时的失败记录，不能把历史失败当作当前所有配置均不可用。

本轮把“准备跑人脸网络”推进到了可复现的软件基准和卷积模式验证。**完整网络已在电脑 CPU 上输出特征向量；完整网络尚未在 SoC 上运行。** 不启动大图 RTL 仿真，不继续 Vicuna/NVDLA，也不改变六大模块顶层。

## 1. 固定了什么

- 模型来源：[foamliu/MobileFaceNet](https://github.com/foamliu/MobileFaceNet)，源码提交 `a6cc9032a659b615f477833e1a70b5e7931bcccc`，保留其 Apache-2.0 许可证。
- 使用仓库内 `pretrained_model/mobilefacenet_scripted.pt`，SHA-256：`780e31e7c2639a0d5fdebe843f5df3ff81fda79a090164df0ff40514d172853a`。与你 `D:/code/facemodel/MobileFaceNet/pretrained_model/` 中的文件哈希相同。
- 实际加载的模型有 999,936 个参数，输入 RGB 112×112，输出 128 维特征。后处理 L2 归一化后计算余弦相似度。
- 使用你提供的 `D:/code/facemodel/person_1.jpg` 到 `person_4.jpg`，原文件只读。四张都是 112×112；没有重新检测、裁剪或五点对齐，不能仅凭尺寸认定标准对齐已经完成。
- 预处理固定为上游 `data_gen.py` 的验证配置：RGB/255，再按均值 `[0.485,0.456,0.406]`、标准差 `[0.229,0.224,0.225]` 标准化，转 NCHW。本次单次前向，无水平翻转融合。上游 demo 的归一化不同，不能混用；正式准确率评估仍需确认训练约定。

## 2. 真实图片的软件结果

四张图均成功输出有限的 128 维特征，PyTorch 与导出的 ONNX 逐值对比通过，最大绝对误差约 `6.44e-6`。

- [运行记录](reference_result.json)：模型/图片哈希、依赖版本、误差和耗时。
- [图片之间的余弦相似度](cosine_similarity.csv)：只给出数值，不推断图片身份；没有同人/异人标注、阈值或准确率评估。
- [完整算子表 CSV](operators.csv) / [JSON](operators.json)：每个节点的输出尺寸、卷积核、步长、通道分组、计算量和适配说明。
- [中间数值范围](activation_ranges.json)：四张图的观察值，不是充分的量化校准集。

ONNX 已将 BatchNorm 折叠进卷积。本版本实际结构如下，不能把其他 MobileFaceNet 实现的 PReLU 配置直接套进来。

| 运算 | 数量 | 本轮结论 |
|---|---:|---|
| 普通 3×3 卷积 | 1 | 第一层 stride=2；原生小数据模式通过，模型通道/边界仍需接入 |
| 1×1 卷积 | 33 | 小数据模式通过；大通道分块与量化还需验证 |
| 3×3 深度卷积 | 16 | 小数据模式通过；含 3 层 stride=2 |
| 7×7 全局深度卷积 GDConv | 1 | 无原生 7×7 接入；分块累加仅完成软件等价性证明 |
| ReLU6 | 32 | 必须同时实现下限 0 和上限 6 对应的量化阈值，普通 ReLU 不等价 |
| 普通 ReLU | 2 | 现有逐元素算子可复用，量化尺度仍需衔接 |
| 残差 Add | 12 | 需要双输入就绪、保留旁路张量、尺度对齐、饱和处理 |
| Reshape | 1 | 最后展平；不需要乘加阵列 |

本网络没有 MaxPool、PReLU 或 Softmax。L2 归一化与相似度比较在网络输出后单独处理。

单张图卷积共 **233,810,432 次 MAC**（一次 MAC 指一次乘法并累加）。其中 1×1 卷积占 218,431,488 次，约 **93.4%**。因此下一步的性能重点是 1×1 的通道分块、权重/特征搬运和层间衔接，不能仅按算子种类平均复制 3～5 份硬件。最大中间张量有 401,408 个元素，INT8 紧凑存储约 392 KiB，还未计权重和双缓冲；现有小测试的 64 KiB SRAM 不能直接装下全网络中间数据。

## 3. NEureka 小规模 RTL 验证

复用上一轮已经编译的真实 NEureka 条带子系统，执行前核对所有 RTL 与监视器哈希。没有重新编译，没有用 Python 卷积替代硬件。比较包括卷积原始输出、随后普通 ReLU 输出、输入不被破坏和输出区保护字节。

测试输入为确定性生成的小整数，**不是上述人脸图片，也不是模型权重**。每项两帧、四个条带任务；为单独检查运算模式，采用串行卷积/ReLU。输入写入与卷积仍有重叠；层间重叠的证据见前一轮 `deliverables/neureka_stripes`，不能把本轮串行模式的计数说成层间并行。

| 模式 | 测试输入 | 核对的最终字节 | 结果 |
|---|---|---:|---|
| 1×1，CI=3、CO=5 | 10×7，取左上 8×5 输出区域 | 400 | PASS |
| DW3×3，CI=CO=3 | 10×7，valid，输出 8×5 | 240 | PASS |
| 普通 3×3 stride2，CI=3、CO=8 | 10×7，valid，输出 4×3 | 192 | PASS |
| DW3×3 stride2，CI=CO=4 | 10×7，预期输出 4×3 | 未完成 | FAIL：超时 |

前三项记录见 [RTL 模式结果](rtl_modes_result.json)。stride2 使用实际 RTL 配置位 8，不是算完整输出后由 Python 抽样；地址步长配合屏蔽隔行隔列 PE，使输出紧凑写回。本测试 CO 为偶数，不能直接推广到奇数通道和任意边界。

原生 stride2 与深度模式的组合另有单独结果文件，见 [补充 DW stride2 结果](rtl_dw_stride2_result.json)。所有测试均为 valid 卷积；真实网络的 padding=1、通道数超过 32 的累加、偏置和逐通道量化未包含在这些 PASS 中。

**目前不能把 DW stride2 算作可用。** 第一条任务停在 `core_state=4`（MATRIXVEC），没有产生卷积写回或完成，最终达到测试平台 200,000 周期上限。最后一次读请求握手约在 28.095 µs，之后直到超时没有写回；已接收两个任务但完成数为 0，后续提交受反压。`memory_fault=0`、`error=0`，这不是已捕获的 SRAM 地址错误。`compute_active` 在此期间持续为高仅表示停留在计算状态，**不能据此认定每拍都在有效乘加**。见 [失败日志](dw_stride2_failure.log) 和 [末态诊断](dw_stride2_diagnostic.json)。当前证据不足以区分寄存器配置、预取交互或核心模式握手问题，未擅改第三方 RTL，也不能推断所有 NEureka 配置都不支持该模式。

该失败在 `build/runs/20261021_232534_neureka_model_modes` 保留了原始 VCD、输入、权重、寄存器和金标准。由于网络确实需要该模式，应优先定位；可选降级方案是 DW stride1 后按偶数行列抽取，但这会多算并多搬数据，而且抽取路径目前尚未实现。

## 4. 7×7 怎么处理

末端不是普通平均池化，而是每个通道都有独立 7×7 权重的深度卷积，不能擅自换成平均池化或单次 3×3。

已用四张图实际产生的 7×7×512 特征和模型权重，做局部整数化验证：将 7×7 拆为九个不大于 3×3 的区域，先保留宽位宽部分和，全部相加之后再量化。对 4×512 个通道，分块结果与直接整数 7×7 点积完全相等。软件同时验证了有符号激活改成无符号表示时的权重和补偿。

[分解验证记录](gdconv_lowering.json) 中的 `hardware_implemented=false` 是实际状态：边缘补零、32 位中间结果、跨任务累加及最终量化还没有接到 NEureka。局部整数化误差是诊断数据，未包含完整网络量化误差；本例也没有验证硬件偏置融合。绝不能先把九个部分结果各自压到 8 位再相加，否则会丢失信息。

## 5. 下一步实施顺序

1. **先解决 DW stride2，并冻结整数数值约定。** 小例定位配置/握手，避免直接放大任务；同时明确输入/权重尺度、零点、有符号表示、逐通道乘数、移位、偏置、舍入与饱和。四张图可供调试，不能承担正式准确率校准。当前参考图中 63/97 个被观察的算术节点出现负值，不能假设所有层都只有非负像素。
2. **补齐后处理和残差。** 在 CNN 内实现量化 ReLU6、尺度对齐的残差加法及必要的重定量。先用短链逐层对照整数参考。
3. **让卷积适配真实形状。** 首层 padding/stride2、PW/DW 大通道分块、偏置、32 位部分和，随后实现 7×7 分解。已有模式 PASS 只覆盖表中小形状。
4. **做模型任务表与缓冲生命周期。** 从算子表生成依赖和张量地址；把“输入行够了”“两个残差输入都好了”“输出槽可以复用”作为实际发射条件。多张图和条带必须带 frame/layer/tile 标识；残差用完之前不能释放旁路数据。
5. **接 CPU/UART，再按瓶颈增实例。** 先做首层→DW→PW→激活/残差的小链条，再扩全图；保持顶层六模块。UART 不在本轮仿真中，不能声称四张照片已经通过串口进入 SoC。

以上仍沿用开源模型、NEureka 算术核心及上游权重排列定义；自行实现部分主要是本工程的量化适配、任务生成、缓冲与调度。不从头重写卷积核心。

## 6. 复现与 GPU

本轮最终软件参考运行目录为 `build/runs/20261021_232600_mobilefacenet_reference`，含导出模型、形状检查、四张图的双框架对照、中间范围统计和分解验证，脚本计时 **29.61 秒**；此前同流程约 9.48 秒，说明电脑负载会影响耗时，不能当作硬件速度。最新前三项 RTL 运行 `20261021_232033_neureka_model_modes` 合计仿真 **63.71 秒**，脚本总计 70.32 秒；补充 DW stride2 超时仿真 **106.48 秒**。以上均不含首次下载/安装推理依赖，RTL 重新编译耗时为 0。三个通过案例在 100 MHz 下的硬件时间分别为 70.36、72.77、93.71 µs，含测试平台输入间隔与两帧任务，不能等同完整人脸推理延迟。
