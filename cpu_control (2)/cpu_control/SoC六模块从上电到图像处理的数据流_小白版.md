# SoC 六模块从上电到图像处理的数据流（小白版）

日期：2026-10-08。按用户最新决定，继续使用旧版六模块方案。独立程序下载口、可写 IMEM 和下载互锁方案不再推进。

> 后续需求澄清：用户期望运行时无需电脑，由外部存储数据源自动供数。下文“电脑上传”是现有接口使用示例，不是系统必须依赖电脑；固件指板内CPU执行的程序。自动外部加载方案及其与当前RTL的差别，见 [上电自动读取外部数据与固件作用说明](上电自动读取外部数据与固件作用说明_小白版.md)。

本文依据当前 `rtl/soc/face_soc_top.sv`。本次只整理说明，没有修改 RTL；此前讨论的下载改造没有实施，因此无需回滚硬件代码。

**先记住主线：IMEM 给 CPU 提供程序；电脑经图像桥把数据放入 SRAM；CPU 配置并启动 CNN；CNN 自己读 SRAM、计算、写回 SRAM；CPU 查询完成，电脑再经图像桥取回结果。**

阅读时区分两种标记：

- **【已有硬件】**：现有 RTL 已有对应接口或动作。
- **【需要固件配合】**：硬件有通路，但具体程序、数据布局和双方通知规则仍需实现，不能认为上电后会自动完成。

## 1. 先认清六个模块

| 模块 | 小白理解 | 在处理图像时做什么 |
|---|---|---|
| `clock_unit` | 节拍器和统一复位开关 | 提供公共时钟、控制复位释放；不处理像素 |
| `imem_rom`（IMEM，也曾写作 IEM） | CPU 的程序书 | 保存 CPU 指令，按 CPU 给出的地址返回指令 |
| `cpu_core` | 执行程序、安排工作的控制者 | 初始化、检查准备状态、配置 CNN、查询完成和处理结果 |
| `image_bridge` | 电脑与 SRAM 之间的搬运员 | 接收 UART 数据包，校验后读写 SRAM，再回复电脑 |
| `datasram` | 共享数据仓库 | 放图像、权重、参数、任务表、中间结果、最终结果和软件变量 |
| `mobilefacenet_accelerator_top`（CNN） | 专门计算网络任务的计算模块 | 读取任务和输入数据，执行支持的算子，把结果写回 SRAM |

![旧版六模块连接图](docs/figures/soc_cpu_mem_io.png)

CPU、IMEM、datasram 是三个平级模块，不是把两个存储器藏在 CPU 里面。CNN 与图像桥共享 datasram 的 B 侧访问入口，仲裁已经在 datasram 内部。

## 2. 上电前先准备什么

要让“上电后处理图像”成立，至少要先准备好下面两类内容。

| 内容 | 放在哪里 | 例子 |
|---|---|---|
| CPU 程序 | IMEM | 初始化、等待图像就绪、写 CNN 寄存器、轮询状态等指令 |
| CNN 所需数据 | 运行前放到 datasram | 图像张量、模型权重、参数和任务描述符 |

**CPU 程序不是图像；模型权重也不是 CPU 指令。**

旧版通过 `IMEM_INIT_FILE` 指定指令初始化文件。仿真时由 `$readmemh` 加载；板级要将正确初始化内容纳入 FPGA 配置流程并验证。旧版 UART 只能访问数据 SRAM，不能在线写 IMEM。

当前顶层 `IMEM_INIT_FILE` 默认空字符串，不代表已经有一份完整人脸识别程序。下面说明的完整业务流程，以实际提供合适固件为前提。

默认 IMEM 为 64 KiB，datasram 为 256 KiB；这不表示整个模型的权重和中间张量一定全部放得下，实际数据布局和容量仍需核对。

## 3. 第一步：上电、时钟运行、系统复位

**主角：clock_unit。其他五个模块接收它的时钟和复位。**

【已有硬件】板载晶振把时钟送到 `sys_clk`，外部复位通过 `rst_n_in` 进入 `clock_unit`。

```text
板载晶振 → sys_clk → clock_unit → clk → 其余五个模块
外部复位 → rst_n_in → clock_unit → rst_n → 其余五个模块
```

本版时钟直接传递，不倍频、不降频、不带 PLL。外部复位拉低时，内部复位拉低；外部复位释放后，经过三个时钟沿同步释放内部复位。采用同步复位的模块还会在有效时钟沿执行相应状态更新。

复位主要让：

- CPU 的 PC 回到 `RESET_PC`，默认 0；流水线和寄存器回到初始状态。
- CNN 的控制、任务状态回到初始状态。
- 图像桥的收包、回复和事务控制回到初始状态。
- datasram 的在途访问和故障控制状态清除。

**复位不会把 datasram 的整个存储数组自动清零，也不会把一张图片或模型自动装进去。** 普通复位同样不会重新运行 IMEM 的初始化文件读取动作。

## 4. 第二步：CPU 开始从 IMEM 取指

**主角：cpu_core 和 IMEM；clock_unit 持续提供时钟。**

【已有硬件】CPU 从复位地址开始请求程序指令：

```text
CPU：imem_addr = 当前指令地址，imem_re = 1
                 ↓
IMEM：在上升沿接收地址，沿后给出 imem_rdata
                 ↓
CPU：接收指令，译码并执行
```

这是固定一拍的同步取指接口，不是组合读出，也没有额外 ready。

CPU 内部大致按“取指 → 译码 → 执行 → 访存相关处理 → 写回”推进。Control 看懂指令并产生控制信号；Datapath 保存状态、计算地址和数值、真正执行读写。

顺序执行时地址通常加 4；碰到跳转或分支时按指令改变下一地址。CPU 等图像、配置 CNN、查询结果时，都在持续执行 IMEM 中的程序，而不是只有开机时读一次 IMEM。

## 5. 第三步：CPU 初始化，准备接收图像

**主角：cpu_core 和 datasram；image_bridge 准备接包。**

【需要固件配合】CPU 应先按程序建立软件运行环境，初始化必要变量和双方通信状态，安排好 SRAM 各区域的用途。

可以这样理解仓库分区，以下仅表示用途，不是已冻结的地址表：

```text
datasram
├─ CPU 的栈、变量和通信标志
├─ 输入图像 / 输入张量
├─ 权重、偏置及其他算子参数
├─ CNN 任务描述符队列
├─ 中间结果缓冲区
└─ 最终输出区
```

CPU 通过 A 口初始化或读取这些内容：

```text
cpu_core ── dmem_addr / dmem_wdata / dmem_we / dmem_wstrb ──→ datasram
cpu_core ←──────────────── dmem_rdata ──────────────────── datasram
```

A 口读为固定一拍，写按字节使能生效。CPU 的普通 LW/SW 等访存指令走这条路径。

初始化和电脑上传必须有先后及所有权约定，避免“电脑刚写好的图像又被 CPU 初始化覆盖”。图像桥能收包，不等于 CPU 固件已经初始化完成；原 `led_ready` 也不能代表“整个人脸识别应用已就绪”。

目前还没有完整应用固件和正式通信地址表，这一步需要补齐。

## 6. 第四步：电脑把图像和计算资料送进 SRAM

**主角：image_bridge 和 datasram。CPU 不搬运每个图像字节。**

【已有硬件】旧版图像输入通路是 UART，没有相机接口：

```text
电脑准备好的原始数据
    ↓ UART串行发送
uart_rx
    ↓
image_bridge：收包、检查CRC、检查地址和长度
    ↓ io_mem_* 请求
datasram：通过内部B侧选择接收并写入
    ↓ 完成 / 错误
image_bridge：组织回复 → uart_tx → 电脑
```

一次包最多携带 256 字节数据。电脑发完一包，要等到完整回复后再发下一包，直到传完需要的内容。图像桥不会一次缓存整张图像。

写数据时，图像桥把串口字节整理为对齐的32位访问，利用 `io_mem_be` 选择目标字节。它并不是把8位串口字节直接接在32位存储器总线上。

电脑除了传图像，也可以通过同一 SRAM 写入通路传权重、参数和任务表，因为图像桥本质上搬运的是字节，不会判断这些字节属于哪种算法。

**图像桥不会解码 JPEG/PNG，也不会自动做人脸裁剪、缩放或量化。** 输入必须按照模型要求预先整理好，或明确交给其他软件处理；不能把 JPEG 文件原样送入就当作有效 CNN 输入张量。描述符和权重的格式同样要符合 CNN 的定义。

CPU 和 CNN 在此期间不应读写正在上传的区域。桥写入成功只代表该包的内存传输完成，不代表整张图已到齐、模型资料齐备，更不代表识别完成。

## 7. 第五步：CPU 怎样知道“资料传完，可以计算”

**主角：电脑、image_bridge、datasram、cpu_core。这里需要软件交接。**

目前没有“图像桥自动向 CPU 发图像完成中断”的硬件接口，也没有桥收到最后一包就直接启动 CNN 的逻辑。

【需要固件配合】可通过 SRAM 中双方约定的通信区，也就是 mailbox，完成通知：

```text
电脑先上传全部数据并校验
    ↓ 最后写一个“本轮输入准备完成”的通信记录
image_bridge → datasram 的约定通信区
    ↓
CPU运行等待程序，通过A口读取通信记录
    ↓ 确认本轮数据完整、有效
准备启动CNN
```

这个通信记录可以表达本轮序号、输入位置、长度及准备状态，但**当前没有冻结其字段和地址，也没有配套完整固件**。这里是解释应如何接起业务流程，不是宣布现有模块已经自动做好通知。

启动时通信区必须先初始化并建立可靠的就绪约定，不能把 SRAM 上电的随机内容当成“已传完”。发送方和接收方也应约定写入、检查及确认时段，避免双方同周期访问同一字且有写入，触发现有 SRAM 的冲突规则。

如果模型权重和任务表可复用，后续每张图未必都要重传它们；是否复用由固件和内存规划决定。

## 8. 第六步：CPU 通过 MMIO 配置并启动 CNN

**主角：cpu_core 和 CNN。IMEM 继续为 CPU 提供程序指令。**

【已有硬件】CPU 执行普通32位读写指令，访问 CNN 寄存器地址。Datapath 译码地址后，将这些请求送到 CNN，而不是数据 SRAM。

```text
IMEM中的配置程序 → CPU执行SW → cnn_mmio_* → CNN内部寄存器
```

默认地址及本轮主要动作如下：

| CPU访问的地址 | 当前含义 | 做什么 |
|---|---|---|
| `0x4000_0004` | STATUS | 先检查 CNN 是否可开始新任务 |
| `0x4000_0008` | QUEUE_BASE | 写入 SRAM 中任务描述符队列的起始地址 |
| `0x4000_0018` | TASK_COUNT | 写入任务数量 |
| `0x4000_0000` | CONTROL | 写 `0x3D`，设置队列模式并触发启动 |

【需要固件配合】必须先准备好完整任务表，再写队列地址、任务数并启动。每个任务的输入、输出、权重地址和运算参数保存在 SRAM 的描述符里，不是 CPU 通过一组新引脚逐层塞给 CNN。

这组 MMIO 为当拍响应，CPU 不支持在这里无限等待。CNN 即使计算很久，其寄存器访问也不应因此拉低 ready 拖住 CPU；计算进度由 STATUS 表达。

忙时不要重复 START，也不要试图更新队列配置。CNN 原始寄存器逻辑对这些情况有约束，软件应按其规则操作。

## 9. 第七步：CNN 自己去 SRAM 取任务、取数据、计算

**主角：CNN 和 datasram。CPU 不在图像计算数据的必经路径上。**

【已有硬件】CNN 接受启动后，内部调度逻辑根据队列地址读取任务描述符，再安排对应计算单元工作。

```text
CNN 发出任务表读取地址
    ↓ mem_addr / mem_read
datasram B侧读出描述符
    ↓ mem_rdata / mem_ready
CNN读懂任务：算什么、输入在哪、输出放哪
    ↓
CNN继续读取输入、权重和参数
    ↓
CNN内部计算单元执行相应运算
```

一个32位读访问可以这样理解：

1. CNN 给出地址并保持 `mem_read=1`。
2. datasram 在可以接收时的上升沿读出该字，并记录返回属于 CNN。
3. 随后的响应周期同时给出正确 `mem_rdata` 和 `mem_ready=1`。
4. CNN 在响应采样沿接收数据，推进到后续访问。

这里 ready 表示完成，不能在读数据尚未准备好时提前拉高。

输入图像不是先流经 CPU 的寄存器堆或 ALU 再送 CNN，实际路径是：

```text
datasram → CNN → datasram
```

CPU 在这时可以运行轮询程序或做互不冲突的其他操作。由于 A、B 两口共享同一存储数组，仍不能无约束地修改 CNN 正在使用的数据。

## 10. 第八步：CNN 把中间结果和最终结果写回 SRAM

**主角仍然是 CNN 和 datasram。**

【已有硬件】CNN 通过原生写口写回：

```text
CNN：mem_addr = 目标地址
     mem_wdata = 计算结果
     mem_write = 1
             ↓
datasram：成功接受时给mem_ready，在采样沿写入
```

中间任务的输出可以成为后续任务的输入，具体依赖和地址由任务表描述。不是每做完一层都必须先把结果传到电脑，再传回来。

CNN 外部写口按整个32位字写入；内部需要写一个 INT8 字节时，由它原有的访存模块先读整个字、替换目标字节、再写回。这个读改写过程不是对其他主设备的跨事务原子锁，所以 CPU 和电脑不能同时修改同一个结果字。

整个队列完成后，CNN 更新自身状态寄存器中的 DONE；出错则记录 ERROR。**状态寄存器保存“做完没有”，真正的计算输出仍在 SRAM。**

## 11. 第九步：CPU 查完成、检查结果

**主角：cpu_core、CNN，以及需要时的 datasram。**

【已有硬件】CPU通过MMIO读STATUS：

| STATUS 位 | 含义 |
|---|---|
| bit0 BUSY | CNN 是否仍忙 |
| bit1 DONE | 队列完成状态 |
| bit2 ERROR | 队列执行错误状态 |

【需要固件配合】程序循环检查状态，同时处理 ERROR 和超时，不能只等 DONE 而永远不处理失败。

```text
CPU → CNN STATUS：完成没有？
    ├─ 仍忙：继续等，或做允许的其他工作
    ├─ 出错/超时：执行错误处理
    └─ 成功完成：确认结果可以读取
```

之后 CPU 可以通过自己的 SRAM A 口读取输出，也可以仅发布“本轮结果已就绪”的软件状态，让电脑通过图像桥直接读走结果。两种方式都需要固件明确安排。

还要区分“CNN 计算输出”和“识别出是谁”：如果输出是特征向量，后续与已登记特征比较、阈值判断、名字或ID映射，需要另有软件流程。当前硬件不能仅凭 DONE 就被描述为已经输出某个人的身份。

## 12. 第十步：电脑从 SRAM 取回结果

**主角：image_bridge 和 datasram。CPU负责的软件就绪通知需要先完成。**

【需要固件配合】电脑先按约定确认本轮结果已就绪、地址和长度正确。桥本身不知道哪次计算做完了，不能看到桥空闲就直接读正在变化的输出。

【已有硬件】电脑发SRAM读请求，返回路径是：

```text
电脑发送：读某地址、某长度
    ↓ uart_rx
image_bridge → io_mem_req → datasram
    ↓ 等待gnt接单，再等待rvalid返回
image_bridge取出返回字中的对应字节，组织回复和CRC
    ↓ uart_tx
电脑得到输出数据
```

这个过程不需要 CPU 逐字节代发 UART。CPU 也没有一组直接连串口发送器的输出接口。

原硬件不会主动把结果推送到电脑，电脑需要发起读请求。读完并按软件约定确认本轮结束后，才能安全复用输入/输出缓冲区处理下一张图。

## 13. 六个模块从头到尾的工作顺序表

下表是业务阶段，不是说每个阶段只有一个模块在时钟上运行。

| 阶段 | clock_unit | IMEM | cpu_core | image_bridge | datasram | CNN |
|---|---|---|---|---|---|---|
| 上电复位 | 提供时钟、释放复位 | 指令内容按配置准备 | PC和流水线复位 | 接收控制复位 | 访问控制复位，数据不自动清零 | 控制和任务状态复位 |
| 软件初始化 | 持续供时钟 | 持续供指令 | 初始化并进入等待 | 可按协议收包，软件须约定时机 | 保存变量及通信区 | 未启动则空闲 |
| 上传资料 | 同上 | CPU需要时供指令 | 等待/维护软件状态 | 接收、校验、写入、回复 | 保存图像/权重/任务表 | 不访问正在上传的区域 |
| 交接并启动 | 同上 | 供应配置程序 | 确认资料齐全，写CNN MMIO | 已结束上传 | 保存已完整交接的数据 | 接受队列启动 |
| CNN计算 | 同上 | 供应CPU轮询等程序 | 查询状态或做允许的工作 | 避免干扰计算数据 | 供数、保存中间和最终结果 | 取任务、计算、写回 |
| 完成处理 | 同上 | 供应后处理程序 | 检查错误、处理/发布结果 | 等电脑读取请求 | 保留有效输出 | 状态记录完成 |
| 结果返回 | 同上 | CPU需要时供指令 | 按约定维护结果状态 | 从SRAM读出、通过UART回复 | 提供输出数据 | 等待下一轮 |

## 14. 最容易混淆的几件事

**一，clock_unit 一直工作，但不搬运数据。** 它给其他模块提供动作节拍。

**二，CPU 一直按 IMEM 程序办事，但不必亲自搬每个像素。** 上传和取回由图像桥完成，CNN计算时自己访问数据SRAM。

**三，IMEM 和 datasram 地址都可从0开始，但不是同一块存储器。** 程序取指走独立接口；旧UART写地址0只会进入datasram。

**四，CNN MMIO 的读回值是配置或状态，不是结果数组。** 输出数据从SRAM读取。

**五，桥忙灯不是CNN忙灯。** `led_busy=bridge_busy`；LED熄灭不能证明CNN完成。`led_ready`也不代表模型、固件或整帧数据全部就绪。

**六，共享存储器不代表可以随意同时改数据。** B侧CNN优先，图像桥可能等待；A/B同周期访问同一字且任一方写入时，B侧报错。仲裁不保证整帧上传或CNN读改写原子性。

**七，CNN存储故障和普通队列ERROR不同。** `cnn_mem_fault`可能让CNN一直等访存完成，恢复需系统复位；UART内存超时也需系统复位。程序必须考虑超时，不能假定所有错误都能靠写CNN软件RESET解决。

## 15. 当前项目实际走到了哪一步

| 内容 | 当前状态 |
