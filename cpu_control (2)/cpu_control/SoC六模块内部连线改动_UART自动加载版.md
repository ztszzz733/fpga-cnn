# SoC 六模块内部连线改动说明（UART 外部设备自动加载版）

日期：2026-10-08。

> 后续方案调整：用户要求六模块之间点对点增线，不采用本文的顶层MMIO分流方案。当前讨论稿改为 [CPU与图像桥三线直连增线说明](SoC六模块增线说明_CPU与图像桥三线直连.md)。本文仅保留作未实施的备选历史稿，原六模块RTL未改。

适用前提：外部存储设备或控制模块具备 UART 接口，运行时不需要电脑控制。具体设备命令和帧格式仍待确定；UART 电气兼容不等于应用协议已经兼容。

**本文是接线改动设计稿，不是已经实现的 RTL。原六模块代码、旧版接线说明均保留。本次不修改 RTL，不恢复已放弃的 IMEM 在线下载方案。**

旧版依据：[SoC 顶层连线与总体 I/O 说明](SoC顶层连线与总体IO说明_小白版.md)。固件含义见 [上电自动读取外部数据与固件作用说明](上电自动读取外部数据与固件作用说明_小白版.md)。

## 1. 先看结论：外部不加引脚，内部新增一条控制分支

本稿选用如下方案：

> **IMEM 预装固定固件；CPU 上电自动配置加载器；image_bridge 主动通过原 UART 向外部模块取数据并写 SRAM；CPU 读取加载状态，资料齐全后启动 CNN。**

“CPU配置加载器”是板内程序自动执行，不是电脑操作。上电后这套程序会自行往下走。

| 项目 | 改动后 |
|---|---|
| 平级大模块数量 | 仍然六个，不新增第七个程序下载桥 |
| 对外数字 IO | 仍为 7 根：时钟、复位、UART RX/TX、三个 LED |
| CPU 时钟和复位 | 继续共用原系统时钟和复位，不增加 CPU 独立时钟或下载复位 |
| IMEM | 仍为只读取指，预装固定固件，不增加外部程序写入口 |
| 原有存储通路 | CPU A口、CNN B口、图像桥 B口保留 |
| 新增内部连接 | CPU 的 MMIO 增加到 image_bridge 的控制/状态分支，以及顶层读回选择 |
| 自动读取控制 | 加在 image_bridge 内部 |
| CPU 代码 | 补完整固定固件，并扩展加载器寄存器的地址译码 |

这里没有新加 `prog_rx/prog_tx`，也没有让图像数据先经过 CPU 再转交 CNN。

## 2. 改动后的六个模块分别负责什么

| 大模块 | 原职责 | 本方案的变化 |
|---|---|---|
| `clock_unit` | 公共时钟、复位同步释放 | 基本职责和连线保持 |
| `imem_rom` | 保存并返回 CPU 程序 | 接口不变，补入实际自动运行固件 |
| `cpu_core` | 取指、执行、数据访存、CNN MMIO | 保留 Control C1 执行控制；MMIO 可寻址范围增加加载器寄存器，执行自动调度固件 |
| `image_bridge` | 被动接收 IMIO 请求、访问 SRAM、回复 | 增加内部控制/状态寄存器、主动读取外部模块的协议状态机、长度/校验/完成管理 |
| `datasram` | 共享 RAM、A/B 访问、内部 B 仲裁和完成时序 | 原端口与仲裁保留；为加载数据和运行数据划分区域 |
| `mobilefacenet_accelerator_top` | 按任务队列计算 | 原 MMIO、访存接口和计算逻辑保留 |

自动读取状态机和寄存器是 image_bridge 内部子模块，不把它们数成新的平级大模块。

## 3. 总体连线图

```text
                          clock_unit
                    clk / rst_n → 其余五模块

IMEM ←──── ① 固定一拍取指 ────→ cpu_core
                                  │
                                  ├── ② 数据A口 ───────────→ datasram
                                  │
                                  └── 原MMIO输出
                                         │
                              顶层地址选择 / 返回选择
                                  ┌──────┴──────┐
                                  ▼             ▼
                            ③ CNN寄存器    ⑥ 新加载器寄存器
                                  │             │
                                 CNN       image_bridge
                                  │             │
                           ④ 原生mem_*    ⑤ 原io_mem_*
                                  └──────┬──────┘
                                         ▼
                                     datasram B侧

外部UART存储模块 TX ──→ 原 uart_rx ──→ image_bridge
外部UART存储模块 RX ←── 原 uart_tx ←── image_bridge
```

图中的“顶层地址选择/返回选择”是顶层连线和组合选择逻辑，不是独立的第七个大模块，也不是 SRAM 仲裁器。

image_bridge 使用新增控制接口接收“读哪一段、放哪里、何时开始”，使用原 `io_mem_*` 把数据写进 SRAM；两套接口用途不同。

## 4. 哪五组原有连接保持

| 编号 | 模块之间 | 请求方向信号 | 返回方向信号 | 位宽 |
|---|---|---|---|---|
| ① | CPU ↔ IMEM | `imem_addr[31:0]`、`imem_re` | `imem_rdata[31:0]` | 33 / 32 |
| ② | CPU ↔ datasram A口 | `dmem_addr[31:0]`、`dmem_wdata[31:0]`、`dmem_re`、`dmem_we`、`dmem_wstrb[3:0]` | `dmem_rdata[31:0]` | 70 / 32 |
| ③ | CPU ↔ CNN寄存器 | `cnn_mmio_addr[31:0]`、`cnn_mmio_wdata[31:0]`、`cnn_mmio_re`、`cnn_mmio_we` | `cnn_mmio_rdata[31:0]`、`cnn_mmio_ready` | 66 / 33 |
| ④ | CNN ↔ datasram B侧 | `mem_addr[31:0]`、`mem_wdata[31:0]`、`mem_read`、`mem_write` | `mem_rdata[31:0]`、`mem_ready` | 66 / 33 |
| ⑤ | image_bridge ↔ datasram B侧 | `io_mem_addr[31:0]`、`io_mem_wdata[31:0]`、`io_mem_req`、`io_mem_we`、`io_mem_be[3:0]` | `io_mem_rdata[31:0]`、`io_mem_gnt`、`io_mem_rvalid`、`io_mem_error` | 70 / 35 |

位宽不包含公共时钟和复位。第③组仍是相同的 CNN 接口，但它的请求来自新的顶层地址选择分支，而不是无条件直接连接 CPU 请求。

这些时序约定继续保留：

- IMEM 取指固定一拍，CPU 数据 SRAM A口固定一拍，不新增等待线。
- CPU 访问 CNN MMIO 仍为零等待。
- CNN 的 `mem_ready` 表示真正完成，读时返回数据有效；不增添不存在的 CNN gnt/error 端口。
- 图像桥写操作在 gnt 时确认完成，读操作在 gnt 后等待 rvalid；error 保留。
- B侧仍在 datasram 内部仲裁，不新增外置 B 仲裁器或存储适配器。

## 5. ⑥ 新增 CPU 与 image_bridge 的控制/状态连接

本稿选择让 CPU 用普通 LW/SW 读写加载器寄存器，避免 CPU 反复轮询某个正被 B口写入的 SRAM 完成标记，从而触发同字读写冲突。

新增到 image_bridge 的逻辑接口如下，名称为拟议名称：

| 线组 | 新内部信号 | 位宽 | 来源 → 去向 | 用途 |
|---|---|---:|---|---|
| 地址 | bridge_mmio_addr[31:0] | 32 | CPU经顶层分支 → image_bridge | 选择加载器控制/状态寄存器 |
| 数据 | bridge_mmio_wdata[31:0] | 32 | CPU经顶层分支 → image_bridge | 写源位置、目标地址、长度和命令 |
| 数据 | bridge_mmio_rdata[31:0] | 32 | image_bridge → 顶层返回选择 → CPU | 读忙、完成、错误及进度 |
| 信号 | bridge_mmio_re | 1 | 顶层 → image_bridge | 该设备的寄存器读请求 |
| 信号 | bridge_mmio_we | 1 | 顶层 → image_bridge | 该设备的寄存器写请求 |
| 信号 | bridge_mmio_ready | 1 | image_bridge → 顶层返回选择 → CPU | 当拍寄存器访问完成 |

合计：**新增一组66位请求、33位返回的内部逻辑接口。** 不表示 FPGA 外部增加99根引脚。地址和写数据可以由原 CPU MMIO 网络分支给两个设备，实际是增加接收端，不需要CPU再造第二套地址计算电路。

本方案不用额外的 `load_done` 引脚直接连CPU Control。`load_busy/load_done/load_error` 在桥内部保存为状态位，经 `bridge_mmio_rdata` 返回给 CPU。

因此，CPU读“加载完成了吗”也是执行普通加载指令，不需要新的CNN指令、UART指令或中断机制。

## 6. 顶层 MMIO 接线怎样由一条变成两条分支

旧版：

```text
cpu_core.mmio_* ←→ CNN
```

新版设计：

```text
                      ┌─ 地址属于CNN ───→ CNN
cpu_core.mmio_* ──选择─┤
                      └─ 地址属于加载器 → image_bridge

CNN返回 ─────┐
             ├─ 按同一地址选择 ─→ cpu_core.mmio_rdata / mmio_ready
图像桥返回 ──┘
```

在顶层可将CPU原接口对应网络改称 `cpu_mmio_*`，两个外设分支称 `cnn_mmio_*`、`bridge_mmio_*`。这是接线名称的区分，不是修改Control C1端口。

设计规则：

1. 地址译码互斥，一笔CPU请求只发给一个设备。
2. 两个设备可接收同一份地址/写数据网络，但 `re/we` 必须按地址分别使能。
3. CPU的rdata和ready通过选择逻辑接收，不能把两个设备的输出直接短接。
4. 加载器寄存器必须像现有CNN寄存器一样当拍响应，不能等外部串口传完数据才给ready。
5. `bridge_mmio_ready=1`只表示CPU寄存器访问完成，不表示外部数据已经加载完成。后者必须读STATUS。

### 地址译码不能漏改

现有生产 `address_decoder.sv` 只认可CNN窗口内 `+0x00`～`+0x20` 的九个对齐寄存器槽位。**仅在顶层加一组线，CPU仍不会自动发出新的加载器MMIO请求。**

实际实现时必须扩展CPU数据访问的地址译码，让新的加载器寄存器地址也被识别为合法的字读写MMIO，并保证不会误命中SRAM。

Control C1的指令译码和流水线控制不因此增加端口；Datapath的计算、流水寄存器及访存时序可以保留，但**Datapath相关的地址译码属于必须调整的集成部分**。不能把本方案说成“CPU侧任何RTL都不需要改”。

实施时应保留伙伴原始代码，使用独立集成版本和明确文件清单；同名模块不可同时编译。本次未生成或修改该版本。

## 7. 加载器寄存器建议（仅设计草案）

为方便解释，暂用独立基址 `0x4000_1000`，与原CNN基址 `0x4000_0000` 分开。该地址目前不在旧CPU的有效MMIO范围内，**尚未实施、尚未冻结为双方正式地址规范**。

| 偏移 | 拟议寄存器 | 读写 | 含义 |
|---|---|---|---|
| `+0x00` | LOAD_CONTROL | 写命令 | START发起一段加载；空闲时CLEAR_RESULT清除上一段结果。清状态不等于中途取消传输 |
| `+0x04` | LOAD_STATUS | 只读 | BUSY、DONE、ERROR；复位后均清零 |
| `+0x08` | SOURCE_OFFSET | 读写 | 外部数据源的逻辑位置，由外部设备协议解释 |
| `+0x0C` | SRAM_DST | 读写 | 本段数据写入的内部SRAM字节地址 |
| `+0x10` | BYTE_LENGTH | 读写 | 本段预期字节数，必须非零且目标范围合法 |
| `+0x14` | EXPECTED_CRC | 读写 | 本段期望校验值；具体CRC覆盖范围和格式待协议确定 |
| `+0x18` | BYTES_WRITTEN | 只读 | 本段已成功写入SRAM的字节数 |
| `+0x1C` | ERROR_CODE | 只读 | 设备无响应、协议错误、校验失败、SRAM错误等原因 |

CPU固件先写配置，再发START，之后读STATUS。START接受后清上一段结果并置BUSY；读寄存器不清DONE/ERROR，避免轮询错过结果。

忙时配置保持不变，重复START必须按协议明确拒绝并记录原因，不能悄悄把当前数据改写到另一地址。所有寄存器访问仍需当拍完成；拒绝的是业务动作，不是把CPU挂在总线上。

一段DONE必须在长度满足、校验通过、最后一笔SRAM写入成功完成后才置位。本段失败不得置成功DONE；部分数据可能已经写入，固件要把该段视为无效。

**这里的DONE表示“一段加载完成”，不是“整个模型都准备好了”。** 固件依次加载图像、权重、参数、任务表，全部必要段完成后才允许启动CNN。

SOURCE_OFFSET不代表任意UART模块都支持内存地址读取。若设备按文件名或对象编号访问，需要在桥内部按真实协议映射；协议未确定前不能编造实际读命令。

## 8. image_bridge 内部需要增加什么

旧版的主流程是“等外部发IMIO包 → 检查 → 访问SRAM → 回复”。新版自动加载模式增加：

```text
CPU配置加载器
      ↓
等待外部UART模块就绪 / 按协议建立会话
      ↓
通过原uart_tx发读取命令
      ↓
通过原uart_rx接收本段数据
      ↓
分块校验、整理地址和字节使能
      ↓
用原io_mem_*写入datasram，等待完成或error
      ↓
确认长度、整段校验及最后一笔写入完成
      ↓
锁存DONE或ERROR，CPU通过新MMIO分支读取
```

这些状态机、控制寄存器和缓冲区放在image_bridge内部。外部接线仍只有一对UART信号。

需按实际设备提供流量控制：例如每块确认后才发下一块，或桥只请求自己缓冲得下的数据。现有桥在访存/回复期间并不能无限接收连续数据，因此不能直接假定外部设备持续满速发送也不会丢字节。

如果外部设备上电主动推送而不接受读取命令，可以把“发读命令”替换为“按协议等待/确认数据”，但仍保留CPU初始化、接收授权、目标范围和完成状态管理。兼容UART只是本稿前提，最终推送/请求方式仍需按设备协议确定。

旧IMIO调试模式若要继续保留，必须与自动读取模式互斥选择，且共用一个明确的TX控制者，不能让两个状态机同时驱动UART。是否保留、怎样切换属于后续协议设计，不能承诺改造后所有旧命令天然兼容。

## 9. 上电后的实际自动步骤

这里描述目标行为，不是当前RTL已经完成的验收结果。

1. **clock_unit释放复位。** CPU、桥、CNN和存储控制回到初始状态，使用同一个clk。
2. **CPU从IMEM执行固定程序。** 初始化自己的变量和数据布局，确认加载区不会被初始化过程覆盖。
3. **CPU写加载器寄存器并发START。** 这些指令由CPU自动执行，不需要电脑。image_bridge这时才开始本段外部读取，避免抢在CPU初始化之前写数据。
4. **image_bridge通过UART读取并写入SRAM。** CPU可以轮询桥的状态寄存器，不在被写入的数据字上竞争。
5. **逐段完成。** CPU依次确认图像、权重、参数和任务表全部有效；任何段错误或超时都不启动CNN。
6. **CPU配置原CNN寄存器。** 写QUEUE_BASE、TASK_COUNT，再向CONTROL写`0x3D`。
7. **CNN经原mem_*计算和写回。** CPU继续查询CNN STATUS，检查DONE、ERROR和超时。
8. **处理结果。** 由CPU按固件处理、发布或安排输出；确认这一轮结束后再加载下一轮。

第一版采用“加载与CNN计算分阶段”的固件规则，避免加载器覆盖CNN正在使用的图像、权重和结果。现有硬件仲裁不会自动保证整份数据的所有权，不能仅靠B口优先级代替软件阶段管理。

本稿不增加CNN直接连到image_bridge的busy线，CNN的状态仍由CPU通过原MMIO查询。若未来要求硬件强制禁止所有非法并发，需要另行增加明确互锁，不能把本稿的软件规则描述成已有硬件保护。

外部结果回传并非当前UART加载流程的自然副作用。若要主动把结果发回外部设备，需要另定义结果发送命令和桥内发送流程；这通常仍可使用原UART引脚，但不属于本稿已完成的功能。

## 10. 外部总体 IO：仍为原来的7根

| 顶层引脚 | 方向 | 位宽 | 新版连接/含义 |
|---|---|---:|---|
| sys_clk | 输入 | 1 | 板载晶振 → clock_unit |
| rst_n_in | 输入 | 1 | 外部复位 → clock_unit |
| uart_rx | 输入 | 1 | 外部UART存储模块TX → image_bridge |
| uart_tx | 输出 | 1 | image_bridge → 外部UART存储模块RX，主动读命令或协议确认 |
| led_ready | 输出 | 1 | 桥可接受新的加载控制，具体状态语义需随改造更新说明 |
| led_busy | 输出 | 1 | 桥正在进行外部通信/加载事务，不是CNN busy |
| led_error | 输出 | 1 | 桥故障或CNN存储故障 |

合计3输入、4输出，仍为7位。公共地、电源和JTAG等专用配置连接不计入这7个RTL端口；UART两端需匹配电平、波特率和帧格式。

串口对端由电脑换成外部存储模块，物理RX/TX方向没有变化。桥内新增MMIO、加载状态寄存器及控制线都留在FPGA内部，不引出封装。

如果设备强制要求额外RTS/CTS、唤醒或专用复位脚，就不能再无条件保证7根IO。本稿的7根IO前提是：设备可以用现有TX/RX完成通信、就绪协调和必要的包级流量控制。

原LED组合逻辑可以继续引用 `bridge_ready / bridge_busy / bridge_error / cnn_mem_fault`，但自动模式下桥状态含义需相应定义。特别是led_ready仍不代表模型完整、CNN完成或身份识别成功。

## 11. 修改范围清单

| 文件/部分 | 需要的改动 | 不应混淆的边界 |
|---|---|---|
| 新版顶层集成文件 | 新增bridge_mmio分支、设备选择和读回选择，连接桥的新端口 | 原六模块数量不变 |
| CPU地址译码集成版本 | 接受加载器地址，并保留CNN和SRAM原有合法性检查 | 不是只改顶层就够，也不是给Control增加状态引脚 |
| image_bridge集成版本 | 新MMIO寄存器、UART自动读取、计数校验及完成状态 | 需要实际新增逻辑，旧被动桥不能直接冒充 |
| CPU固定固件/初始化文件 | 初始化、按段启动加载、轮询错误、启动CNN、处理结果 | 固件在板内自动运行，不是运行时电脑软件 |
| IMEM、CNN、datasram | 原接口与主要逻辑可保留，核对容量和时序 | 不重加外置SRAM仲裁器，不改IMEM为在线下载 |
