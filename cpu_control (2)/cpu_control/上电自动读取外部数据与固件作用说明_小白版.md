# 上电自动读取外部数据与“固件配合”的含义（小白版）

日期：2026-10-08。目标：**设备上电后自动取得外部存储的数据，自动交给 CNN 处理，运行时不需要电脑控制。**

本说明继续以原六模块为基础，不重新启用已经放弃的 IMEM 在线下载方案。本次没有修改 RTL。外部存储器型号和接口尚未确定，文中分别说明不同情况，不能把尚未选定的设备当成已有硬件。

## 1. 先直接回答你的疑问

**不是 Verilog 不能实现这些功能，而是当前交付的 RTL 尚未把“自动读取、确认完整、自动启动计算”整套流程实现完。**

Verilog 可以描述一个控制电路，让它上电后依次做这些事：

```text
等待外部设备就绪 → 发读取请求 → 接收数据 → 写SRAM
→ 检查数据完整 → 配置CNN → 启动计算 → 等待完成 → 处理结果
```

这类按步骤推进的电路通常叫“状态机”。当前 UART 图像桥内部已经有收包、校验、访存、回复状态机，但它的职责只到这些动作，并没有包含上述完整业务流程。

之前写“需要固件配合”，意思是：**现有 CPU 可以通过执行 IMEM 中的程序，完成初始化、等待数据就绪、配置 CNN 和检查结果；但这份完整应用程序还没有交付。**

我之前将“电脑上传”和“软件交接”作为例子，容易让你理解成必须由电脑上的软件指挥。实际并非如此：**固件可以在板内自动运行，完全不需要电脑在线。**

## 2. Verilog 电路、CPU 固件、电脑软件，分别是什么

| 名称 | 在哪里 | 做什么 | 工作时必须连电脑吗 |
|---|---|---|---|
| Verilog 描述的硬件电路 | FPGA 内部 | 接收串口、访问 RAM、执行指令、计算 CNN、实现控制状态机等 | 不需要 |
| CPU 固件 | 指令放在 IMEM，由 cpu_core 执行 | 按程序初始化、调度、查询状态、判断错误 | 不需要 |
| 电脑上的发送/调试软件 | 外部电脑 | 手动或自动发送数据包、看结果、调试 | 只有采用电脑作为运行时数据源时才需要 |

可以用“工厂”理解：

- Verilog 定义工厂里有哪些机器，以及线路如何连接。
- 固件是放在工厂内部的工作流程，由 CPU 这台机器自动执行。
- 电脑可以是调试工具或外部供货方，但不必一直留在系统里。

CPU 硬件本身负责执行“加载、存储、判断、跳转”等指令。它不会在没有程序的情况下，自己知道哪块地址是图像、何时启动 CNN。

同样，UART 硬件能接收字节，不代表它自己知道“这次应该去外部存储器的哪个位置读取多少数据”。这些决策必须由固件或硬件状态机之一明确提供。

**“自动运行”与“由软件实现”不冲突；真正需要决定的是，自动流程由 CPU 固件执行，还是由额外的硬件状态机执行。**

## 3. 为什么前面的“资料传完”步骤需要交接

问题的实质不是“要不要电脑软件”，而是两个模块必须交换一个事实：

> 负责搬数据的一方，怎样告诉负责启动计算的一方：这轮输入已经完整、正确，并且真正写入 SRAM？

假设一份输入要分成100个包：

- 第1包收到，不代表全部输入已经收到。
- 最后一个串口字节收到，不代表最后一次 SRAM 写入已经完成。
- 一整张图像收到，也不代表权重、参数和任务表已经准备好。
- UART暂时安静，不代表数据结束，也可能只是外部设备暂时停顿。

如果没有交接规则，CPU 或控制器可能过早启动 CNN，让它读到旧数据、缺失数据或只写了一半的任务表。

交接可以由以下方式实现：

| 方式 | 例子 | 是否必须人工操作 |
|---|---|---|
| 软件协议 | 加载器发布已完成状态，CPU固件轮询确认 | 否，全自动 |
| 硬件握手 | 加载器输出 `load_done`，控制状态机确认后推进 | 否，全自动 |
| 混合方式 | 硬件锁存完成状态，CPU读取状态寄存器后启动CNN | 否，全自动 |

因此你可以取消“电脑来通知CPU”的安排，但仍需要保留“数据已经准备好”的确认机制。

`load_done` 只是这里用于讲解的拟议信号，**当前 image_bridge 并没有这个整批加载完成出口**。如果采用它，还要定义谁接收、怎样保持到被确认、下一轮何时清除，以及失败时如何禁止启动。

## 4. “UART 从外部存储器读取”需要先分清存储器种类

UART是一种设备之间传字节的接口，不专属于电脑。它也可以连接另一块控制板或带串口协议的存储模块。UART的基本TX/RX通信机制可参见 [Microchip UART说明](https://www.microchip.com/en-us/products/microcontrollers/8-bit-mcus/peripherals/communication-connectivity/uart)。

但**存储器不一定使用UART接口**。例如Winbond的W25X/W25Q系列串行Flash使用SPI系列接口，其时钟、片选和数据线不是UART的TX/RX，不能直接当成串口相连。参见 [Winbond串行Flash接口说明](https://www.winbond.com/productResource-files/DA05-0006.pdf)。

### 情况A：外部是带UART协议的模块，或另一块控制板

这种情况下，保留UART是合理的：

```text
外部存储器 → 外部模块内的读取控制器 → UART
                                             ↓
                                 FPGA接收/加载逻辑 → datasram
```

外部模块里面有人负责真正访问存储芯片；这里的“有人”可以是另一个硬件控制器，也可以是外部微控制器的固件，不是必须有电脑。

两种运行方式都可以：

1. **外部自动发送。** 外部模块上电就按约定发送数据，FPGA接收并确认。
2. **FPGA主动请求。** FPGA通过TX发送外部模块支持的读命令、地址和长度，外部模块通过RX返回数据。

必须明确是哪一种，双方还要约定帧格式、设备就绪、丢包/超时、确认与重发规则。

如果外部模块主动发送的内容完全符合现有IMIO分块协议，它可以替代之前电脑的发送角色，原桥的收包/写SRAM功能有机会直接复用。但整批完成通知、自动运行固件和上电先后协调仍需补齐。

如果外部模块使用自己的读命令和回复格式，就要改写或新增相应协议控制；“同为UART”不代表两边应用协议兼容。

### 情况B：外部是需要直接连接的SPI Flash等存储芯片

应使用匹配芯片的存储接口控制器：

```text
外部SPI Flash ←→ FPGA内部SPI读取控制器
                              ↓
                         自动加载逻辑
                              ↓
                           datasram
```

此时是FPGA主动发命令、地址和时钟读Flash，UART不是这条存储访问链路的必要环节。

原有图像桥可以保留作调试接口，也可以在独立版本中改造成该存储加载模块；若要保持六个大模块的组织，可以把存储读取控制器放在数据加载模块内部。但不能仅换个模块名字，就认为现有UART电路已经变成Flash控制器。

如果是SD卡，还要区分“按固定扇区读取预置数据”和“读取文件系统里的某个文件”，两者需要的控制工作不同。最终方案必须根据具体器件、接线和数据组织确定，本说明不把它们当作同一种接口实现。

若外部存储本身是易失性RAM，还要回答上电后数据由谁装进去；它不能凭空成为持久保存图像和模型的数据源。

## 5. 当前提供的UART电路到底能做什么

我核对了 [image_bridge.sv](rtl/soc/image_bridge.sv) 的实际状态机。

| 功能 | 当前实现情况 |
|---|---|
| 接收外部发送的IMIO读写请求 | 已有 |
| 校验每包CRC、长度和地址范围 | 已有 |
| 把包内数据写入共享SRAM | 已有 |
| 按外部请求读回SRAM并回复 | 已有 |
| 上电主动向外部存储模块发读命令 | 没有 |
| 按外部存储芯片协议产生读时序 | 没有 |
| 识别整份图像/模型资料已经加载齐全 | 没有完整业务机制 |
| 数据加载完成后自动配置并启动CNN | 没有完整业务机制 |

当前复位后进入的是 `RECEIVE`，等待外部发包。TX主要用于回复这些包，不是一个已经可供CPU任意发送存储读取命令的串口寄存器外设。

另一个容易混淆的地方：现有协议的“读SRAM”指**外部设备要求FPGA把内部SRAM的数据返回去**，不是“FPGA主动读外部存储器”。方向相反。

所以，如果两边上电后都在等对方先发数据，就会一直等下去。必须设计一个明确的发起者和上电启动流程。

## 6. 保留CPU的推荐方案：硬件自动加载，固定固件自动调度

结合现有六模块，建议先采用：

**外部接口/加载状态机负责把资料自动搬进SRAM，CPU运行预先放好的固定固件，确认资料就绪后自动驱动CNN。**

这样不需要运行时电脑，也不需要修改IMEM为可写，更不需要前面已经放弃的独立程序下载串口。

```text
                         clock_unit
                       给各模块提供时钟和复位

预装程序的IMEM ── 指令 ──→ CPU
                            │ 读取加载状态；配置/查询CNN
                            ▼
                           CNN
                            ↕ mem_*
外部存储/模块 → 自动数据加载模块 ↔ datasram
                   │            ↑
                   └─完成状态── CPU通过约定接口读取
```

图中的自动数据加载模块，可以在 `image_bridge` 的独立改造版本里实现；其内部使用UART还是SPI，取决于上一节的外部设备类型。

自动加载仍可使用现有 `io_mem_*` 写入datasram，保留70位请求、35位返回和error语义，不需要重加旧外置SRAM仲裁器。CNN原生 `mem_*` 和CPU A口也可以保持各自现有用途。

CPU读取加载状态的接口要正式定义。可以是约定的数据区，也可以是新增可读状态寄存器；**当前CPU没有现成的 `load_done` 输入或通用加载器MMIO映射，不能只画一根线到Control就算完成。** 若新增寄存器，需要相应地址译码和接线；若用SRAM通信区，需要处理初始化、完成提交及访问冲突。

当前datasram对A/B同周期访问同一字且任一方写入会报B侧错误，因此不能忽略CPU轮询和加载器写完成标记之间的冲突。需要设计明确的交接与重试/访问安排，或选择不占用同一RAM字的状态寄存器接口。

## 7. 按六个模块，上电后应当自动怎样走

下面是目标流程，包含仍需实现的加载控制和固件，不是当前代码已经完成的整机行为。

| 步骤 | 模块 | 自动执行的动作 |
|---|---|---|
| 1 | clock_unit | 提供公共时钟，按规则释放系统复位 |
| 2 | IMEM、cpu_core | CPU开始运行预装固定程序，初始化必要状态，进入等待加载完成的流程 |
| 3 | 自动数据加载模块（图像桥改造） | 与外部模块确认就绪并发读请求，或等待约定的外部自动发送；直连Flash时执行相应读取时序 |
| 4 | 加载模块、datasram | 依次加载图像、必要权重/参数、任务描述符，等待每次存储访问成功完成 |
| 5 | 加载模块、cpu_core | 校验整批数据，发布可靠完成状态；CPU自动确认，失败则不启动CNN |
| 6 | cpu_core、CNN | CPU用SW写QUEUE_BASE、TASK_COUNT，再写CONTROL=`0x3D`启动队列 |
| 7 | CNN、datasram | CNN自行取任务、读取数据、计算，并写回结果 |
| 8 | cpu_core、CNN | CPU轮询STATUS，处理完成、ERROR和超时 |
| 9 | cpu_core及选定输出通道 | 按目标显示、发送、保存或继续处理结果，随后安排下一轮 |

过程中IMEM持续提供CPU指令，clock_unit持续提供时钟。CNN数据仍直接在CNN与datasram之间流动，不需要每个像素经过CPU。

也可以用硬件加载完成后再释放CPU的方式安排启动，但那会增加复位分工。对当前讨论，固定固件等待有效加载状态即可表达自动流程，不必因此重新设计CPU时钟或IMEM下载口。

CPU初始化与外部加载必须协调：CPU不能在加载器写完图像后又清空那块区域。可以先完成CPU初始化再允许加载，或把初始化区域与加载区严格分开，并在协议中明确。

## 8. 如果我连CPU固件都不想写，可不可以

可以把调度流程也写成Verilog状态机，例如：

```text
复位 → 加载 → 校验 → 写队列地址 → 写任务数 → 写启动寄存器
→ 轮询完成 → 处理结果 → 下一轮
```

但这相当于用一个硬件控制器承担原本CPU程序的调度工作，需要真正新增相应逻辑，不是现有CPU会自动获得这些行为。

还要解决CNN寄存器端口由谁驱动：目前只有CPU连接CNN MMIO。若新硬件控制器也要写它，必须明确单一控制者，或提供互斥的选择和完整响应路由，不能把两个输出直接并接到同一组信号。CPU自身仍在运行时，也不能随意丢弃它的请求，因为原CPU MMIO是零等待接口。

这种方案能自动运行，但会增加系统控制改造；如果项目本来就需要CPU承担控制功能，让CPU执行一份固定固件通常更直接。**无需电脑，是运行方式要求；完全不用CPU程序，是另一个更强的设计要求。**

## 9. 对当前六模块，需要补齐哪些部分

| 部分 | 为实现无人控制的上电运行，需要什么 |
|---|---|
| clock_unit | 原时钟复位原则可保留，另外考虑外部设备比FPGA晚就绪的等待流程 |
| imem_rom | 保留只读接口，实际提供可用的固定应用程序内容 |
| cpu_core | 原执行核心可保留；如采用新的加载状态寄存器，需补外围映射和接口连接 |
| image_bridge / 数据加载模块 | 自动读取外部设备或接收其自动发送；完成批次计数、校验、错误处理与加载状态发布 |
| datasram | 保留共享存储和内部仲裁；冻结图像、参数、任务表、软件区及结果区布局，检查容量 |
| CNN | 沿用既有任务/MMIO协议；提供正确模型资料和描述符，验证目标运算及结果 |
| 外部存储设备 | 数据预先写好，协议和电气连接匹配，明确谁先发命令 |
| 结果输出 | 指定送到哪里、谁主动传、接收方如何确认；原图像桥不会自动推送结果 |

还要区分“FPGA上电配置”和“业务数据加载”：没有电脑时，板子也必须能自行完成FPGA配置，CPU程序初值要随实际配置流程准备好。业务外部存储是否与配置存储共用，需要根据板卡连线确定，不能默认共用后就能直接访问。

## 10. 自动加载不能只判断“收到了最后一个字节”

至少应把以下条件纳入本轮完成判定：

1. 知道本轮要加载哪些段、每段多长、目标SRAM地址是什么。
2. 每段都收全，格式/校验正确，地址不越界、不覆盖其他必要区域。
3. 最后一笔SRAM访问已经确认完成，且没有error或超时。
4. 图像、必要模型参数和任务表都可用，不把仅图像完成当成全部完成。
5. 完成状态保持到CPU或控制器确认，启动下一轮时按规则清除，避免旧状态误触发。

这些全部可以由Verilog实现，也可以一部分由固件承担；关键是职责明确，并且实际写出和验证相应逻辑。

外部文件也需要是CNN能理解的数据布局。串口或Flash加载器不会天然解码JPEG/PNG、整理模型权重或生成描述符；可以在设备出厂/准备资料时预先转换，也可以另行实现所需处理。运行时不需要电脑，不代表开发和预置数据时不能使用电脑工具。

## 11. 下一步由外部器件决定，当前不能直接承诺哪套接线

要落实电路，需确定：

- 外部设备的型号、接口及协议：UART模块、另一块控制板，还是直接连接的存储芯片。
- 数据从哪里开始、有多长、是固定布局还是文件、如何确认完整。
- 外部设备自动发送还是由FPGA主动请求，以及上电先后如何协调。
- 结果是返回外部模块、存到某处、显示，还是只在内部使用。

如果你说的是“另一块板从存储器读数据，再通过UART送来”，可以继续围绕现有UART通路做自动化；如果是“FPGA直接读一颗SPI Flash”，应设计存储读取接口，而不是坚持让UART直接接Flash。

本说明已经明确目标可以实现，但当前缺少的是自动读取控制、完整应用固件/状态交接以及器件协议选型，不是Verilog语言能力。当前六模块的小任务及UART仿真结果，也不能代替尚未实现的无人控制上电加载流程验收。
