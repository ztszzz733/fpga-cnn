# 8卷积共享2后处理：实现、验证与资源

## 已完成

2个3×3/DW3卷积和6个PW8卷积均已接入同一个共享后处理后端，复用现有2个后处理计算单元，仅新增2条8项寄存器FIFO。共享后端已接入生产CNN调度入口，不再只是上一版独立算子对试验。

所有生产算子的计算和数据复用代码保持不变；新增路由、排队与任务完成管理。SHARED_POST_STREAM默认1，设0可构建原独立后端。旧任务0/5/1等仍走存储路径；**要实际启用直连，需要加载软件规划产生的新合并任务6/7**。不会自动把既有MobileFaceNet模板改写成直连。

当前生产入口LATEST_OPERATORS=1时使用该共享后端；旧LATEST_OPERATORS=0入口保持独立方式。CNN仍为四图片上下文、每图一个在途任务；后端单独验证了8个物理卷积同时提交，不表示四帧调度器现在能同时发出8个图片任务。

## 排队与传输

```text
K3_0 / K3_1（也支持DW3） ─┐
PW8_0 … PW8_5            ├─ 首结果就绪的请求集合＋轮询选择 ─ FIFO0 ─ Post0 ─ 最终存储
                         └────────────────────────────── FIFO1 ─ Post1 ─ 最终存储
```

- 卷积可以先加载数据、计算；产生第一项结果后才申请后处理，避免加载期间提前占用后处理。
- 等待由每个物理卷积当前任务形成，每个卷积一次一个任务，不另外复制8套描述符FIFO。
- 在有首结果的卷积之间轮询分配。分配后，owner保持到整层最后一笔最终写响应完成；两路绝不混入不同任务的数据或参数。
- FIFO满时反压卷积。FIFO每项包含32位结果、32位元素位置、10位通道号，能够接收微块/通道交错的输出顺序。
- 卷积done只表示原始结果排空；对外合并任务done还要等待后处理、FIFO和最终写响应，下一层不能提前读取半成品。
- 不适合融合的任务由软件保留原始卷积和后处理两条任务；普通后处理与流式后处理共用同两套实例，Add仍独立。
- 当前是层级独占：一层处理中不切换owner，也暂不把卷积实例提前释放给下个任务。轮询公平针对等待中的卷积；有流式等待时优先预约空闲后处理，不宣称对无限任务流的跨类型公平。

## 软件与接口

软件入口`sw/conv_post_plan.py:plan_pair`在网络加载/提交前检查相邻算子、单消费者、形状/数量/通道匹配、地址范围和活跃输入/权重/参数重叠。通过则产生一条合并命令，否则返回原来的两条命令。硬件没有复制上一版每对算子的宽位尺寸乘法和完整合法性规划；仍检查FIFO/计数、后处理参数及运行错误，卷积自身检查保持。

规划函数要求**重定位后的绝对地址**。通用网络生成器还须重排合并后的任务编号、依赖和缓冲租约；这部分不能只删除原后处理行。本次四图两层测试已通过实际生成的新模板验证，但没有改写或重跑完整MobileFaceNet生成器。

现有CPU寄存器写入协议和640位模板格式保持。16个命令字中的合并格式：

| 字 | 含义 |
|---|---|
| 0 | 6：3×3/DW3＋后处理；7：PW8＋后处理 |
| 1、2 | 输入、权重；沿用原source_modes重定位 |
| 3 | 最终UINT8输出；沿用workspace重定位，租约也是最终输出 |
| 4 | 后处理参数绝对地址，5个32位字/通道 |
| 5 | 最终输出元素数量，软件预先计算 |
| 6、7、8、9、10、11 | 输入通道、宽、高、输出通道、步长、DW标志，沿用卷积含义 |
| 12 | 生产者虚拟INT32结果基地址，默认0xE0000000；必须不溢出、避开输入/权重；无需分配实际SRAM |
| 13、14 | 由现有调度器填入图片tag和帧槽 |

FIFO把虚拟结果地址转换为元素位置；虚拟地址不会发往真实存储。参数/输入/权重读取、最终结果写入仍走原存储接口。CPU不参与逐元素搬运。

## 功能验证

1. **10批、共80个卷积任务**：8个真实计算核并发，覆盖双后处理、只开一个后处理、混合普通卷积/普通后处理、DW3、步长2、非对齐、小块/大通道、即时响应、长写等待、FIFO满时清空重启、单端口停顿、后处理暂不可用。合并结果逐字节匹配128位整数参考；旧卷积原始结果和普通后处理同样核对。
2. **实际CNN MMIO入口的3个场景**：四张不同7×7×3小图，经3×3卷积（输出5×5×4）＋量化，再经1×1卷积（输出5×5×3）＋量化。合并为每图2命令，共8命令；旧存储形式每图4命令，共16命令。核对两层数据、输出tag/地址/长度、结果ACK、计数、缓冲释放及最终写排空。
3. **24项软件规划检查**：合法融合、多个消费者、关闭直连、Add/不支持组合、数量/通道/来源不匹配、输出别名、非法形状与地址溢出。
4. 当前完整SoC顶层语法/连接展开通过；不等于完整SoC执行仿真。GTKWave实际加载16根唯一控制信号通过。

同样的四图两层计算，存储形式接口读取5548字节、写入3500字节；融合形式读取2748字节、写入700字节，合计省5600字节，等于700个卷积结果×8字节中间读写。这里只统计算子端口流量，不是DDR实测事务字节。软件规划当前由PC侧Python函数生成，测试台模拟CPU写MMIO，不含CPU指令执行。

三个MMIO场景的等待模型不同（普通延迟、即时响应、强等待），其周期数不能直接拿来比较新旧加速率。本次目标是共享和正确性，不声称完整网络速度提升。

## 怎么看波形

先看[共享时间线](shared_timeline.png)：灰色是busy（含读数据等待），蓝色是真实MAC生效，橙色是首结果就绪但等待后处理，绿色/紫色细条分别表示持有Post0/Post1。下方两行表示两个后处理正在服务哪个卷积。主压力场景最多6个卷积同时等待，两条通路同时拥有任务53800周期。

这是特意延长存储写响应的压力测试，用于检查排队和反压，不是整网性能展示。任务是不同小特征图计算，不代表8张完整MobileFaceNet图片。

[放大控制图](shared_control_zoom.png)展示实际MAC、FIFO占用、后处理计算和最终写响应。寄存器FIFO入队并不等于最终结果已写回；看final_write_ack才是写响应，合并unit_done还要确认整个任务排空。

GTKWave入口：[shared_pool.gtkw](shared_pool.gtkw)，真实VCD：[shared_pool.vcd](shared_pool.vcd)。16个信号均只出现一次，按卷积/排队/FIFO/后处理/存储分色：

- unit_busy/work/done/error：位0/1为K3，位2～7为PW8，位8/9为Post。work的卷积位是MAC生效；Post位沿用写请求接受事件。
- waiting：8位等待集合；stream_jobs：8位合并任务集合。
- owned：两路有效；owner_id低3位是Post0来源，高3位是Post1来源。
- fifo_level低4位是FIFO0，高4位是FIFO1；fifo_push/pop每位对应一路。
- post_retire和final_write_ack每位对应一路，分别是直连计算结果生效、最终写响应。
- mem_valid/ready/response为10位存储端口控制，位映射同上。

PNG按每周期10ns（100MHz）条件换算，VCD也是10ns时钟；未验证板级频率。没有UART、真实DDR或112×112全网仿真，也不评估人脸识别准确率。
