# 给软件同学的交付需求：编译任务图，尽可能并行执行

日期：2026-11-16。配套：[存储侧需求](CNN存储侧需求_20261116.md)。

## 1. 交付目标

**给定一张完整任务图，例如包含50个卷积、后处理、Add等任务，软件在运行前生成并行执行计划。硬件按计划和真实完成条件执行，让没有依赖冲突的任务尽可能同时运行。**

必须支持：同一张图片内的独立任务并行，以及不同图片之间并行。网络变化时重新生成计划；同一网络的计划可重复用于后续图片，不要求所有图片到齐后才开始。

这里的“编译”是开发任务图规划工具，不是要求普通C编译器自动完成调度。50个是算子任务示例，展开后的搬运、分块命令可能更多；不要求找到数学上的全局最优方案。

## 2. 需要实现的功能

| 功能 | 必须实现什么 |
|---|---|
| 读取任务图 | 读取算子参数、输入输出张量和任务依赖；先支持明确格式的JSON，不强制第一版支持ONNX导入 |
| 检查可执行性 | 检查依赖无环、算子/尺寸/格式支持、地址范围、容量和队列限制；不支持就返回具体原因 |
| 找出并行任务 | 根据依赖图判断哪些任务可以同时执行，不能把全部任务简单排成单链 |
| 分配算子实例 | 根据硬件实例数和估计耗时绑定任务、安排优先级；硬件延迟变化后仍按完成条件推进 |
| 规划DDR和本地空间 | 分配图片、权重、中间结果地址及本地缓冲；按最后使用者安排复用，保留分支和残差需要的数据 |
| 生成分块与搬运 | 将能分块的任务拆成块，生成LOAD/RUN/STORE；安排当前块计算时准备后续数据，避免无意义的重复搬运 |
| 生成执行条件 | 每条命令带前置完成编号；必须覆盖数据就绪、实例可用和缓冲可复用条件，不能只按预计时间启动 |
| 生成可检查报告 | 输出任务分配、依赖、地址、缓冲峰值、预计执行顺序和瓶颈；实际运行后用事件记录画并行时间线 |

第一版分块先支持普通1×1、stride=1、完整输入/输出通道的空间分块；其他算子可先按整任务执行。不能擅自把输入通道拆开，跨块累加需要额外硬件支持。

## 3. 工具输入与输出接口

| 接口 | 输入 | 输出 |
|---|---|---|
| `build_plan()` | `task_graph.json`、`caps.json`、算子耗时/搬运代价配置 | `plan.bin`、`plan.json`、`memory_plan.json`；非法图返回具体原因 |
| `load_plan()` | 计划和权重/量化参数 | 装载成功/失败 |
| `submit_image()` | `epoch`、`frame_id`、图片DDR偏移、输出DDR偏移 | 已接受，或上下文/存储空间不足 |
| `get_result()` | `epoch`、`frame_id` | 未完成，或结果DDR偏移、字节数、错误状态 |
| `release_image()` | `epoch`、`frame_id` | 用户取走结果后释放图片上下文及工作区 |

### `task_graph.json`字段

| 对象 | 必须包含 |
|---|---|
| `tasks[]` | `task_id`、`op_type`、`inputs[]`、`output`、`params`、`depends_on[]` |
| `tensors[]` | `tensor_id`、`shape`、`dtype`、`layout`、`bytes`；权重/量化参数引用 |
| 网络输出 | 指定需要交付给用户的张量ID |

### `caps.json`字段

算子类型/实例ID/能力、图片上下文数、本地地址基址/可用容量/端口限制、DDR合法范围、搬运对齐、队列/依赖容量、协议版本。软件根据实际能力规划，不能写死资源数。

## 4. 执行计划与硬件接口

以下是**待实现的接口合同**，不是已有函数或物理寄存器。CNN同学需提供轻量计划执行器和实例命令入口；存储同学提供配套文档中的搬运/本地访问接口。

| API | 含义 |
|---|---|
| `hw_get_caps()` | 读取上述硬件能力 |
| `hw_load_plan(plan.bin)` | 装载或分批送入计划，检查版本和容量；未就绪命令不能阻塞所有其他可运行命令 |
| `hw_submit_frame(epoch, frame_id, address_map)` | 为图片设置DDR/本地地址映射并启动计划 |
| `hw_poll_event()` | 取完成/错误事件，用于结果管理和时间线；CPU不必在每个块切换时及时响应才能继续计算 |

每条计划命令包含：

| 字段 | 类型 | 含义 |
|---|---|---|
| `command_id` | uint32 | 计划内唯一编号；LOAD/RUN/STORE统一编号 |
| `kind` | uint32 | 0=LOAD、1=RUN、2=STORE |
| `depends_on[]` | uint32数组 | 必须先成功完成的命令；缓冲复用依赖也放在这里 |
| `priority` | uint32 | 同时就绪时的执行优先级，数值越小越优先 |
| `payload` | 按类型确定 | 下表内容 |

| 命令 | `payload`必需字段 |
|---|---|
| LOAD/STORE | `ddr_ref`、`local_ref`、`bytes`；引用由图片地址映射解析为实际偏移 |
| RUN | `unit_id`、`descriptor[16]`；地址引用按该图片映射后生成现有算子描述符 |

RUN描述符沿用当前格式：字0类型，1输入A地址，2权重/输入B地址，3输出地址，4后处理参数地址，5元素数，6通道数，7/8宽高，9输出通道数（Pad为填充值低8位），10步长，11低1位depthwise；12～15在新RUN接口中保留填0。

当前类型：0=K3/DW3、1=Post、2=Add、4=Pad、5=普通1×1。DDR地址使用逻辑偏移；本地地址使用 `local_base + local_offset`。当前未启用DW7。

完成事件字段：`epoch/frame_id/command_id/kind/status`，均为uint32；`status=0`成功。相同计划用于多张图时command_id会重复，必须用三元组`epoch+frame_id+command_id`区分。LOAD完成才可读本地输入；RUN完成才可消费本地结果；STORE完成及PS缓存维护完成后才能读取DDR结果。

硬件只需按依赖、实例忙闲和队列容量执行，不要求它重新寻找最优网络方案。超出硬件依赖/命令容量时，编译器必须拒绝或采用硬件明确支持的分批方式，不能把未装入的依赖当成完成。

## 5. 必须通过的验收

1. 提供约50个算子任务的测试图，包含分支、汇合、多个相同算子和数据复用；再提供一张顺序不同的合法任务图，改变网络不修改RTL。
2. 结果与整数参考逐元素一致；错误依赖、空间不足、提前覆盖能被发现。
3. 时间线能看到同一张图片的两个独立任务在不同实例上实际工作；也能看到两张图片交错工作。仅busy重叠不算。
4. 能看到LOAD与其他缓冲上的RUN实际重叠；注入DDR延迟后依然正确。在约定的CPU最大服务间隔及队列容量内，不依赖CPU逐块响应才能继续，也不丢完成记录；报告允许的服务间隔。
5. 与相同硬件、数据、存储条件下的串行计划比较总周期、DDR字节和缓冲峰值；报告收益，不预先承诺加速倍数。

## 6. 当前代码必须补齐的部分

当前生产配置是K3×2、PW8×6、Post×2、Add×1、Pad×1，4张图片上下文，392KiB共享本地RAM。当前硬件每张图片一次只允许一个活动任务，不能据此宣称已完成本目标。

- **软件同学：**交付任务图规划工具、上述API、计划文件和测试图。
- **CNN同学：**新增按实例执行和依赖驱动的计划执行入口，解除同图单活动任务限制，同时保证缓冲与结果正确。
- **存储同学：**交付显式搬运、本地窗口、计算/搬运重叠及带身份的完成事件。

现有20字模板、256步和每图4槽仅作为兼容路径；新任务图计划不能不经适配直接塞入旧模板。此次只重写文档，不修改代码或启动仿真。
