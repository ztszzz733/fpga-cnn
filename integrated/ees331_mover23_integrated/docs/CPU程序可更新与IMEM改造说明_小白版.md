# CPU 程序可更新与 IMEM 改造说明（小白版）

日期：2026-10-08。依据：当前 CPU_CONTROL 工程源码。

**这是一份设计说明。本次没有修改 RTL，也没有实现下面提出的程序下载功能。**

## 1. 先回答你的三个问题

**第一，当前程序写入 IMEM 后，上电运行期间能不能换？**

按现在的硬件接口，不能通过已有串口或 CPU 普通写内存指令改写 IMEM。它没有运行时写入口。要换程序，目前需要改变初始化内容，再走仿真加载或 FPGA 配置更新流程。

但这不等于 CPU 只能永远运行同一个程序。**CPU 已经是执行程序的处理器；当前缺少的是“运行中的板子接收新程序并重启执行”的下载机制。**

**第二，能不能做成上电后可下载程序？**

可以。把 IMEM 增加为可写的指令存储器，再配下载控制和启动控制即可。第一版可以保留现有 CPU 的指令集、Control C1 和生产 Datapath，主要修改外围模块与接线。

**第三，是不是 IMEM 接两根线到 IO 就行？**

外部通信可以只用 UART 的 RX/TX 两根信号线，而且本工程已经有这两根线，通常无需再加两根 FPGA 信号引脚。但内部不能只连两根线：还要把串行数据翻译成地址、指令数据、写入使能，检查是否收全，并控制 CPU 什么时候停、什么时候重新运行。实际串口连接还需要公共地以及匹配的电平。

## 2. 用“读菜谱”理解 CPU、IMEM 和 CNN

可以这样类比：

| 工程里的东西 | 类比 | 实际作用 |
|---|---|---|
| CPU | 按菜谱做事的人 | 一条条执行指令，读写数据、判断、跳转、控制 CNN |
| IMEM | 菜谱本 | 保存 CPU 要执行的机器指令 |
| 数据 SRAM | 工作台 | 保存图像、权重、描述符、变量和结果 |
| CNN | 专门做某类工序的机器 | 按任务描述符执行已经支持的计算操作 |
| UART 下载逻辑 | 收件员 | 从电脑接收内容，再写到指定存储器 |

现在的 CPU 已经会读不同菜谱。问题是现有“收件员”只能把东西放到工作台，还不会更换菜谱本。

CNN 的“可编程”主要是：用任务描述符指定支持的算子、地址、尺寸、参数和执行关系。CPU 的“可编程”则是：用机器指令描述整个控制流程。两者可以同时存在。

CNN 任务可配置不等于任意新算子都不用改硬件；同样，CPU 换程序也不会自动增加原本不支持的指令。

## 3. 现在的 IMEM 到底是什么样

源码是 [imem_rom.sv](../partners/datapath/delivery/rtl/soc_memory/imem_rom.sv)，默认容量 64 KiB，可以放 16,384 条 32 位指令。

它对外只有这些功能信号：

| 信号 | 作用 |
|---|---|
| `imem_addr` | CPU 告诉 IMEM：“我要读这个地址” |
| `imem_re` | CPU 发出取指请求 |
| `imem_rdata` | IMEM 返回一条 32 位指令 |
| `clk / rst_n` | 时钟和复位 |

**没有写地址、写数据、写使能，也没有串口输入。** 名称里的 ROM 在这里表示当前接口只读，不是在说程序一辈子不能改变。

当前代码用下面的方式初始化：

```systemverilog
initial begin
    if (INIT_FILE != "") $readmemh(INIT_FILE, mem);
end
```

要分清三个场景：

- **仿真：**仿真启动时读取指定文件。测试代码直接给 `mem[...]` 赋值，也只是仿真工具装载内容，不是已经存在板级下载通路。
- **FPGA 配置：**Vivado 支持用这类文件初始化块存储器。成功综合和实现后，初始化数据可以随 FPGA 配置装入；FPGA 运行时不会自己去电脑上重新读取那个文件。本工程尚未完成板级综合映射验收。见 [AMD UG901：用文件初始化存储器](https://docs.amd.com/r/en-US/ug901-vivado-synthesis/Loading-Memory-Contents-With-File-I/O-Tasks)。
- **按复位键：**当前复位只把 IMEM 的读输出设为 NOP，不重新执行 `$readmemh`，也不会因此重装一份新程序。重新配置 FPGA 与普通逻辑复位是两回事。

此外，`IMEM_INIT_FILE` 默认是空字符串，不能理解为“已经放好一个能做人脸识别的程序”。正式应用仍需准备程序内容。

## 4. 为什么已有 UART 不能直接下载 CPU 程序

现在实际通路是：

```text
电脑 → UART RX → image_bridge → datasram → 图像/权重/任务/数据

CPU  → 独立取指通路 → imem_rom → CPU 指令
```

两条通路没有连接。现有 UART 协议只有“读 SRAM”和“写 SRAM”，参见 [UART 协议](uart_image_bridge_protocol.md)。

特别容易弄混的一点：**IMEM 和数据 SRAM 的默认起始地址都为 0，但它们是两块不同的存储器。** 现在串口往地址 0 写入机器码，只会写数据 SRAM，不会写入 IMEM。CPU 也不会因为那些字节看起来像指令，就改从数据 SRAM 取指。

因此需要在下载协议中明确“这是 CPU 程序，目标是 IMEM”，不能只沿用地址数字来区分。

## 5. 推荐第一版：停下来下载，校验后从头运行

对当前工程，建议先做“可以换程序，但换程序时停止应用”的方案。它不要求 CPU 一边执行旧程序，一边修改自己正在读取的指令。

目标通路如下；下面都是**拟议改造**：

```text
                         ┌→ 原数据通路 → datasram
电脑 ↔ 现有 UART RX/TX ↔ 下载/图像桥
                         └→ 新程序写入口 → 可写 IMEM
                                               ↓
                                      原取指接口 → CPU

下载状态 → 应用复位/启动控制 → CPU、CNN及必要的访存控制状态
```

IMEM 可以使用 FPGA 内部 RAM，让一个访问入口保持 CPU 原有的同步取指，另一个入口用于下载。具体用双端口 RAM，还是停机时复用一个端口，要在实现时选择；**关键是 CPU 看到的取指时序仍然保持固定一拍。**

一轮下载建议这样工作：

1. **进入下载状态。** 停止旧应用，复位 CPU，停止并清除旧 CNN 任务和相关在途访存状态；确认进入停机状态后，才接受程序写入。
2. **接收程序。** 电脑分块发送机器码，下载器检查目标、地址、长度和每包校验，再写 IMEM。
3. **检查是否完整。** 检查声明的程序长度、所有数据是否到齐、整个程序的校验结果。可以读回核对；不能只因为收到最后一包就认为成功。
4. **准备运行环境。** 装好新程序需要的数据 SRAM 初值、栈和 CNN 参数，或由新程序启动代码初始化。旧数据不会自动变成适合新程序的数据。
5. **明确启动。** 只有本轮程序完整且校验通过，才接受启动命令；同步释放应用复位，CPU 从约定入口开始运行。

第一版可固定程序从 IMEM 地址 0 装入，从当前 `RESET_PC=0` 开始执行，避免同时增加可变入口 PC。若以后要支持程序装在任意地址并从任意入口运行，还需要入口地址检查和 PC 启动机制。

下载失败、漏包、中断或校验不通过时，CPU 应继续停住，允许重新下载。单份 IMEM 下载会覆盖旧程序，**不能承诺失败后自动回到旧程序**；若需要回退，才考虑两份程序存储和切换机制。

## 6. 为什么不能把全系统一直按在复位里

现在 [板级顶层](../rtl/soc/face_soc_top.sv) 让 CPU、CNN、UART 桥等模块共用 `rst_n`。如果为了停 CPU 而一直拉低这根公共复位，UART 接收器也停止工作，新程序根本收不进来。

需要区分两种控制：

| 控制 | 哪些东西要停 | 哪些东西要工作 |
|---|---|---|
| 外部系统复位 | 所有控制逻辑回到初始状态 | 释放后下载器恢复工作 |
| 下载期间的应用复位 | CPU、CNN，以及需要清除的访存状态 | UART、下载状态机和 IMEM 写入口继续工作 |

可以让下载控制逻辑输出“应用保持复位”的请求，在顶层/复位模块完成连接。CPU 继续使用它已有的 `rst_n` 输入，原则上不需要改它内部的 Control 或 Datapath。

但不能随意用一个组合门拼出新复位就结束：必须保证复位持续足够时钟周期、释放与时钟同步、CPU 流水线和取指缓冲已清空、旧 CNN 请求不会继续写内存。尤其当前 CPU 内部多个状态采用同步复位，需要真正经历有效复位时钟沿。

只拉低 `imem_re` 或只暂停 PC 也不等于停住整个 CPU：流水线里已经进入的指令仍可能执行访存。第一版用应用复位实现“停止并从头开始”，比引入完整暂停/续跑机制更适合当前接口。

## 7. 哪些模块要改，哪些可以保持

以下是建议的改造边界，不是已经完成的修改：

| 部分 | 是否需要动 | 具体内容 |
|---|---|---|
| IMEM 模块 | 需要 | 新增下载写入口、地址/写入规则，保持 CPU 一拍取指；可另建可写版本，保留原 ROM |
| `image_bridge` 或独立下载控制模块 | 需要 | 区分程序与数据下载，增加写 IMEM、校验、停止/启动状态控制 |
| 顶层 `face_soc_top` | 需要 | 连接下载写口，区分系统复位与应用复位，更新状态输出含义 |
| `clock_unit` 或配套复位控制 | 需要配合 | UART 能运行时 CPU 可保持复位，启动时同步释放 |
| CPU Control C1 | 可保持 | 指令译码、冒险处理不因下载程序而改变 |
| 生产 Datapath / `fetch_adapter` | 可保持，前提是接口时序不变 | 继续固定一拍取指，通过原复位入口重新从 `RESET_PC` 运行 |
| `datasram` | 不必为了写 IMEM而新增外置仲裁器 | 确认下载切换时清除在途状态；继续保存数据，复位不等于清空数据 |
| CNN 算法 RTL / MMIO 协议 | 可保持 | 通过顶层停止/复位旧任务；CPU仍用原寄存器协议驱动CNN |
| 电脑端 Python 工具 | 需要 | 发送程序包、整体验证、查询状态、发启动命令 |
| 软件构建流程 | 需要 | 把程序转成 CPU 支持的机器码，约定装载地址、入口和数据初始化 |
| 编译清单、测试、文档 | 需要 | 加入新模块，验证下载/复位/旧数据协议兼容性 |

可以把下载状态机并入现有图像桥，以维持六个平级大模块的结构；也可以用内部子模块组织实现。这里还没有决定最终端口名称或协议编码。

本项目原始交付源码应继续保留。若实施，可新增可写 IMEM 模块并在顶层选用，避免覆盖伙伴原始 `imem_rom.sv`。

## 8. “两根线”真正能解决什么

UART 的两根线承载的是按时间排列的比特流，例如“第一个字节、第二个字节……”。IMEM 需要的却是：“在某个时钟沿，把这 32 位数据写到这个地址”。

所以真正的关系是：

```text
外部：RX / TX 两根信号线
           ↓ 接收、解析、校验、拼字
内部：目标选择 + 写地址 + 写数据 + 写使能 + 完成/错误
           ↓
         IMEM
```

内部这些线不需要全部引到 FPGA 外部，它们只在模块之间连接。也不建议为程序再复制一套 UART，现有串口可以通过命令类型复用。

未来协议可以在概念上提供“开始下载、写程序块、读回/校验、启动、查询状态”等操作。**这些不是现有 IMIO v1 已支持的命令**，不能现在就按这些名字发送并期待硬件响应。新协议需要兼容已有图像上传，明确版本或新操作码；序号、重复包、错误回复和超时后的状态也要规定。

## 9. 换程序之后，断电能不能保留

如果只是 UART 写 FPGA 内部 RAM，新的程序内容不因下载而自动存入非易失存储。断电、重新配置后，不能指望它仍是刚才下载的版本。

第一版建议明确采用：**上电后先等待下载，下载校验通过后再运行。** 下载成功标志在系统复位时清除，重新进入等待状态；这是拟议的启动策略，不是当前已实现行为。

若希望“下次上电自动运行上次更新的程序”，需要增加非易失保存和启动加载方案，例如板上 Flash 及其控制/引导逻辑，或更新包含程序初值的 FPGA 配置。当前不能凭空假定板子有什么 Flash、怎样连接。

也不必认为每次更换初始程序都一定要重新做全部布局布线：AMD 提供 UpdateMEM，将软件数据与已有位流中的块 RAM 映射结合来生成更新后的配置文件。但需要正确的实现结果、存储映射等条件，本工程尚未建立该流程；它仍属于更新配置文件，不等于 UART 在线改写 IMEM。见 [AMD UG1580：Using UpdateMEM](https://docs.amd.com/r/2023.1-English/ug1580-updatemem/Using-UpdateMEM)。

## 10. CNN 已可编程，CPU 是否一定要马上增加程序下载

**不一定。** 可以先给 CPU 放一个通用控制程序：等待数据准备好 → 读取约定配置 → 写 CNN 队列寄存器 → 启动 CNN → 查询完成 → 提供结果。

这时更换图像、权重、任务描述符，甚至在已支持算子的范围内改变网络任务，未必需要更换 CPU 程序。前提是通用程序本身写得足够灵活，并且定义好双方共享的数据和控制格式。目前完整应用固件及这些地址约定尚未完成。

可以按需求选择：

| 你希望改变什么 | 主要改哪里 |
|---|---|
| 换图像、权重、合法的 CNN 任务序列 | 数据 SRAM 内容，配合已有通用 CPU 控制程序 |
| 改 CPU 处理逻辑、调度流程、控制策略 | CPU 程序；频繁调试时，UART 程序下载会很方便 |
| 让 CNN 支持当前没有实现的新硬件算子 | CNN RTL及相关软件，不一定只改任务表就够 |
| 让 CPU 支持当前没有的指令或异常功能 | CPU RTL及软件，不是换一份程序即可 |

当前 CPU 只支持已约定的 RV32I 指令范围，没有乘除法扩展、CSR、特权、压缩和完整异常机制。因此电脑上的 C 源码不能原样传入运行；需要适配该 CPU 的编译/汇编、链接和启动代码。即使文件叫 `.bin`，也要确认内容是正确的指令字节流，入口、大小端和存储布局都匹配；带文件头的 ELF 也不能未经处理直接当指令灌入。

## 11. 实施后怎样证明“真的可更新”

后续实现至少要验证这些实际行为：

1. 同一份 FPGA 硬件配置下，通过 UART 先装程序 A，再装程序 B，分别得到不同且正确的运行结果；第二次不重新配置 FPGA。
2. 下载过程中 CPU 不取有效指令、不发数据写或 MMIO 请求，旧 CNN 任务不再继续写数据。
3. 程序漏包、错误校验、越界、非对齐或超时后不会启动半份程序；能够重新下载恢复。
4. 只有完整校验通过才能启动，启动后 PC 和流水线状态正确，IMEM 仍符合原有一拍取指。
5. 原有图像 SRAM 上传与 CNN 联调继续通过，系统复位和应用重启的行为与说明一致。

当前做的是源码核对与方案说明，没有新增程序下载测试结果。此前 CPU/CNN 小任务及 UART 数据传输仿真通过，不能用来证明尚未实现的 IMEM 在线下载已经可用。

建议先实现上面这版“复用串口、停应用、写 IMEM、完整校验、从 0 重启”。它能够满足上电后更换 CPU 程序的需求，同时保留你现有的 Control C1 与 Datapath 接口。
