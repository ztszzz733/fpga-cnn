# NVDLA＋Vicuna 2 联合 SoC 接入

目标：原 RV32I 主 CPU 通过软件选择专用或可编程计算路径。NVDLA 执行已有卷积、SDP、池化；CNN 内的 CV32E40X 小控制核执行可替换的向量程序，驱动 Vicuna 2 完成补充算子。两个引擎共享 DATASRAM，任务依赖目前由主 CPU 软件维护。

本次新增入口为 `rtl/hybrid/face_soc_hybrid_top.sv`，本地源文件清单为 `rtl/filelists/system_hybrid_local.f`。旧 NVDLA、NEureka 和原 CNN 入口仍各自独立，不能混选为同一顶层。

**2026-10-13：三项联合 SoC 小测试 PASS，接口短回归 PASS。** 正式运行目录为 `build/runs/20261013_211215_hybrid_soc`；结果和波形见 [交付说明](../deliverables/hybrid_soc/README.md)。FP32 指令顺序的已知限制见下文。

## 模块结构

顶层仍为 CPU、CNN、DATASRAM、IMEM、IMAGE_BRIDGE、CLOCK 六个实例。CNN 内新增命令接口、可编程子系统和 SRAM 存储桥，保留真实 NVDLA。

```text
主 IMEM → 原 RV32I CPU → CNN 命令寄存器
                            ├─ CSB 适配 → NVDLA → SRAM 客户端 0/1
                            └─ 任务/程序寄存器 → CV32E40X＋Vicuna 2
                                                  ↓ SRAM 客户端 2
                                      DATASRAM（4 bank 仲裁）
```

主 CPU 的 Control C1、生产 Datapath 和原 SRAM 仲裁 RTL 均不修改。Vicuna 的指令 RAM 位于 CNN 内部，主 CPU 使用 MMIO 写入它；它不是主 CPU 的 IMEM，也不是重新引入之前放弃的主 IMEM 串口烧录方案。

## 为什么需要命令寄存器

原 CPU 的地址译码器仅允许 CNN 窗口中偏移 0x00～0x20 的九个字，且读写必须零等待。仅扩大 `CNN_MMIO_SIZE` 不能让 CPU 访问 NVDLA 的全部寄存器，也不能使原流水线等待 CSB 应答。

新 `cnn_command_port` 把一次慢速配置访问变成“写地址、写数据、提交、轮询完成”。CPU 看到的寄存器保持零等待；CNN 内部保持请求直到目标应答。不要沿用旧 CNN 描述符寄存器的含义。

| CPU 地址 | 名称 | 含义 |
|---|---|---|
| 0x40000000 | TARGET_ADDR | 要访问的内部目标字节地址 |
| 0x40000004 | TARGET_DATA | 写数据 |
| 0x40000008 | COMMAND | 写 1 提交写操作，写 2 提交读操作 |
| 0x4000000C | STATUS | bit0 忙，bit1 已完成，bit2 协议/超时错误 |
| 0x40000010 | RESULT | 上一笔目标访问的返回值 |
| 0x40000014 | TRANSACTIONS | 已收到目标应答的事务计数 |

每次新合法命令清除旧完成位。命令执行时不允许覆盖地址、数据或再次提交，违规置错误位且不改变在途目标。软件每次提交后必须等待 `STATUS[1:0]==2` 并检查错误位。超时后系统复位恢复；不要继续提交可能与迟到应答混淆的配置访问。

内部目标地址 0x40000000～0x4003FFFF 对应原生 NVDLA CSB 字节地址。例：要读 NVDLA 完成状态，先把 **0x4000100C 写入 TARGET_ADDR**，再提交读命令，最后从 RESULT 取回。CPU 不能直接对 0x4000100C 执行 load。

## Vicuna 任务和程序接口

下表为内部目标地址，均通过上述命令寄存器间接访问。

| 目标地址 | 读/写含义 |
|---|---|
| 0x40040000 | 读状态：bit0 busy、bit1 done、bit2 fault、bit3 配置错误；写 1 启动 |
| 0x40040004 | 源数据 SRAM 字节地址 |
| 0x40040008 | 目标数据 SRAM 字节地址 |
| 0x4004000C | 元素数量 |
| 0x40040010 | 软件定义的程序模式 |
| 0x40040014 | 结果码，0 表示正常完成 |
| 0x40040018 | 本次任务经历的时钟数 |
| 0x4004001C | 完成任务数 |
| 0x40041000～0x40044FFC | 16 KiB 局部指令 RAM 的写入窗口 |

流程：引擎空闲时装入完整程序 → 写参数 → 写启动 → 轮询 done 并检查 fault/结果码。忙时禁止改程序、参数或再次启动。当前没有程序长度/CRC 校验，软件负责完整装载有效程序。异常访存或看门狗到期需要系统复位。

小控制核启动 PC 为局部 0x80。数据接口中的 0xFFFF0010/14/18/1C 分别读源地址、目标地址、数量、模式；向 0xFFFF0000 写完整 32 位结果码表示完成。程序必须先等待全部输出写回，再发送完成；测试程序使用已接通应答的 `fence`。

硬件配置：128 位向量寄存器，64 位算术通路，32 位单端口存储接口。FP16/FP32 支持来自此前独立验证所用的同一固定源码配置，本次不是完整指令集一致性验收。

## 共享存储握手

| SRAM 客户端 | 用途 |
|---|---|
| 0 | NVDLA 读取 |
| 1 | NVDLA 写回 |
| 2 | Vicuna/内部小控制核数据读写 |
| 3～10 | 本版关闭 |

只有 `cnn_valid[i] && cnn_ready[i]` 才表示接受请求；`cnn_response[i]` 表示完成。不同 bank 可以同周期接受多个客户端，同 bank 由原仲裁器安排。不能把“有三个客户端”解释为始终有三笔并行访问。

Vicuna 存储桥每次仅允许一笔请求在途，保持完整 OBI ID。完整字写为一笔 SRAM 写，部分字节掩码分解为一到三笔字节写，全部完成后才返回一次应答。读出的是完整 32 位字，向量 LSU 自行取有效字节。非法或跨界地址不会提交 SRAM，并置故障。

这种桥优先保证接入正确，吞吐量仍有优化空间；没有多 outstanding、缓存一致性或自动数据依赖调度。主 CPU 必须避免在任务进行中修改其输入、权重、输出区域。软件等待 NVDLA 完成后才能让 Vicuna 读取依赖输出；独立任务可用互不重叠的缓冲区并发。

## 对上游封装的适配

`rtl/hybrid/vicuna_soc_core.sv` 是固定版本 `vicuna2_unit_testing/build_model/cv32e40x/vproc_top.sv` 的独立集成副本，保留原许可头。没有修改卷积或向量算术数据通路。修改包括：

- 新增外部数据 grant，取消“请求即被内存接受”的假设。
- 请求/响应 ID 从被截断的一位恢复为 OBI_ID_WIDTH 位；标量 ID 给定默认值。
- 修正请求记录队列索引，按每个端口的计数索引。
- 在无待完成访存时回应无缓存系统的 FENCE/FENCE.I 刷新请求。

NVDLA 保留先前已通过校验的 `nv_small` 官方生成 RTL 和带 `#delay` 的 RAM 模型。联合编译时，PULP 头文件的函数宏 `COVER` 与 NVDLA 的覆盖开关重名，需要定义 `DISABLE_TESTPOINTS` 关闭 NVDLA 非功能覆盖点。不能因此取消 RAM 时序。

## 小规模验证范围

仿真使用真正六模块 SoC，主 CPU 执行 RV32I 固件，装入 Vicuna 程序并发出全部配置请求。测试平台只在开始前初始化主 IMEM 和 DATASRAM，并在结束后观察 SRAM；没有代替 CPU 发 MMIO。

实际通过以下三组（具体 PASS 记录见交付）：

1. 最小 NVDLA 1×1 卷积，之后 Vicuna 执行 7 字节 INT8 PReLU，检查末尾保护字节；再次启动 3 字节任务，检查重复启动和完成位清除。
2. NVDLA 6×8 空间、192 输入通道、32 输出通道、3×3 卷积及 SDP 输出，再对写回区做 INT8 PReLU。
3. NVDLA 8×8×64 的 2×2 池化，与 256 个 FP32 元素的 PReLU 独立任务同时运行；之后 Vicuna 处理池化结果并再次启动短任务。

官方 NVDLA 输出先独立核对官方 CRC32；Vicuna 的每个输出字节与 Python 参考比较。这里的 INT8 PReLU 系数为 1/4，负值使用算术右移，舍入向负无穷；是明确约定的测试算法，不是任意模型的量化规范。测试处理官方张量缓冲区（包括填充字节），没有新增图像张量排布转换。FP32 只测试有限、可精确表示的数，使用符号掩码＋浮点乘法。

联合配置中，“加载 → 比较 → 浮点乘法 → 选择”的 FP32 PReLU 序列有部分元素错误；改为等价的“加载 → 浮点乘法 → 比较 → 选择”后，256 元素并发测试逐字节通过。增加一次冗余加载的诊断变体还触发了任务看门狗。**根因尚未彻底定位，可能涉及该配置的指令衔接或集成时序；不能把已通过的特定程序外推为任意程序可靠。** 两种顺序及失败记录均保留，应在扩展算子前继续排查。这次没有修改向量算术 RTL 来掩盖差异。

并发用例实测：1965 个周期中 Vicuna 任务未结束且 NVDLA 发出访存请求，其中 230 周期双方同发请求；Vicuna 等待仲裁 16 周期，最终池化和 FP32/INT8 结果均正确。三项成功进程合计约 51.38 秒；原联合模型编译约 173.73 秒（精确值见结果 JSON）。

**本轮不包括 UART 收图、不跑大图、不证明完整人脸识别网络或速度提升。** IMAGE_BRIDGE 与 CLOCK 已在实际顶层实例化，但本轮 UART 保持空闲，主 CPU 不发 load_req。

## 复跑

使用本机已准备的固定源码、工具链和 NVDLA/Vicuna 配置缓存：

```powershell
wsl -d Ubuntu-22.04 -e python3 '/mnt/d/code/FPGA1/cpu_control (2)/cpu_control/scripts/run_hybrid_soc.py'
wsl -d Ubuntu-22.04 -e python3 '/mnt/d/code/FPGA1/cpu_control (2)/cpu_control/scripts/run_hybrid_soc.py' --reuse
wsl -d Ubuntu-22.04 -e python3 '/mnt/d/code/FPGA1/cpu_control (2)/cpu_control/scripts/check_hybrid_adapters.py'
```

首次联合编译最多两个编译进程；后续 `--reuse` 核对源码哈希，只重编软件程序并重新仿真。每项上限 500000 个周期和 180 秒电脑时间。首次工具准备、联合硬件编译、软件编译与实际仿真耗时分别记录，不用旧独立模型的耗时代替联合测试耗时。
