# 译码单元与执行单元合并建议

日期：2026-10-04  
对象：CPU 六模块目标划分中的 `decode_issue_unit` 与 `execute_unit`  
性质：设计建议，不修改生产 RTL、C1 编码、现有接口文档或硬件图

---

## 1. 先给结论

**可以合并，而且从减少总图连线、降低顶层端口数量和方便新手讲解的角度看，合并是合理的。**

但必须区分两种完全不同的“合并”：

| 合并方式 | 是否建议 | 含义 |
|---|---|---|
| 合并模块层级，内部保留 `ID/EX` 流水寄存器 | **建议** | 外面看是一个 `decode_execute_unit`，内部仍然先译码、锁存到 ID/EX，再进入执行逻辑；五级流水行为不变 |
| 删除 `ID/EX`，让译码和执行在同一拍组合完成 | **不建议用于当前项目** | 会改变流水级边界、关键路径、冒险规则和逐周期行为，已经不是简单的模块合并 |

因此，本文推荐的方案是：

> 把 `decode_issue_unit` 和 `execute_unit` 合并成一个较大的 `decode_execute_unit`，但在模块内部明确保留 `ID/EX` 寄存器和 D/E 两个逻辑区域。

合并以后，CPU 对外仍然是 32 bit RV32I 五级流水；只是内部功能模块从六个变成五个：

```text
1. fetch_unit
2. decode_execute_unit
3. memory_access_unit
4. writeback_unit
5. pipeline_control_unit
```

`cpu_core` 仍然只是集成和接线外壳，不计入五个功能模块。

---

## 2. 为什么工业上可行

### 2.1 公开处理器核已经存在“译码+执行”组合方式

低功耗 RISC-V 核 Ibex 的默认流水线将第二级定义为组合的 Instruction Decode and Execute（ID/EX）阶段，译码、寄存器读取和执行放在同一阶段中。这说明“译码与执行作为一个功能区域”在真实处理器设计中是可行的。[Ibex Instruction Decode and Execute](https://ibex-core.readthedocs.io/en/stable/03_reference/instruction_decode_execute.html)、[Ibex Pipeline Details](https://ibex-core.readthedocs.io/en/latest/03_reference/pipeline_details.html)

但 Ibex 默认是两级流水，它只能证明组合方案可行，不能直接证明当前五级流水 CPU 应该删除 `ID/EX`。

### 2.2 工业设计也常保留独立 ID 和 EX 流水边界

OpenHW Group 的 CV32E40X 使用四级顺序流水，将 Instruction Decode 和 Execute 分成不同阶段：寄存器读取在 ID，ALU、分支判断和访存地址生成在 EX。这说明在模块组织和时序设计中保留 ID/EX 边界同样是成熟做法。[CV32E40X Pipeline Details](https://docs.openhwgroup.org/projects/cv32e40x-user-manual/en/latest/pipeline.html)、[CV32E40X Register File](https://docs.openhwgroup.org/projects/cv32e40x-user-manual/en/latest/register_file.html)

所以工业上没有“译码和执行必须分开”或“必须合并”的唯一答案。真正的判断标准是：

- 目标流水级数；
- 时钟频率和关键路径；
- 是否需要多周期执行单元；
- 冒险、前递和冲刷逻辑是否容易验证；
- 团队如何划分模块所有权；
- 合并后能否保持原有周期级行为。

### 2.3 对当前项目而言，模块合并比流水级合并更合适

当前目标划分中：

- `decode_issue_unit` 保存 ID/EX 状态；
- `execute_unit` 是纯组合逻辑，不保存流水状态；
- 二者之间有一组很宽的 E 级数据、地址/编号和控制连接；
- 执行结果仍需进入 `memory_access_unit` 中的 EX/MEM。

因此，把纯组合的执行逻辑包进拥有 ID/EX 状态的译码模块，在层级上是自然的。只要 ID/EX 仍然存在，综合后的寄存器边界和主要组合路径就不必改变。

## 3. 合并能解决什么问题

### 3.1 总图会明显简化

原六模块总图中，译码单元到执行单元有一组 201 bit 的逻辑连接：

| 线组 | 位宽 | 主要内容 |
|---|---:|---|
| 数据线 | 96 bit | `rd1_e`、`rd2_e`、`imm_e` |
| 信号线 | 26 bit | `valid_e`、ALU 选择、访存类型、写回选择、分支和跳转类型等 |
| 地址/编号线 | 79 bit | `pc_e`、`pc4_e`、`rs1_e`、`rs2_e`、`rd_e` |
| 合计 | **201 bit** | D 级锁存后送往 E 级的完整信息 |

合并以后，这 201 bit 不再穿过 `cpu_core` 顶层，也不用在总图中画成两个模块之间的外部线束，而是留在 `decode_execute_unit` 内部。

### 3.2 顶层方向性更清楚

合并前，回写数据和控制信号分别接到译码、执行两个模块：

```text
writeback_unit ─→ decode_issue_unit
writeback_unit ─→ execute_unit

pipeline_control_unit ─→ decode_issue_unit
pipeline_control_unit ─→ execute_unit
```

合并后可以画成：

```text
writeback_unit ─→ decode_execute_unit
pipeline_control_unit ─→ decode_execute_unit
```

连接方向更少，更适合报告和新手讲解。

### 3.3 模块数量从六个降为五个

五个模块仍能保持清楚的职责：

| 模块 | 职责 |
|---|---|
| `fetch_unit` | PC、同步取指和 IF/ID |
| `decode_execute_unit` | 译码、寄存器堆、ID/EX、前递选择、ALU、比较和跳转判断 |
| `memory_access_unit` | EX/MEM、Data SRAM、CNN MMIO 和 M 级读数据 |
| `writeback_unit` | MEM/WB 和最终写回选择 |
| `pipeline_control_unit` | 跨 D/E/M/W 的冒险、暂停、冲刷和前递控制 |

## 4. 合并不能解决什么问题

### 4.1 不会真正消灭那 201 bit 硬件连接

这 201 bit 信息仍然必须从 ID/EX 寄存器送到 ALU、比较器、分支逻辑和后续流水级。合并只是把它们从“模块外部端口”变成“模块内部连线”。

因此可以准确地说：

> 合并减少的是图中箭头、RTL 顶层端口和模块间接线，不是指令执行所需的信息量。

综合工具也可能展开或扁平化层级，所以不能因为 RTL 图上少了端口，就宣称芯片面积一定减少。

### 4.2 不会自动提高性能

只做层级合并并保留 ID/EX 时，D 级和 E 级的寄存器边界没有变化，理论上不应期待明显 IPC 提升。

物理综合可能因为层级、布局或优化范围变化产生小幅差异，但必须以综合时序、面积和布线报告为准，不能仅凭模块数量判断。

### 4.3 不会消除流水控制单元

`pipeline_control_unit` 同时观察 D、E、M、W 四级：

- D 级源寄存器；
- E 级源/目的寄存器和 Load 状态；
- M/W 级目的寄存器与写回状态；
- E 级跳转重定向。

这些信息跨越多个功能模块。因此不建议把 `pipeline_control_unit` 一起并入 `decode_execute_unit`，否则控制责任会重新变得混乱，并使访存、写回状态反向穿入一个更大的模块。

## 5. 推荐的五模块结构

```text
                         ┌──────────────────────────────┐
同步 IMEM ←────────────→ │ 1. fetch_unit                │
                         │    PC / Fetch / IF-ID         │
                         └──────────────┬───────────────┘
                                        │ D级指令、PC、valid
                                        ▼
                         ┌──────────────────────────────┐
                         │ 2. decode_execute_unit       │
                         │                              │
                         │  D区：译码 / RegFile / Imm   │
                         │       │                      │
                         │      ID/EX  ← 必须保留       │
                         │       │                      │
                         │  E区：Forward / ALU / Branch │
                         └──────────────┬───────────────┘
                                        │ E级结果和访存控制
                                        ▼
                         ┌──────────────────────────────┐
Data SRAM ←────────────→ │ 3. memory_access_unit       │ ←────────→ CNN MMIO
                         │    EX/MEM / LSU / Route      │
                         └──────────────┬───────────────┘
                                        │ M级写回候选
                                        ▼
                         ┌──────────────────────────────┐
                         │ 4. writeback_unit            │
                         │    MEM/WB / WB MUX            │
                         └──────────────┬───────────────┘
                                        │ 写回与WB前递
                                        └──────→ decode_execute_unit

                         ┌──────────────────────────────┐
                         │ 5. pipeline_control_unit     │
                         │ Hazard / Stall / Flush / Fwd │
                         └──────────────────────────────┘
                           观察D/E/M/W，控制Fetch和DE
```

图上应在 `decode_execute_unit` 内部画出一条明确的 `ID/EX` 寄存器边界。这样别人不会误解为译码和 ALU 已经变成同一拍组合路径。

建议模块中文名称写成：

```text
译码与执行单元（内部保留 ID/EX 流水边界）
```

而不是只写“译码执行一体化”，后者容易让人误以为流水级也被合并。

## 6. 合并后仍然存在的外部连接

合并只消除原来的 `decode_issue_unit → execute_unit` 外部边界。新的 `decode_execute_unit` 仍需与其他模块连接。

### 6.1 输入来源

| 输入来源 | 线组 | 主要信号 | 连接位宽 |
|---|---|---|---:|
| `fetch_unit` | 数据线 | `instr_d[31:0]` | 32 |
| `fetch_unit` | 信号线 | `valid_d` | 1 |
| `fetch_unit` | 地址线 | `pc_d[31:0]`、`pc4_d[31:0]` | 64 |
| `writeback_unit` | 数据线 | `wb_data_w[31:0]` | 32 |
| `writeback_unit` | 信号线 | `rf_we_w` | 1 |
| `writeback_unit` | 地址/编号线 | `rd_w[4:0]` | 5 |
| `memory_access_unit` | 数据线 | `mem_forward_m[31:0]` | 32 |
| `pipeline_control_unit` | 信号线 | `id_ex_flush`、`fwd_a[1:0]`、`fwd_b[1:0]`、`fwd_store[1:0]` | 7 |
| SoC 时钟硬件 | 信号线 | `clk` | 1 |
| SoC 复位硬件 | 信号线 | `rst_n` | 1 |

`wb_data_w` 在合并模块内部同时连接寄存器堆写口和 EX 前递选择器，不再需要在 `cpu_core` 中分别接到两个模块。

### 6.2 输出对象

| 输出对象 | 线组 | 主要信号 | 连接位宽 |
|---|---|---|---:|
| `fetch_unit` | 地址线 | `branch_target_e[31:0]`、`jalr_target_e[31:0]` | 64 |
| `memory_access_unit` | 数据线 | `alu_result_e[31:0]`、`store_data_e[31:0]` | 64 |
| `memory_access_unit` | 信号线 | `valid_e_o`、`regwrite_e_o`、`memread_e_o`、`memwrite_e_o`、`load_type_e_o[2:0]`、`store_type_e_o[1:0]`、`wb_sel_e_o[1:0]` | 11 |
| `memory_access_unit` | 地址/编号线 | `pc4_e_o[31:0]`、`rd_e_o[4:0]` | 37 |
| `pipeline_control_unit` | D/E 状态线 | D/E valid、源使用标志、Load 标志 | 6 |
| `pipeline_control_unit` | 地址/编号线 | `rs1_d`、`rs2_d`、`rs1_e`、`rs2_e`、`rd_e` | 25 |
| `pipeline_control_unit` | 跳转信号线 | `redirect`、`redirect_sel[1:0]` | 3 |

上表中的“D/E 状态线”具体为：

```text
uses_rs1_d        1 bit
uses_rs2_d        1 bit
valid_e           1 bit
uses_rs1_e        1 bit
uses_rs2_e        1 bit
memread_e         1 bit
```

以上实际合计是 6 bit。推荐让 `valid_d` 继续由 `fetch_unit` 直接扇出到 `pipeline_control_unit`，因此新的合并模块不重复输出 `valid_d`。

## 7. 必须保持的设计要求

如果以后真正实施 RTL 合并，以下条件不能因为“少画线”而改变。

### 7.1 必须保留 ID/EX 流水寄存器

ID/EX 仍然负责保存：

- `valid_e`；
- `pc_e`、`pc4_e`；
- `rd1_e`、`rd2_e`、`imm_e`；
- `rs1_e`、`rs2_e`、`rd_e`；
- 源寄存器使用标志；
- ALU 操作和输入选择；
- 寄存器写、Load、Store；
- Load/Store 类型；
- 写回选择；
- 分支和跳转类型。

模块内部仍应清楚地区分：

```text
IF/ID输出 → D级组合逻辑 → ID/EX寄存器 → E级组合逻辑 → memory_access_unit
```

### 7.2 译码控制必须先经过 ID/EX

主译码和 ALU 译码在 D 级产生控制，但不能直接控制下一周期以外的指令。每条指令的数据和控制必须一起进入 ID/EX，避免发生“数据属于指令 A、控制却属于指令 B”的错配。

### 7.3 `id_ex_flush` 语义不能改变

`pipeline_control_unit` 输出的 `id_ex_flush` 必须直接清空合并模块内部的 ID/EX：

- load-use 时向 E 级插入 bubble；
- EX 重定向时清除错误路径年轻指令；
- 不能误清 EX/MEM 或 MEM/WB 中更老的指令。

### 7.4 分支和跳转仍在 E 级判定

当前基线是：

- Branch/JAL 目标：`pc_e + imm_e`；
- JALR 目标：`(前递后的 rs1 + imm_e) & 32'hffff_fffe`；
- `redirect` 在 E 级产生；
- 错误路径冲刷 IF/ID 和 ID/EX。

合并模块层级后，不能为了接线方便把分支判断提前到 D 级，否则分支数据相关、前递和冲刷时序都会变化。

### 7.5 前递优先级不能改变

必须继续保持：

- MEM 级非 Load 结果优先于 WB；
- WB 结果次优先；
- 否则使用寄存器堆读数；
- `fwd_store` 独立选择 Store 数据；
- 禁止把 M 级 Load 的地址当成 Load 数据前递；
- 紧邻 Load 的消费者仍插入一拍 bubble。

### 7.6 寄存器堆写回行为不能改变

最终写使能仍应满足：

```text
rf_we_w = valid_w && regwrite_w && (rd_w != 0)
```

同一个 `wb_data_w` 同时用于：

- 写回寄存器堆；
- WB→EX 前递。

不能在合并模块内形成两个语义不同的写回值。

### 7.7 流水优先级不能改变

当前控制优先级应继续保持：

```text
复位 > EX重定向 > load-use暂停 > 正常推进
```

### 7.8 存储器和 MMIO 时序不能改变

合并译码与执行模块不能顺便改动访存边界：

- Data SRAM 请求仍按当前 E→M 接受关系工作；
- Load 返回数据仍在 M 级处理；
- Store 提交阶段保持当前生产 Datapath 行为；
- CNN MMIO 仍在 M 级访问；
- 合法 CNN MMIO v1 仍要求同周期 `ready=1`；
- 不新增 Control 到 CNN 的专用硬件端口。

## 8. 不建议采用的做法

### 8.1 不要删除 ID/EX 只为减少线数

如果删除 ID/EX，一条普通 ALU 指令的组合路径可能变成：

```text
IF/ID寄存器
 → 指令译码
 → 寄存器堆读取
 → 前递比较和选择
 → ALU输入选择
 → ALU
 → 分支比较或结果输出
 → EX/MEM寄存器
```

这条路径明显长于当前分开的 D 级和 E 级路径。是否还能满足目标时钟频率必须重新综合和验证，不能把它当成等价重构。

### 8.2 不要把流水控制也塞进合并模块

这样虽然模块数更少，但会形成一个同时负责译码、寄存器堆、执行、冒险、分支、暂停和冲刷的“大模块”。其问题包括：

- 单元验证边界不清楚；
- M/W 状态大量反向进入该模块；
- 后续添加乘除法或异常时更难维护；
- 团队并行开发时容易产生文件冲突。

### 8.3 不要只改信号名称而不保留逐周期语义

模块合并不能成为修改 C1 编码、访存阶段、分支阶段或复位行为的理由。若周期级行为发生变化，应作为新的微架构版本评审，而不是称为“画图简化”。

### 8.4 不要用一个没有字段说明的 200 bit 匿名大总线

为了少写端口而把所有字段机械拼成 `logic [200:0] bus`，会让波形和代码难以审查。

如果以后需要在 RTL 中归组，建议使用有名字的 packed struct。由于 `cpu_control_pkg.sv` 是当前 C1 共享编码基线，不建议为了画图直接修改它；可以另建只服务内部连线的 package，例如：

```text
cpu_pipeline_bundle_pkg.sv
```

这样能保持 C1 数值编码和共享文件哈希不受影响。

## 9. 三种实施方案比较

| 方案 | 图中模块数 | 是否保留 ID/EX | 工业可行性 | 风险 | 建议 |
|---|---:|---|---|---|---|
| A. 只在报告图中合并，RTL 不动 | 5 | 是 | 高 | 很低 | **当前最推荐** |
| B. 新建 `decode_execute_unit` 包装层，内部实例化原译码和执行逻辑 | 5 | 是 | 高 | 低到中 | 后续需要真实五模块 RTL 时推荐 |
| C. 删除 ID/EX，把译码和执行变成同一拍 | 4级或新的混合结构 | 否 | 技术上可做 | 高 | 当前项目不推荐 |

### 9.1 当前阶段推荐方案 A

用户当前目标主要是把硬件总图画清楚，而不是马上重写生产 RTL。因此可以在图中直接使用一个大框：

```text
decode_execute_unit
├── Decode区
├── Register File / ImmGen
├── ID/EX流水寄存器
└── Execute区
```

框内画一条明显的 ID/EX 竖线，框外不再绘制原 201 bit `decode_issue_unit → execute_unit` 连接。

这能立刻达到减少图中信号线的目的，同时不对已经验证的生产 RTL 做任何声明性修改。

### 9.2 后续若实施 RTL，推荐先采用方案 B

第一步不要马上搬运或改写所有逻辑，而是新建包装模块，在内部实例化已经验证的译码和执行子模块，并把 201 bit 连接留在包装模块内部。

优点是：

- `cpu_core` 顶层立即变简单；
- 原有细粒度逻辑可以继续单元测试；
- 更容易做新旧层级的逐周期对比；
- 如果出现问题，可以快速定位是包装接线问题还是原逻辑问题。

包装层验证稳定以后，是否进一步合并源文件属于代码组织选择，不影响功能模块已经对外合并的事实。

## 10. 工业设计方面的利弊

### 10.1 优点

- 顶层端口和总图连线明显减少；
- D/E 数据关系集中，报告更容易讲清楚；
- `wb_data_w` 可在模块内部同时服务寄存器写回和 EX 前递；
- 译码控制与对应执行逻辑距离更近，代码导航更直接；
- 小型 RV32I 核只有一个简单 ALU，没有多发射，模块规模仍可控制。

### 10.2 缺点

- 模块会同时拥有寄存器堆、译码、ID/EX 和 ALU/分支逻辑，文件或层级较大；
- 单独验证“纯译码”和“纯执行”时需要保留内部子模块或测试入口；
- 多人开发时，译码负责人和执行负责人可能同时修改同一包装层；
- 后续增加乘除法、异常、CSR 或调试功能时，模块责任可能继续膨胀；
- 如果工程约束禁止综合器跨层优化，层级变化可能影响时序与面积，需要重新综合确认。

### 10.3 对当前 CPU 规模的判断

当前设计是单发射、顺序、RV32I 五级流水：

- 没有乱序发射；
- 没有重命名；
- 没有复杂调度队列；
- 当前 `mul_busy` 固定为 0；
- 执行单元主要是前递 MUX、ALU、比较和跳转目标计算。

在这个规模下，`decode_execute_unit` 不会大到无法维护。因此从工程规模看，**模块层级合并是可接受的**。

## 11. 如果将来真正修改 RTL，最低验收要求

只有以下项目全部通过，才能宣称合并是“等价重构”。

### 11.1 静态检查

- 所有端口方向和位宽与合并前一致；
- ID/EX 字段无遗漏；
- C1 编码数值不变；
- `cpu_control_pkg.sv` 不因内部 bundle 被随意修改；
- 无组合环路；
- 无多驱动；
- 综合和 lint 无新增严重警告。

### 11.2 逐周期行为检查

新旧结构应逐周期比较：

- PC；
- `valid_d/e/m/w`；
- `rd_e/m/w`；
- `pc_sel`、暂停和冲刷；
- `fwd_a`、`fwd_b`、`fwd_store`；
- ALU 结果；
- `wb_data_w` 和 `rf_we_w`；
- Data SRAM 请求序列；
- CNN MMIO 请求序列。

### 11.3 必测场景

- 普通 ADD 和其他 RV32I 算术指令；
- MEM→EX 前递；
- WB→EX 前递；
- Store 数据前递；
- Load-use 一拍暂停；
- Branch taken/not-taken；
- JAL 和 JALR；
- 跳转与数据前递同时发生；
- 非法指令安全 NOP；
- 复位期间禁止存储写副作用；
- SRAM Load/Store；
- CNN MMIO 读写；
- 连续混合程序。

### 11.4 工具验收

- 运行 Control 全回归；
- 运行真实 Control + 生产 Datapath 的 ADD 和混合程序；
- 使用本机 Vivado XSim 2026.1 建立全新运行目录；
- 不复用旧 VCD、旧 PNG 或旧构建结果；
- 若目标是进入 FPGA，还必须重新跑综合、实现和时序报告；
- 条件允许时增加新旧结构形式等价检查。

## 12. 最终建议

### 当前画图和汇报

**建议合并。** 把两个框画成一个 `decode_execute_unit`，并在内部明确画出：

```text
Decode区 → ID/EX寄存器 → Execute区
```

这样能够减少最显眼的 201 bit 模块间连接，并把写回、前递和流水控制的箭头集中到一个模块上。

### 当前生产 RTL

**暂时不要因为画图而修改。** 当前六模块本身还是目标重划分方案，真实验证使用的是原 Control + Datapath。先把“五模块图”作为结构建议，不应声称五模块 RTL 已经完成。

### 后续真的重构

优先创建包装式 `decode_execute_unit`，内部保留原译码、ID/EX 和执行子逻辑；确认逐周期等价以后，再决定是否进一步合并源文件。

### 一句话结论

> 可以把译码和执行合并成一个功能模块来减少图中连线，但必须保留内部 ID/EX 流水边界；推荐“模块合并”，不推荐“流水级合并”。
