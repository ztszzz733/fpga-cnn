# 为什么原接口还要补充信息

> 2026-09-14 P1 更新：M / Control 已正式接受 C1 v1.0 开发基线；当前确认及待办以 [P1 正式回复](../../docs/control_reply_to_P1.md) 为准，验证以 [本次报告](../../docs/verification_report.md) 为准。下文保留此前说明，不作为最新冻结状态。

原始规格给出了主要分工，但有些接线信息不够完整。若直接照着写，控制模块可能把不同指令混在一起判断。

## 主要问题和解决方法

| 原来缺少什么 | 可能出什么错 | 现在如何处理 |
|---|---|---|
| 执行阶段正在使用哪个寄存器 | 把识别阶段的编号用于执行阶段 | 数据通路反馈当前执行指令的编号 |
| 执行阶段是哪种分支或跳转 | 比较结果和指令对不上 | 指令类型跟随流水线并反馈 |
| 指令是否真的使用某个输入 | 立即数碰巧像寄存器编号，造成误停 | 明确标记每个源是否使用 |
| 访存阶段是不是正在读内存 | 把访问地址当成已经读出的值 | 标记读内存状态并禁止错误传递 |
| 某一阶段有没有有效指令 | 空位或已取消指令误写数据 | 每个阶段保存有效标记 |
| 立即数怎样解释 | 数据通路生成错误的立即数 | 控制模块明确给出立即数类型 |
| 控制输出属于哪个阶段 | 当前新控制影响了另一条旧指令 | 写明先保存再使用的阶段关系 |

这些补充组成 C1 方案，对方在 D1 中原则接受。控制模块仍保持组合逻辑，不在内部另存一套猜测出来的流水状态。

## 哪些问题只是写清楚，尚未硬件验证

- 乘法的完整等待方式尚未实现，预留忙信号固定为零。
- 内存“一周期”需要进一步说明采样边沿，不能凭文字推断兼容。
- 原规格的地址对齐描述较笼统，现按字节、半字和字分别约定。
- CNN 软件通过普通读写指令操作；启动脉冲由数据通路产生，状态由 CNN 提供。
- 非法和特殊指令采用项目安全空操作方案，没有实现标准异常处理。
- CNN 参数格式、起始地址和最终识别路径仍有团队层面的待定项。

具体操作见 [接口接线说明](接口接线说明.md)；时序限制见 [存储器时序说明](存储器时序说明.md)。
