# mover23顶层波形阅读说明

核对日期：2026-11-12。读取本目录原始VCD和随包记录，未重新仿真或修改原始波形。

## 1. 先打开哪个文件

双击[open_top_waveform_local.cmd](open_top_waveform_local.cmd)。它使用本机已有GTKWave，默认加载精简的CNN/存储视图和原A～H标记。VCD约660.9MB，首次加载需要等待。

原open_top_waveform.cmd优先寻找包内runtime或工作区根目录tools；这两个路径在本次解压目录都不存在。本机版额外查找已有工程工具，保留了原启动脚本。

需要原78信号完整视图时，可在本目录执行：

```text
open_top_waveform_local.cmd all
```

先缩放到完整时间范围确认整体阶段，再放大C～D或F～H；不要在全程缩略图上逐拍读握手。

## 2. 这份波形验证的范围

四帧小任务链，共44个任务，包含K3、K1、DW7、Post、Add、Pad六类算子。23路接口都连接，本次实际启动15个实例。CPU、CNN、tile RAM及DATA MOVER为RTL，PS GP0/HP0和DDR为测试模型。

随包记录为PASS，核对28812字节中间输出、4份最终结果；outputs.bin合计32字节。它与此前16算子十图完整网络属于不同配置和不同工作负载，不能混用性能结论，也不能当作板上DDR验证。

## 3. 特别注意横轴单位

VCD声明`$timescale 1ps`。A～H的原始数字都是ps，GTKWave可能自动显示成ns或us。

本文件clk上升沿间隔为10ps，这是测试记录的时间刻度，不代表板上时钟频率。原始波形结束约3.424409us，不能据此说FPGA只用了3.4us。

报告给出的342441个硬件周期，若按100MHz作条件换算，则为3.42441ms；该换算不等于板级频率已经验收。

## 4. 按A～H顺序看

| 标记 | 原始ps | 显示为us | 应观察什么 |
|---|---:|---:|---|
| A | 75 | 0.000075 | rst_n从0变1，CPU开始取指 |
| B | 510230 | 0.510230 | 批次启动命令附近，查看CNN MMIO写入 |
| C | 516215 | 0.516215 | 首个算子任务启动，位22的Pad先工作 |
| D | 554485 | 0.554485 | 首次搬页读完成，read_bytes变为1024 |
| E | 896885 | 0.896885 | active=0x400007，K3#0/1/2与Pad共4个实例在途 |
| F | 2535675 | 2.535675 | 首次HP0写回请求，此时尚未完成全部44任务 |
| G | 2750525 | 2.750525 | debug_completed达到44，计算任务全部完成 |
| H | 3421635 | 3.421635 | write_bytes达到23552，最后一次记录的搬页写回完成 |

G之后仍有DDR写回：**计算任务完成、本地结果完成、DDR写回完成要分开判断。** H后约3421895ps，completed被维护流程清零；应查看它曾达到44的过程，不能只看波形末尾的0就认为任务没完成。

## 5. 第一遍只读任务进度

| 信号 | 含义 | 读法 |
|---|---|---|
| debug_unit_start[22:0] | 发射任务的脉冲 | 第i位为1，表示给实例i启动任务 |
| debug_unit_active[22:0] | 实例仍持有任务 | 多位同时为1说明多个任务同时在途，包含访存等待 |
| debug_work[22:0] | 算子本拍work推进指示 | 与active分开看；MAC类与后处理类的work含义需按算子区分 |
| debug_completion[22:0] | 任务完成脉冲 | 哪一位为1，哪个实例的任务完成 |
| debug_completed[10:0] | 累计完成任务数 | 正常批次内递增到44；十六进制44是0x2C |
| debug_error / debug_fault | CNN/存储错误 | 本次正常路径保持0 |

mask按低位到高位解释：

| 位号 | 实例 | 本次启动数 |
|---|---|---|
| 0～3 | K3#0～3，普通3×3和DW3共享 | 各2次 |
| 4～7 | K1#0～3 | 各1次 |
| 8～15 | K1#4～11 | 各0次，本次未用 |
| 16 | DW7 | 4次 |
| 17～20 | Post#0～3 | 各4次 |
| 21 | Add | 4次 |
| 22 | Pad | 8次 |

例如`start=0x400000`表示只启动Pad；`active=0x00000F`表示4个K3都在途。active不是MAC利用率，任务持续期间可以包含等待。

## 6. 第二遍放大C～D，看一次缺页和返回

建议观察0.516～0.555us：

1. Pad先启动，向CNN存储接口提交对本地逻辑地址0x8000附近的访问。
2. 同一路`cnn_valid[i] && cnn_ready[i]`表示请求被接收；尚不能说明读数据或写操作已经完成。
3. 存储发现所需页不在本地，`debug_page_misses`增加，HP0发起DDR读取。
4. 查看`ARVALID/ARREADY`地址握手，以及`RVALID/RREADY`返回数据握手；本次搬页为1024字节。
5. `debug_mover_read_bytes`增加到1024后，原CNN请求收到`cnn_response[i]`，算子才能按自己的状态机继续。

CNN信号中，第i位都对应同一个实例。地址/数据总线是23路32位拼接：第i路位段为`[32*i +: 32]`。不能把736位地址总线显示的一长串数当成单个地址。

`cnn_write[i]=1`表示写请求；`cnn_byte[i]=1`表示字节访问。读请求在response时读取对应rdata；写请求也须等完成响应，不能仅凭ready就发布后继任务完成。

## 7. 第三遍看F～H的DDR写回

读通路：`ARVALID && ARREADY`接受读地址，`RVALID && RREADY`传递读数据，`RRESP`检查错误。

写通路：分别看`AWVALID && AWREADY`地址接受、`WVALID && WREADY`数据接受，再看`BVALID && BREADY`写响应。地址和数据握手不要求恰好同拍。`WSTRB[7:0]`表示64位写数据中的哪些字节有效。

`VALID=1、READY=0`时是反压等待，请求相关字段应保持稳定；总线地址或数据自己变化，不等于发生一次有效传输。响应码00在本测试普通访问中表示正常成功。

`debug_mover_read_bytes`与`debug_mover_write_bytes`是搬页完成后的累计字节数，不是最终输出文件的长度。本次最终读27648=27×1024字节、写23552=23×1024字节；4份最终结果只有32字节，中间特征及整页读写带来了额外流量。

本文件提供的主要是顶层接口和进度观察。完整完成条件仍需结合维护响应、测试台断言及metrics/result记录，不能只看一个计数器就替代全部协议检查。

## 8. CPU和PS信号什么时候看

- CPU TO IMEM：看CPU是否持续取指；imem_addr是指令地址。
- CPU TO LOCAL RAM：本次有少量本地读写；不是CNN特征数据的主通路。
- IMAGE BRIDGE TO CNN：看CPU控制命令是否到达CNN MMIO。
- PS GP0 MAILBOX：控制/配置及测试数据交接；与HP0 DDR数据通路分开看。
- STORAGE MAINTENANCE：看维护/写回命令与响应，解释为何CNN计算结束后存储仍继续工作。

## 9. 文件对应关系

- mover23_top_raw.vcd：原始时序数据，未修改。
- top_interconnect.gtkw：原完整接口视图。
- cnn_storage_reading.gtkw：新增阅读用精简视图，仅选择已有信号。
- top_milestones.tcl：原A～H标记。
- 波形阅读核对.json：从原始VCD选取信号重新核对的观察记录，不是新仿真。
- metrics.json / result.json / simulation.log：原测试统计、来源哈希与PASS日志。

先判断“有没有启动、能否继续推进、是否达到44、DDR是否完成写回、有没有错误”，再放大单条请求。这样比一次同时读完全部78根信号更容易理解。
