## 1. 总体结论

Z 方接受 DZ1 提出的 CPU—CNN 连接方向，并确认保留新版 CNN 内置九个 MMIO 寄存器，CPU 通过对齐 LW/SW 配置、启动和轮询，CPU/CNN 分别使用共享 Data SRAM 的 A/B 口。

本次补充实际测试网络的存储分配、真实工程附件和 B 口适配分工建议。不要求 CPU 暂停 M2 核心开发，也不将尚未确定的 SRAM 实体时序视为已经冻结。

## 2. 对 DZ1 第 6.1 节的逐项确认

| 事项 | Z 方回复 |
|---|---|
| 寄存器归属 | **接受。** CNN 保留内部九个寄存器；CPU 侧只负责地址路由、访问桥接和 Load 回读，不维护第二套配置寄存器。 |
| MMIO 基地址 | **确认。** 首版采用 `BASE_ADDR=32'h4000_0000`。接受系统预留 `0x4000_0000～0x4000_0FFF` 的 4 KiB 窗口，但仅九个合法寄存器地址转发到 CNN。 |
| MMIO ready | **确认。** 地址命中且 `mmio_we` 或 `mmio_re` 有效时，当前顶层组合输出 `mmio_ready=1`；不因 CNN BUSY 而插入等待。 |
| 非法 / 未对齐地址 | **接受 CPU 侧处理。** 未实现地址、未对齐地址或不支持的访问宽度不发送到 CNN；Load 返回 0，Store 无副作用且不永久等待。此行为由 CPU 桥实现，不依赖 CNN 提供完成响应。 |
| 混合内部复位 | **有条件接受，无需为本方案修改 CNN RTL。** CPU 内部同步复位、CNN 内部异步复位可以共用系统复位，具体约束见第 3 节。 |
| 访问宽度 | **接受。** CNN MMIO 首版仅使用 4 字节对齐 LW/SW；普通 SRAM 仍可使用 CPU 已支持的字节/半字访问。 |
| CNN stub | **同意 Datapath 按 Z1/Z2 行为自行编写联调 stub。** 本次提供真实 RTL 工程，无需等待 Z 方另交 stub 才开始 MMIO 联调；stub 覆盖边界见第 7 节。 |

补充确认：FEATURE_SIZE、LAYER_PARAM 命名，CONTROL[5:2] 的 OP_TYPE，LAYER_PARAM[21] 的 ReLU6 语义，以及六种算子和 CHW/OIHW 数据格式，均按 Z1 保持。

对于 DZ1 第 4 节第 4、5 项，Z 方均确认接受。同时提醒：合法地址 ready=1 只表示本次 MMIO 访问已应答，不等于启动一定被接受。BUSY 时配置写入被忽略，重复 START 会置 ERROR，CPU 应按既定状态规则处理。

`valid_m && memwrite_m && address_hit` 是 Store 请求的必要门控；若该有效指令跨多个时钟保持，还需防止同一条指令重复提交。请保留 DZ1 已提出的“一条有效 SW 只提交一次”约束。

## 3. 复位方案确认及边界

接受 DZ1 C-05 的兼容方案，条件如下：

1. 首版 CPU、CNN 和 SRAM 适配器采用同一时钟域。
2. 系统 `rst_n` 低电平至少覆盖两个有效上升沿，使 CPU 同步复位逻辑确实获得复位。CNN 保留现有 `posedge clk or negedge rst_n` 实现。
3. 复位释放由系统统一的同步释放电路产生，满足各寄存器的时序要求；不能仅把外部异步复位直接连入后宣称已同步释放。
4. 复位期间 CPU/MMIO 桥不得发出有效读写请求，SRAM A/B 口适配器清除未完成事务状态，并禁止残留写入。CNN 的组合 MMIO ready 本身不由 rst_n 门控，系统不能把它当作复位结束指示。
5. 不要求硬复位清空整片 SRAM，但重新启动前软件必须完成所需输入、权重、bias 的装载。
6. CNN CONTROL.RESET 是局部软复位，不应直接复位 SRAM B 口适配器。已呈现请求仍须得到 ready 并排空；等待 BUSY=0 后才能重新启动，已提交写入不会回滚。

若后续改为多时钟域，需另行设计跨域与各域复位分发。本回复的兼容结论不直接覆盖多时钟方案。

## 4. 当前测试网络的 SRAM 容量核算

### 4.1 112×112 输入、15 个任务的确定性测试链

核算依据：`scripts/generate_vectors.py` 与当前 `build/vectors/manifest.json` 中的 `chain_00` 至 `chain_14`。这是一条使用测试权重的小通道网络，不是训练模型的容量规格。

以下为现有向量实际使用的地址，末地址包含在范围内：

| 区域 | 起始地址 | 最大使用末地址 | 数据字节数 | 说明 |
|---|---|---|---:|---|
| 输入 | 0x00000101 | 0x00009400 | 37,632 | 3×112×112 INT8 |
| 激活 A | 0x00010001 | 0x00011880 | 6,272 | 各层复用该起点，按该区域最大输出长度计 |
| 激活 B | 0x00018001 | 0x00018620 | 1,568 | 与 A 交替使用，按该区域最大输出长度计 |
| 残差 R | 0x00024001 | 0x000240C4 | 196 | 保留 4×7×7，供 ADD 使用 |
| 最终输出 | 0x00028001 | 0x00028080 | 128 | FINAL_OUTPUT 写入 |
| 全部卷积/DW 权重 | 0x00030003 | 0x000306DA | 1,752 | 预先装载，逐层连续分配 |
| 全部 bias | 0x0003E000 | 0x0003E2DF | 736 | 184 个 INT32 |

容量结论：

- 固定分区中各区域最大有效数据量之和为 **48,284 字节**，其中 A/B 激活双缓冲合计 7,840 字节。该值不是包含地址空洞后的 SRAM 容量，也不是优化内存生存期后的理论下限。
- 当前起点故意包含非对齐地址，用于验证字节读写和相邻字节保护。按每个区域涉及的完整 32 位字计，覆盖量之和为 **48,308 字节**；CPU 不能使用这些首尾字中的相邻字节进行并发写入。
- 保留现有地址布局且 SRAM 基地址为 0 时，最高访问字节是 `0x0003E2DF`，连续 SRAM 至少需要 **254,688 字节（0x3E2E0）**。
- **建议第一轮采用 256 KiB（262,144 字节），地址范围 0x00000000～0x0003FFFF。** 当前默认回归也是这个容量。现有全部 34 个向量任务按分别初始化的测试场景复用内存，不需要把各独立测试的数据同时叠加装入。

以上数值由本次交付的 `docs/DZ1_memory_audit.json` 给出机器可读核算。若重新压紧布局，需要同步重生成任务地址和向量，再验证；本次不以理论压紧容量替代已使用的地址图。

### 4.2 未训练 ONNX 测试图

现有 ONNX fixture 使用三个 256 字节激活槽，范围 `0x1000～0x12FF`；权重 410 字节，自 `0x1300` 开始；bias 568 字节，自 `0x149C` 开始。按当前地址图，最后使用地址为 `0x16D3`，从零起连续覆盖需 5,844 字节；导出文件的仿真容量仍配置为 256 KiB。

三个槽包含中间激活生存期和最终输出的复用，不能简单减少为两个槽。该测试图也不是训练模型，不代表真实 MobileFaceNet 的 SRAM 需求。

### 4.3 软件区与地址图建议

建议首轮保持上表布局，以便直接复用已有向量。`0x0003F000～0x0003FFFF` 可作为 **4 KiB CPU 数据/栈预留候选区**；是否足够由 CPU 软件负责人确认，尚未完成 CPU 程序容量验证。CPU 的栈、全局变量、运行时数据和其他外设不能侵占 CNN 数据区。

PC/IMEM 地址归 CPU 侧确定。若指令与数据共享同一物理存储器，还需合并程序空间重新计算容量；上面的 256 KiB 建议仅针对当前 CNN 测试布局，不自动包含指令存储需求。

## 5. SRAM B 口适配器的责任回复

**建议由 Datapath / 系统集成侧实现双口 SRAM wrapper 及 CNN B 口适配器，Z 方提供 Master 端协议说明和已有测试模型，并配合联调。请对方确认接手人。**

原因是 SRAM 器件/IP、实体端口、地址采样沿和读延迟均由系统侧选择；目前这些参数尚未冻结，Z 方没有一份可宣称已匹配该实体 SRAM 的适配器可交付。

本次工程中的 `rtl/accelerator_mem_if.sv` 是 CNN 内部 RAM Master；`tb/model_data_ram.sv` 是仿真 RAM 模型。两者均不能直接标记为已完成的 FPGA 双口 SRAM B 口适配器。

请系统侧补齐下表后冻结实体协议：

| 事项 | Z 方建议 / 要求 | 待系统侧提供 |
|---|---|---|
| SRAM 基地址 / 容量 | 首轮 0x00000000 / 256 KiB | 是否采用，以及具体器件资源可行性 |
| A/B 口结构 | CPU A 口固定延迟，CNN B 口独立握手适配 | SRAM 模块名、端口声明、时钟和使能定义 |
| 读时序 | CNN 完成沿之前 mem_rdata 必须有效 | 地址采样沿、数据有效沿、是否启用输出寄存器 |

CNN 单笔未完成事务、等待期间地址/数据/请求保持、无 byte-enable、整字读改写、ready 作为完成握手的协议按 Z1 保持。不要在同步读数据尚未有效时把 mem_ready 常量接 1，也不要把它或 BUSY 接成 CPU 全局 stall。

## 7. Stub 及真实网络边界

同意 Datapath 自行建立与 Z1 顶层一致的 stub，供 CPU MMIO 和流水线控制测试使用。建议至少覆盖寄存器读写、单次启动、配置锁定、STATUS 粘滞、重复 START 和软复位；固定完成周期应标注为 stub 的测试约定。

如果 stub 不实现真实 RAM Master 或不写计算结果，应明确这些项目未覆盖。stub 的 PASS 不能代表 SRAM B 口或真实 CNN 联调通过，参数合法性和完整数据结果以真实 RTL 为准。

当前没有可交付的真实训练模型输入/权重/bias/Golden 集。附件包含确定性测试网络与未训练 ONNX fixture，具有可重复输入及逐层期望输出，可验证功能和协议，但不能用于宣称识别准确率。

真实模型、预处理、L2 归一化、相似度与身份库负责人仍需三方指定。获得模型后还需检查算子和量化兼容性，再计算实际容量；不能假定当前 256 KiB 对真实模型同样足够。
